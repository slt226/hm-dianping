> **结论先行：技术深度已经够实习，差的全在「工程交付」和「数据」。**

## 二、P0：不补会直接掉分的 7 件事

### P0-0 初始化脚本缺 13 张表（半天，**最紧急**）

**现状证据**：

```text
src/main/resources/db/hmdp.sql 里 CREATE TABLE 只有 11 张：
tb_blog / tb_blog_comments / tb_follow / tb_seckill_voucher / tb_shop / tb_shop_type
/tb_sign / tb_user / tb_user_info / tb_voucher / tb_voucher_order

而 mysql> show tables 是 24 张。
```

也就是说，**别人按 README 执行 `mysql < hmdp.sql` 之后直接启动，券体系、会员、搜索、工单、AI、死信表全都没有**，
第一次点开"券中心"就会 `Table 'hmdp.tb_coupon_template' doesn't exist`。

这比"没有 Docker"严重得多：Docker 只是不方便，**这是跑不起来**。

**为什么 DDL 会缺**：券/会员/死信的表是分天迭代加的，DDL 当时贴进了
`docs/W1-券体系.md`、`docs/Day10`、`docs/Day11`、`docs/秒杀P0-04` 的正文里，**从没回写进初始化脚本**。
这正是"文档与代码漂移"的活样本——你自己就是受害者。

**做什么**：

```text
db/
  init/
    01-base.sql          # 现有 hmdp.sql 原样搬过来（含基础数据）
    02-coupon.sql        # tb_coupon_template / tb_coupon_use_log / tb_user_coupon
    03-member.sql        # tb_member / tb_member_level / tb_growth_log
    04-seckill.sql       # tb_seckill_dead_letter（从 db/seckill_dead_letter.sql 搬）
    05-ai.sql            # tb_ai_session / tb_ai_message / tb_knowledge_doc + 9 条知识库
    06-search-behavior.sql  # tb_search_log / tb_user_behavior / tb_service_ticket
```

DDL 直接从库里导，比手抄 markdown 可靠：

```powershell
# 只导结构，不导数据（避免把测试数据带进仓库）
mysqldump --defaults-extra-file=$env:TEMP\hmdp-my.cnf --no-data --skip-add-drop-table hmdp `
  tb_coupon_template tb_coupon_use_log tb_user_coupon > db\init\02-coupon.sql
```

**验收**：`DROP DATABASE hmdp; CREATE DATABASE hmdp;` → 按顺序跑 `db/init/*.sql` → 启动 → `/coupon/center`、
`/member/info`、`/seckill/ops/queues` 全部 200，且**没有一条 `Table doesn't exist`**。

**面试怎么讲**：
> "我在做交付的时候发现初始化脚本只覆盖了最初 11 张表，后面迭代加的 13 张表 DDL 都散在文档里。
> 我把它收敛成了按模块编号的 `db/init/*.sql`，并用`DROP DATABASE` 重建验证了一遍。
> 这件事让我意识到：**DDL 也是代码，必须和代码同源同版本**。"

### P0-1 一键可运行（半天）

**为什么最重要**：简历上的项目链接，面试官点开的概率不高，但只要点开，"跑不起来"就是负分。
反过来，能 `docker compose up` 三分钟起来，本身就是工程能力的证明。

**做什么**：

1. 加 `docker-compose.yml`（MySQL/Redis/RabbitMQ 三个依赖，初始化 SQL 挂载进容器）：

```yaml
# docker-compose.yml（与本项目实际配置对齐：Redis 带密码、MySQL 5.7、MQ 带管理台）
services:
  mysql:
    image: mysql:5.7
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: hmdp
      TZ: Asia/Shanghai
    ports: ["3306:3306"]
    volumes:
      - ./db/init:/docker-entrypoint-initdb.d   # hmdp.sql + 02~05 的升级脚本，按文件名顺序执行
      - mysql-data:/var/lib/mysql
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_general_ci
  redis:
    image: redis:6
    command: ["redis-server", "--requirepass", "123321", "--appendonly", "yes"]
    ports: ["6379:6379"]
  rabbitmq:
    image: rabbitmq:3.9-management
    ports: ["5672:5672", "15672:15672"]
volumes:
  mysql-data:
```

2. 配置外置：`application.yaml` 里的密码改成占位符，默认值保持"本地能跑"。

```yaml
spring:
  datasource:
    url: ${DB_URL:jdbc:mysql://127.0.0.1:3306/hmdp?useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&characterEncoding=utf8&useUnicode=true}
    username: ${DB_USER:root}
    password: ${DB_PASSWORD:root}
  redis:
    host: ${REDIS_HOST:127.0.0.1}
    password: ${REDIS_PASSWORD:123321}
  rabbitmq:
    host: ${MQ_HOST:127.0.0.1}
```

3. README 顶部加「快速开始」三段：`docker compose up -d` → `mvn spring-boot:run` → `curl /shop/1`。

**验收**：删掉本机已装的依赖（或换台电脑），只按 README 操作，5 分钟内 `/shop/1` 返回 200。

**面试怎么讲**：
> "我把它做成了 compose 一键起，因为面试官不会花半小时装 MySQL。依赖隔离之后还有个附带好处：
> 我可以随时 `down` 掉 Redis 来做降级演练——这正好是我项目里'Redis 不可用不雪崩'那条设计的验证方式。"

这个回答的价值不在"我会 Docker"，而在**你把 Docker 用成了实验工具**。

### P0-2 压测与数据（一天）

**现状证据**：`docs/` 里 4 处提到压测，全是"压测时把 prefetch 调回 10~50，否则吞吐会被 prefetch=1 限制成串行速度"（`秒杀P0-02:203`）这类**建议**，没有一份**结果**。
秒杀项目最容易被追问的就是"多快、瓶颈在哪"，没有数据等于放弃了最值钱的一段叙事。

**怎么做**——不要只跑一次"看起来很猛"的压测，要跑**三组对照**，每组只改一个变量：

| 组 | 变量 | 想证明什么 |
|---|---|---|
| A | 临时把秒杀入口改成"直接 DB 扣减"（加一个 `@Profile("naive")` 开关，别污染主分支） | Redis 挡掉了多少流量：DB QPS 从 N 降到 0.0x·N |
| B | `prefetch=1 / concurrency=2` ↔ `prefetch=50 / concurrency=4` | MQ 参数对吞吐与串行度的影响（你的 02 课已经踩过这个坑） |
| C | 并发 500 / 1000 / 2000，库存固定 100 | 拐点在哪、拐点后是拒绝还是超时 |

**必须记录的口径**（缺一项这份数据就不可信）：

- 机器：CPU 核数 / 内存 / 单机单实例（不要写成"集群"）；
- 工具与参数：JMeter 线程数、Ramp-up、循环次数、是否复用连接；
- 初始状态：`seckill:stock:{id}` 初值、DB `stock` 初值、订单表行数；
- 结果：QPS、P95、P99、错误率、**DB 库存与 Redis 库存的差值**、订单数 − 卖出数（少卖）、卖出数 − 可卖数（超卖）；
- 收尾：压测后必须核对 `Redis + 死信 = DB − P`，否则上一组的数据污染下一组。

**报告模板**（`docs/压测报告.md`），结论段只写三句：

```markdown
## 结论
1. 加 Redis 预扣后，落到 MySQL 的写请求从 100% 降到 1.2%（500 并发、库存 100），DB 不再是瓶颈。
2. 单机 QPS 拐点约 1.8k（Tomcat 200 worker，Hikari 10 连接），继续加压错误率从 0.3% 升到 11%，瓶颈在连接池而非 Redis。
3. 三组压测后 stock: Redis 0 / DB 0 / 订单 100，超卖 0、少卖 0；死信表 0 行。
```

**面试怎么讲**（这段背下来）：
> "我压测不是为了报一个 QPS 数字，是为了找拐点。500 并发时 DB QPS 只有个位数，说明 Redis 把流量挡住了；
> 加到 1500 之后错误率上来了，我用 `SHOW PROCESSLIST` 和 Hikari 的指标定位到是连接池 10 个连接打满，不是 Redis 慢。
> 所以这个系统的瓶颈在 MySQL 连接池，扩容优先级是'先加连接池/加从库'，而不是'上 Redis 集群'。"

⚠️ **口径纪律**：本机（单机、Windows、机械盘 MySQL）压出来的 QPS 就是几百到几千。
报告里写清受限条件，比虚报十万 QPS 更有说服力——**追问一句"你怎么压的"就露馅了**。

### P0-3 秒杀入口还有一次 DB 查询（代码级，半天）

**现状证据**：`service/impl/VoucherOrderServiceImpl.java:65`

```java
SeckillVoucher sv = seckillVoucherService.getById(voucherId);   // ← 每个秒杀请求都打一次 MySQL
```

这条查询和"Redis 挡住所有流量"的叙事**直接矛盾**：压测时会看到 `tb_seckill_voucher` 的 QPS = 全量请求 QPS。
面试官读代码到这一行，你之前讲的"Redis 削峰"会被打七折。

**怎么改**（三选一，按你能讲清的程度选）：

| 方案 | 做法 | 代价 |
|---|---|---|
| ① Redis 缓存券元数据 | `seckill:meta:{id}` 存 `beginTime/endTime/status`，TTL 30s；Lua 里顺带判断时间窗 | 时间窗最多晚 30s 生效（秒杀场景可接受） |
| ② 本地缓存 | `ConcurrentHashMap` + 启动预热 + 建券时失效 | 多实例要广播失效（本项目单实例，能讲清即可） |
| ③ 把时间窗下推到 Lua | Redis Hash 存 `begin/end`，脚本内 `TIME` 比较 | 逻辑最重，但完全没有网络往返 |

推荐 ①：改动最小，且能把 05 课的 `RedisConstants` 复用起来。
改完再压一次 A 组，你会得到一条非常漂亮的数据：**"DB QPS 从 2k 降到 3"**。

**面试怎么讲**：
> "第一版 Lua 挡了库存，但我后来发现入口还有一次 `getById` 查券——等于每个被拒绝的请求都先去打一次 MySQL。
> 把它改成 Redis 缓存券元数据（30 秒 TTL）后，DB 侧的 QPS 从四位数降到个位数。
> 这个问题是我自己读代码发现的，压测数据也印证了。"

**"自己发现并修掉自己的坑"** 是实习面试里最稀缺的信号，比多写三个功能都值钱。

### P0-4 统一错误码 + 参数校验（半天）

**现状证据**：`dto/Result.java` 只有 `success / errorMsg / data / total`；全项目 `@Valid` 仅 2 处。
现在前端只能靠**中文文案**判断错误类型——文案一改，前端就挂。

**做什么**：

```java
// dto/ErrorCode.java —— 分段：0 成功 / 4xxx 客户端 / 5xxx 服务端；4xxx 内再按 41 参数、42 秒杀 细分
public enum ErrorCode {
    OK(0, "ok"),
    BIZ_GENERAL(4000, "业务处理失败"),   // 旧 throw new BizException("文案") 的归口
    PARAM_INVALID(4100, "参数不合法"),
    UNAUTHORIZED(4101, "未登录或登录已过期"),
    SECKILL_NOT_EXIST(4201, "秒杀券不存在"),
    SECKILL_NOT_BEGIN(4202, "秒杀尚未开始"),
    SECKILL_ENDED(4203, "秒杀已结束"),
    SECKILL_SOLD_OUT(4204, "库存不足"),
    SECKILL_REPEAT(4205, "每人限购一件"),
    INTERNAL(5000, "服务繁忙，请稍后重试");
}
```

> 分段的理由（面试要能一句话说清）：**首位数字 = 责任方**。4xx 是调用方改参数/改状态就能解决的，
> 5xx 是服务端故障必须告警；段内第二位再分业务域（41 通用入参、42 秒杀），
> 这样运维按 `code like '5%'` 就能筛出真正的故障，前端按 `4xxx` 只弹提示。

- `Result.fail(ErrorCode)` 重载保留 `fail(String)`，老代码不用全改；
- `BizException` 增加 `errorCode` 字段（老构造器保留，归口 `BIZ_GENERAL`）；
- 加 `@ExceptionHandler(MethodArgumentNotValidException.class)` / `BindException` / `ConstraintViolationException` 到**已有的** `BizExceptionAdvice`，返回 `PARAM_INVALID + 字段名`；
- 给秒杀、重放、建券三个入口的入参加 `@NotNull @Min`。
- ⚠️ 别再新建第二个 `@RestControllerAdvice`：已有 `BizExceptionAdvice`（业务，warn）和 `WebExceptionAdvice`（兜底，error）

**面试怎么讲**：错误码要能说出"为什么分段"和"前端怎么用"（`code` 判分支、`errorMsg` 给人看、`traceId` 给客服查）。

## 四、明确不要做的（性价比低、追问必翻车）

| 别做 | 原因 |
|---|---|
| 拆微服务、上 K8s / Nacos / Dubbo | 单体 16 个 Controller 谈微服务，第一个问题"为什么拆、拆完解决了什么"就答不上；实习面试考的是基础不是分布式治理 |
| 引 Elasticsearch 做搜索 | `SearchController` 目前是**空壳**（4 行）：先把它做成 DB `LIKE` + 写 `tb_search_log` 就有价值了；引 ES 就要答倒排、分词、一致性，数据量也撑不起来 |
| 编造 QPS / 并发数 | 一旦被追问"用什么压的、机器什么配置、瓶颈在哪"，编的数字撑不过三个问题 |

补功能不难，难的是**补完之后整份项目仍然"自洽"**。下面每一条都是面试官会顺手一问的地方。

| # | 翻车点 | 为什么会翻车 | 怎么防 |
|---|---|---|---|
| 1 | **数据口径不写清** | 报了 QPS 却不写机器和参数，等于自曝 | 压测报告必须含：机器配置、JMeter 参数、初始库存、结论三句；脚本一起提交 |
| 2 | **文档与代码漂移** | 改了 P0-3 的缓存逻辑，docs 里还写着"每请求查 DB" | 每次改代码同 commit 内回改对应 docs；文档头部记一句 `> 对应 commit: xxxx` |

| 7 | **异常被吞** | `rollbackRedis` 里 `catch (Exception ignored)`，Redis 回滚失败没有任何痕迹 | 改成 `log.warn` + 打点，并说明"最终由对账兜底"——**吞异常必须有兜底，才算设计而不是偷懒** |

## 六、面试怎么讲（最重要的一节）

### 6.1 五分钟主线稿（逐字背下来）

> "我做的是一个本地生活优惠券平台，核心是秒杀系统。
> 秒杀的技术难点不在于'快'，而在于**三个不一致**：
> 一是 Redis 预扣和 MySQL 落库不一致；二是消息重复投递导致重复扣减；三是消费者最终失败后，已经扣掉的库存没人还回来。
>
> 我的方案是按'三道闸'来设计：
> 第一道，Lua 脚本在 Redis 里原子完成'判库存 + 一人一单 + 预扣'，把 99% 的请求挡在数据库之前；
> 第二道，MQ 削峰，消费者用'订单号主键 + 幂等门禁 + 唯一索引'三件套保证重复消息不会重复扣库存；
> 第三道，消息最终失败就进死信队列，落库成'死亡证明'，再由定时对账任务按券核对 `Redis 库存 = DB 库存 − 在途预扣量`，不一致就修复并写回死信表。
>
> 工程上我还补了两块：一个是死信的运维接口（列表 + 带状态机校验和分布式锁的人工重放），
> 一个是队列健康告警（采样 pending 消息数，连续 120 秒异常才确认告警，避免消费端本地重试的抖动误报）。
>
> 压测下来，500 并发、库存 100 的场景，DB 侧写请求只有个位数 QPS，最终 100 单全部落库，超卖 0、少卖 0。
> 我做这个项目最大的收获是一句话：**宁可少卖，不可超卖**——少卖可以人工补，超卖只能赔钱。"

这段稿子的结构：**业务 → 难点（三个不一致）→ 方案（三道闸）→ 工程闭环 → 数据 → 认知**。
最后那句"宁可少卖不可超卖"是你的个人标签，面试官记住人比记住功能重要。

### 6.3 高频追问 20 问（左列问题，中列一句话答案，右列别踩的坑）

| # | 追问 | 一句话答案 | 坑 |
|---|---|---|---|
| 1 | 为什么用 Lua，不用分布式锁？ | 锁只能互斥，判库存+扣库存+记用户要**原子多步**；Lua 在 Redis 单线程内一次执行完，没有锁的释放/续期问题 | 别说"Lua 比锁快"，要说是**原子性**需求 |
| 2 | 为什么 RabbitMQ 不用 Kafka/RocketMQ？ | 量级不大但要**死信队列 + 本地重试 + 延迟能力**，RabbitMQ 原生支持；Kafka 更适合日志流 | 别贬低 Kafka |
| 3 | 消息丢了怎么办？ | 生产端 confirm + return 双确认，发送失败**回滚 Redis 预扣**；消费端手动 ack；极端丢失靠对账兜底 | 别只答"开了 confirm 就够了" |
| 4 | 重复消费怎么办？ | 三道：订单号主键唯一、`selectById` 幂等门禁放在扣库存之前、DB 唯一索引 `uk_uid_vid` 兜底 | 门禁顺序错=白做 |
| 5 | Redis 扣了、DB 没扣怎么办？ | 死信落库 + 定时对账，差多少补多少，`retry_count` 区分人工与自愈 | 别答"靠人盯着" |
| 6 | orderId 为什么不用 UUID？ | UUID 无序、字符串索引页分裂；`RedisIdWorker` 是时间戳+序列号，全局唯一且**趋势递增** | 别把雪花算法说错位 |
| 7 | `@Transactional` 加在 `@RabbitListener` 上有效吗？ | 有效，Spring 代理的是 bean；但要保证异常**抛出方法外**才会回滚 | catch 后 return = 手动 commit |
| 8 | 死信消费者为什么不回滚 Redis？ | 本地重试会重复调用，回补会被放大 N 倍（实测 82 次把 97 补到 179）；改为每条死信只补一次 | 这是你最真实的踩坑，一定要讲 |
| 9 | `retry_count` 有什么用？ | 0 = 系统自愈，>0 = 人工介入；出事时能一眼看出"这单是人碰过还是自己好的" | 别答"统计用" |
| 10 | 告警为什么要确认 120 秒？ | 消费端本地重试 1s+2s 会让 pending 短时抖动，立即告警就是狼来了；120s 是抖动窗口的 2 倍余量 | 数字要能解释来源 |
| 11 | 怎么保证不超卖？ | Redis 预扣是唯一出口；DB 扣减带 `stock > 0` 的 CAS；死信只补回 Redis，不碰 DB | 三条都要说全 |
| 12 | 少卖了怎么办？ | 死信可人工重放；宁可少卖也不超卖 | 主动承认取舍 = 加分 |
| 13 | 一人一单并发怎么保证？ | Lua 内 `SADD` 判重原子；DB `uk_uid_vid` 唯一索引兜底 | 别只说 Redis |
| 14 | 库存预热怎么做的？ | 建券/活动开始时把 `tb_seckill_voucher.stock` 写入 `seckill:stock:{id}`；缺失时 Lua 返回 1（视为售罄）而不是放行 | 缺 key 千万别当 0 卖 |
| 15 | Redis 挂了怎么办？ | 秒杀降级为"请稍后"（快速失败），不让流量穿透到 DB；券查询走 Redis 失败也降级查 DB | 讲降级策略而不是"加集群" |
| 16 | MQ 挂了怎么办？ | 发送失败回滚预扣并返回"系统繁忙"；`Confirm` 超时按失败处理 | 别答"MQ 不会挂" |
| 17 | 对账多久跑一次？为什么？ | 我这个是定时 + 按券维度，间隔要小于"用户可容忍的少卖时长"，跑太勤会拖 DB | 频率要有依据 |
| 18 | 为什么不用延迟队列做超时取消？ | 那是订单超时未支付场景，本项目没接支付回调，硬加会变成"没被测过的代码" | **不会就别加** |
| 19 | 秒杀怎么做限流？ | 目前只有一人一单 + Lua 闸门；下一步打算在网关/入口加令牌桶，按 userId+IP 限 | 承认现状 + 有方案 = 合格 |
| 20 | 你项目里最难的 bug？ | 死信重试期间重复回补 Redis，库存越补越多；靠"日志里的库存数字 + 对账发现的不变式破坏"定位 | 备好完整故事（现象→怀疑→验证→结论） |

> 每个问题都有"**现象 → 怀疑 → 验证 → 结论**"四步，别只报结论。

**代码层是零**：8 个类全是 4 行空壳——`AiServiceController`、`IAiService`、`LlmClient`、`ChatRequest`、
`AiSession`、`AiMessage`、`KnowledgeDoc`、`SearchController`。

> 结论：这是一个**"设计完整、实现为零"**的模块。留着它，风险远大于收益——
> 简历写"AI 问答"，面试官点开只有一个空类，比不写还糟。

### 10.2 三个选项（选一个，别摇摆）

| 选项 | 工作量 | 收益 | 风险 | 适合谁 |
|---|---|---|---|---|
| **A. 删壳** | 10 分钟 | 仓库干净，"没有的功能不出现"；不留死代码 | 0 | 时间紧 / 不想在 AI 上被追问 **（已执行：8 个空类已 `git rm`，`mvn -o -q compile` 通过）** |
| **B. 知识库问答（不接大模型）** | 半天 | 有可演示的业务闭环；能讲"召回优先于生成、无命中转人工、配额限流" | 低（零外部依赖、零成本、零幻觉） | **推荐大多数人** |
| **C. 接真 LLM** | 1~2 天 | 简历上"AI"最有说服力，可投 AI 相关岗 | 高：key 管理、成本、超时、幻觉、评测，每个都要答得上 | 时间充裕且目标岗位偏 AI |

**为什么推荐 B**：面试官问 AI，本质是在问"你知道大模型不能乱用吗"。
B 的每一条设计都在回答这个问题，而且**不需要 API key、不会因为网络挂了 demo 翻车**。

### 10.3 B 方案：半天落地的 5 步

```
POST /ai/chat  { "sessionId": null, "question": "优惠券为什么用不了" }
```

1. **建会话（幂等）**：`sessionId` 为空则生成 32 位 id，靠 `uk_session` 保证重复提交不重复建；
2. **召回**：拿 `question` 去匹配 `tb_knowledge_doc`（`keywords` 命中数 + `priority` 排序），取 Top-3；
3. **组装答案**：Top-3 的 `content` 拼接返回；命中数为 0 → **不猜**，返回兜底话术 + 会话置 `status=2`（已转人工）+ 写 `tb_service_ticket`；
4. **落库**：`tb_ai_message` 写 user / assistant 两条；`turn_count+1`；超过 10 轮把前 N 条压成 `summary`（截断即可，别上 LLM）；
5. **预留 LLM 位**：`LlmClient` 写成接口 + `Optional<String> polish(...)` 空实现，开关 `ai.llm.enabled=false`；
   将来接大模型只是"把模板答案交给它润色"，**接口和表都不用动**。

**这个方案的四个面试讲点**（每个都比"我调了个 API"值钱）：

- **AI 不在金钱/库存主链路上**：它挂了不影响下单，这条决定了引入它是安全的；
- **召回优先于生成**：知识库命中就不让模型编，命中不了就转人工——这是幻觉的产品级解法；
- **降级是设计出来的**：模板兜底 + 开关关闭，不是 try-catch 吞掉；
- **量级决定技术选型**：9 条知识不需要向量库。被问就答"先做关键词召回，超过几千条再上 embedding + 向量检索"。

### 10.4 AI 部分的三个"别做"

| 别做 | 原因 |
|---|---|
| 简历写"基于大模型的智能客服"但只做了 B | 一被追问 prompt/评测/成本就穿帮；B 就写"知识库问答 + 转人工兜底" |
| 为 9 条数据上向量数据库 / RAG 框架 | 会被问"为什么不用关键词""embedding 模型选型依据"，答不上就是减分 |
| 把 AI 塞进秒杀链路（如"AI 判断是否刷单"） | 秒杀链路已经闭环且被测过，加一个不确定组件 = 亲手砸掉自己最强的那条叙事 |

> **优先级排序（重要）**：
> **P0-0 补 DDL** > **P0-2 压测数据** > **B（AI 最小版）** > **P0-6 接口文档**。
> AI 是"锦上添花"，前两项是"能不能及格"。
