# 秒杀 P0 · 05 死信只能看不能动、队列挂了没人知道 · 复盘

> 前四课把链路修到"坏账会自己收敛"。这一课补两个**收敛不了**的口子：
> 人想动手时没有入口（`retry_count` 有字段没接口），系统不敢动手时没人知道（`consumers=0 + ready>0` 只躺在 info 日志里）。
>
> 前置阅读：[02 消费端幂等](秒杀P0-02-消费端幂等.md) · [03 重试与死信](秒杀P0-03-重试与死信.md) · [04 死信落库与对账](秒杀P0-04-死信落库与对账.md)

## 一、一句话概括

死信从"能看"变成"能动"：`POST /seckill/ops/dead-letters/{id}/replay` 在**不绕过任何一道防重复闸**的前提下，把一条死信重新补一次；
队列从"能查"变成"会喊"：`SeckillQueueAlertTask` 每 30 秒采样主队列与死信队列，`ready>0 且 consumers=0`（或积压超阈值、或探针失效）**持续 120 秒** → `【队列告警】`，恢复 → `【队列告警解除】`。

两件事的共同点：**它们都不改账本规则，只改"人能不能及时介入"**。04 的不变式 `Redis_stock = DB_stock − P` 一个字都没动。

## 三、人工重放：自动对账已经在重试了，为什么还要人

### 3.1 `settlePending` 覆盖不到的三件事

| 场景 | 自动对账的行为 | 人需要什么 |
|---|---|---|
| 一条 `status=0` 卡了很久，Redis 刚修好 | 每分钟重试**按 `create_time` 排序取前 200 条**，这轮可能轮不到它 | 点名 + 立刻补，而不是等下一分钟、下下一轮 |
| 待补偿超过 `SETTLE_BATCH=200` | 200 名之后的记录本轮不动 | 先补最要紧的那几条（金额大 / 用户已投诉） |
| `status=2`（已忽略）后来确认是误判 | **只扫 `status=0`**，2 永远不会被再评估 | 重新评估一次：订单若已被人工删掉，就该回补 |

还有一层是审计：`settlePending` 从不碰 `retry_count`，只有人工重放才会 `+1`。
所以这个字段能区分「系统自愈了几次」和「人介入了几次」——复盘时这两件事的责任完全不同。

### 3.2 状态闸：`status=1` 必须拒绝

先用 04 课的不变式算一遍，闸门该不该存在就一目了然：

```
Redis_stock = DB_stock − P          (P = 在途预扣数，含所有 status=0 的死信)
```

| 重放对象 | 库存动作 | P 的变化 | 结果 |
|---|---|---|---|
| `status=0`（待补偿） | `+1` | `−1`（0 → 1 已补偿） | 两边同时 +1，**等式仍成立** ✅ |
| `status=1`（已补偿） | `+1` | 本来就是 0，不变 | `Redis = DB + 1`，**凭空多卖一张** ❌ |

所以这条闸写在**服务里**，不是"前端禁用按钮"：

```java
if (before != null && before == SeckillDeadLetter.STATUS_COMPENSATED) {
    throw new BizException("该死信已补偿完成（orderId=" + record.getOrderId()
            + "），再重放会让库存多归还一张");
}
```

线上真正造成错乱的，永远是"接口被直接调了一次"，而不是"按钮被点了一次"。

### 3.3 重放为什么**不删** `doneKey`

`seckill:dlq:done:{orderId}` 存在，等于"这张券的 Redis 预扣已经归还过"。
重放时最直觉的做法是"先把 doneKey 删掉，让它能重新补"——这正是最危险的一步：

- 正常路径下它**不该存在**：补偿失败会主动 `delete`，留着它只说明补成功了；
- 它存在而 `status` 还是 0，只可能是「Redis 已 `+1`、`markStatus` 之前进程挂了」。
  此时删 key 再补一次，就是把 `+1` 变成 `+2`。

正确做法是**不删**，让 `compensateAndMark` 里已有的 doneKey 分支把状态对齐为 1、库存不动：

```java
Boolean first = stringRedisTemplate.opsForValue()
        .setIfAbsent(doneKey, "1", DONE_KEY_TTL_HOURS, TimeUnit.HOURS);
if (!Boolean.TRUE.equals(first)) {
    markStatus(record, SeckillDeadLetter.STATUS_COMPENSATED, null);   // 只对齐状态
    return false;                                                     // 明确告诉调用方"没动库存"
}
```

这不是"少补了一次"，而是**修掉一个虚高的 P**：
`status` 停在 0 时，对账会把它当成在途，目标值按 `DB − P` 算就会偏低，库存被往低压（少卖）。
把状态对齐后 P 恢复真实值，等式重新成立。

> 结论：重放只做「重置状态 + 重新走一遍补偿链路」，**没有一行代码绕过 04 的两道闸**（DB 订单校验、doneKey 抢占）。

### 3.4 一条 UPDATE 完成三件事

```java
deadLetterMapper.update(null, new UpdateWrapper<SeckillDeadLetter>()
        .eq("id", id)
        .set("status", SeckillDeadLetter.STATUS_PENDING)
        .set("compensate_time", null)
        .setSql("retry_count = retry_count + 1"));
```

- **打回 0**：进入待补偿状态，`settlePending` 也能接管；
- **清补偿时间**：`compensate_time` 表示"最后一次成功补偿的时刻"，重放后必须为空，否则看板上会出现"待补偿却有补偿时间"这种自相矛盾的行；
- **`retry_count` 用 SQL 自增**：写成 `select → setRetryCount(x + 1) → updateById` 时，两次并发重放会读到同一个旧值，计数少加一次——而这个数字是复盘时唯一的"人介入"依据。

### 3.5 返回体：`compensated` 比 `status` 更值得看

`status=1` 有四种来源，只有第一种真的动了库存。所以响应里同时给 `statusBefore/statusAfter/compensated/message`：

| 落点 | `compensated` | 真实含义 | 该不该再操作 |
|---|---|---|---|
| `status=1` | `true` | 本次真的归还了预扣（库存 +1、用户从已抢集合移除） | 不用 |
| `status=1` | `false` | 此前已回补过，本次只把状态对齐（库存**未变**） | 不用 |
| `status=2` | `false` | 订单已在库中，仍是误判死信，未回补 | 先去核对订单 |
| `status=0` | `false` | 补偿失败（Redis 仍不可用），保持待补偿 | 修好 Redis 后再点，或等对账 |

如果文案把第二行也写成"补偿成功"，运维会以为库存被加了两次，跑去改库——**一个新的、人为制造的坏账**。

## 四、告警：把"拒绝修复"翻译成一条 error

### 4.1 第四课留下的观测缺口

04 已经把 `consumers=` 打进对账的门禁日志：

```
【对账】存在在途，本轮跳过 | voucherId=10, mainReady=1(consumers=0), dlqReady=0(consumers=2), pendingDeadLetter=0
```

问题在于这行日志的**读者是人**，而故障发生时恰恰没人看：

- 它是 `info` 级别，多数团队只给 `error` 配告警；
- 消费者全挂时，对账会**永远**跳过修复——日志内容和"一切正常"长得几乎一样；
- 死信队列 `ready>0`、`consumers=0` 时，死信没人补偿，但主队列看起来完全正常。

所以这一课要做的事只有一句话：**把系统"不敢动手"的信号，升级成一条 `error`**。

### 4.2 三种违规，一个状态机

判定规则（`QueueAlertJudge.classify`）顺序有意义：**不可读 > 没人消费 > 积压**。

| 原因 | 判定条件 | 为什么单独成类 | 值班该做什么 |
|---|---|---|---|
| `NONE_CONSUMER` | `ready > 0 && consumers == 0` | 积压只会单调增长，且属于"消费者进程没了"而不是"慢" | 拉起实例 / 看消费端日志 |
| `BACKLOG` | `ready >= backlog-threshold`（默认 1000） | 消费者活着但产能不够 | 扩容消费线程 / 查下游变慢 |
| `UNREADABLE` | 探针读不到（队列不存在、broker 抖动） | `ready/consumers` 都是 `-1`，拿去比阈值会得出"积压 -1 条" | 查 broker、查队列是否被误删 |

状态机（`NORMAL → PENDING → ALERTING → RECOVERED`）：

```
       违规首次出现            持续 ≥ confirm(120s)
NORMAL ───────────▶ PENDING ──────────────────▶ ALERTING ──每 remind(600s)──▶ REMIND
  ▲                    │                            │
  └──────恢复──────────┴────────────恢复─────────────┘
                      （打一条 RECOVERED，回到 NORMAL）
```

为什么一定要有 `PENDING` 这一层：**采样密度和告警时机是两件事**。
30 秒采样是为了"看得见趋势"，120 秒确认是为了"敢开口"。
消费端本地重试窗口是 `1s + 2s`，broker 抖动几秒，消费者重启几秒——这些都会让 `ready` 短暂大于 0 且 `consumers` 短暂为 0。
没有这一层，告警会被训练成噪音，最后没人看。

### 4.3 抑制与解除

| 行为 | 如果不做会怎样 |
|---|---|
| 告警持续中，同一原因**不重复打** | 30 秒一条 `error`，一小时 120 条，真告警被淹没 |
| 告警持续中，原因**变化立刻再报** | 从"没人消费"变成"积压"，处置动作完全不同（前者拉起实例，后者扩容），沿用旧告警会误导 |
| 恢复时**主动**打 `RECOVERED` | 没有"解除"通知，值班的人不知道现在到底还在不在故障里 |
| 每 `remind-seconds` 提醒一次 | 长故障期间没有任何心跳，人会以为"已经好了" |
| `NONE` 一律不打日志 | 30 秒 × 每条队列的 debug/info 会把日志文件灌满；要确认任务活着有 `/seckill/ops/queues` |

### 4.4 判定逻辑为什么要单独成一个类

`QueueAlertJudge` 是**纯逻辑**：输入"采样值 + 当前时间戳"，输出"本轮动作"。
这样"持续 119 秒不报、121 秒报"这种边界才测得动——留在 `@Scheduled` 方法里，验一次要真等两分钟，还得祈祷期间没人发消息。
定时任务只保留三件事：**什么时候采样、采哪些队列、把结论写成日志**。

### 4.5 `QueueProbe`：一份事实，两个读者

探针从 `SeckillReconcileTask` 里抽出来了。理由不是"复用"这么空：

- 对账要判断"有没有在途"，告警要判断"有没有人消费"，读的是**同一条事实**；
- 各写一份 `queueDeclarePassive`，一旦某天给探针加了超时/换了实现，两边就会给出不同答案——排查事故时最忌讳两个监控说两套话。

`Stat` 用一个哨兵区分"读不到"和"是 0"：

```java
public static final Stat UNREADABLE = new Stat(false, -1, -1);   // ok=false，且 -1 不会被当成"空闲"
public boolean isIdle()      { return ok && ready == 0; }
public boolean isAbandoned() { return ok && ready > 0 && consumers == 0; }
```

对账把它当"有在途"（宁可不修），告警把它当 `UNREADABLE`（必须喊）——**同一个事实，两种正确的反应**。

### 4.6 运维接口

`GET /seckill/ops/queues` 每次都真实探一次，不返回缓存：

```json
{"success":true,"data":[
  {"queue":"seckill.queue","readable":true,"ready":0,"consumers":2,"alerting":false,"alertSeconds":0,"pendingSeconds":0},
  {"queue":"seckill.dlq","readable":true,"ready":0,"consumers":2,"alerting":false,"alertSeconds":0,"pendingSeconds":0}
]}
```

三个字段值得解释：
- `readable=false` 时 `ready/consumers` 为 `null` —— 不要拿 `null` 去做判断；
- `alerting=true` + `ready=0` 是**刚恢复、还没翻状态**的正常过渡；
- `pendingSeconds > 0` 是"快报警了"的观察值，压测时比 `alerting` 更有用。

## 五、实测验收

### 5.1 单测：把两分钟的时间轴压成毫秒

```
mvn -o -q -Dtest=QueueAlertJudgeTest -DfailIfNoTests=false test
→ Tests run: 9, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.045 s
```

| # | 用例 | 断言的关键点 |
|---|---|---|
| 1 | 抖动不足确认时长不告警、满 120 秒才告警 | 0s/60s/119s → `NONE`；121s → `ALERT`，`lastingMillis=121s` |
| 2 | 抖动中途恢复正常则重新计时 | 60s 时 `ready=0` 清计时；100s 再违规 → 200s 仍 `NONE`（`pendingSeconds=100`），221s 才 `ALERT` |
| 3 | 恢复后主动上报并清空状态 | `RECOVERED` 只发一次，`lasting=200s`，随后 `alerting=false`、`alertReason=null` |
| 4 | 告警期间同一原因保持安静，到提醒间隔才重复 | 120~690s 共 19 轮全 `NONE`；720s → `REMIND` |
| 5 | 告警中原因变化立即再报一次 | `NONE_CONSUMER` → `BACKLOG` 同一轮就 `ALERT`，不重走确认窗口 |
| 6 | 没人消费优先于积压 | `ready=5000, consumers=0` → 报 `NONE_CONSUMER` 而不是 `BACKLOG` |
| 7 | 积压阈值边界 | `999` 条跑 10 分钟不报；`1000` 条先 `NONE`（开始计时），121 秒后 `ALERT` |
| 8 | 读不到队列状态本身就要告警 | `UNREADABLE` → 121s `ALERT(UNREADABLE)`；恢复后 `RECOVERED` |
| 9 | 多条队列互不影响 | 主队列告警时，`seckill.dlq` 仍然 `alerting=false` |

### 5.2 告警端到端：造一个真实的"有消息、没消费者"

不去停消费者（会影响业务链路），而是**临时多监控一条没有消费者的探针队列**——正好验证"监控名单可配置"这条设计：

```powershell
# 1) 用 management API 建一个空队列（不是业务队列，实验后删除）
PUT  http://127.0.0.1:15672/api/queues/%2F/seckill.alert.probe

# 2) 用测试参数启动（把 120 秒确认缩到 10 秒、30 秒采样缩到 3 秒）
java -jar target\hm-dianping-0.0.1-SNAPSHOT.jar `
  --seckill.alert.queues=seckill.queue,seckill.dlq,seckill.alert.probe `
  --seckill.alert.confirm-seconds=10 --seckill.alert.sample-interval-ms=3000

# 3) 往探针队列发 1 条（0 个消费者）
POST http://127.0.0.1:15672/api/exchanges/%2F/amq.default/publish
     {"routing_key":"seckill.alert.probe","payload":"{\"probe\":1}","payload_encoding":"string"}

# 4) 观察恢复（两个参数只是为了快，线上是 30s/120s）
DELETE http://127.0.0.1:15672/api/queues/%2F/seckill.alert.probe/contents
```

实测日志（`logs/hmdp.log`，`com.hmdp` 的 debug 全开）：

```
16:53:49.686 ERROR SeckillQueueAlertTask : 【队列告警】有消息但没有消费者（消费端可能已全部挂掉） | queue=seckill.alert.probe, ready=1, consumers=0, 已持续 12s
16:54:10.751  WARN SeckillQueueAlertTask : 【队列告警解除】有消息但没有消费者（消费端可能已全部挂掉） | queue=seckill.alert.probe, ready=0, consumers=0, 共持续 33s
```

三个细节对得上设计：

| 现象 | 说明 |
|---|---|
| 发消息是 16:53:37 左右，告警是 16:53:49 | 采样 3 秒一次、确认 10 秒 → 实际落在第 4 次采样上（`已持续 12s`） |
| 中间 21 秒没有再刷 error | 同原因抑制生效，否则这 21 秒会多 7 条 |
| 恢复后打的是 `WARN` + "共持续 33s" | 恢复必须被看到，但不该触发告警级别 |

### 5.3 重放三条路径

准备：库里 3 条人造死信（`voucherId=10`），当时 `stock(DB)=98`、`stock(Redis)=98`、订单 5 条。

| 记录 | 起始状态 | 动作 | 响应 | 库存 | DB 结果 |
|---|---|---|---|---|---|
| `id=7, orderId=9999900001` | `status=0` | 重放 | `compensated=true`，`statusBefore=0 → statusAfter=1`，`retryCount=1` | 98 → **99** | `status=1`，`compensate_time=16:54:50` |
| 同上 | `status=1` | 再点一次 | `success=false`：`该死信已补偿完成（orderId=9999900001），再重放会让库存多归还一张` | **99 不变** | 不变 |
| `id=8, orderId=9999900002` | `status=2`（误判） | 重放 | `compensated=true`，`2 → 1`，`retryCount=1` | 99 → **100** | `status=1` |
| `id=9, orderId=9999900003` | `status=0`，且**手工种了** `seckill:dlq:done:9999900003` | 重放 | `compensated=false`，`0 → 1`，`retryCount=1` | **98 不变** | `status=1`（仅对齐） |

第 4 行就是 3.3 讲的那条：**doneKey 存在 → 只对齐状态、不动库存**，`compensated=false` 是给调用方的明确信号。

### 5.4 权限：401 与 403 是两道不同的门

| 请求 | 结果 | 谁拦的 |
|---|---|---|
| 不带 token `GET /seckill/ops/queues` | **401** | `LoginInterceptor`（未登录） |
| 普通用户 token（userId=2） | **403** | `AdminInterceptor`（已登录但非管理员） |
| 管理员 token（userId=1） | 200 + 数据 | — |

重放会直接改库存，所以这两道门都要有：401 保证"匿名不能点"，403 保证"用户不能点"。

## 六、踩过的坑

### 6.1 用真业务链路做实验，会被对账"收回去"

5.3 里两次成功重放把库存从 98 推到 100，41 秒后对账把它压回了 98：

```
16:55:00.058 WARN 【对账】库存已修正 | voucherId=10, redis 100 -> 98, db=98 (闸门虚高，压回账本)
```

这不是 bug，而是 04 的不变式在正常工作：**人造死信没有对应的真实预扣**，`P` 实际是 0，
所以 `Redis(100) > DB(98)` 一定是坏账。两个结论：

- 验重放要看**动作发生后立刻**的 Redis 值，别隔一分钟再看，否则会被对账"擦掉证据"；
- 反过来也说明：对账能兜住"任何人（包括运维）把库存改高"的情况——它不信任任何单方面写入。

清理要一次做全：删死信行、删 `doneKey`、删探针队列、核对 `stock`/订单数/已抢集合。
少删一个 `doneKey`，下次真出事时这条订单就再也补不上了。

### 6.2 日志的"级别"和"频率"是两个独立决定

第一版在 `NONE` 分支打了 `debug`。按 30 秒采样 × 2 条队列算，一天 5760 行——项目里 `com.hmdp: debug` 是全开的，
这些行会把真正的 SQL 日志和业务日志冲散。最终改成**正常路径不打日志**。

"任务还活着吗"这种问题不该靠日志回答——`GET /seckill/ops/queues` 更准，因为它读的是真实队列。

### 6.3 "读不到"不等于"空闲"

探针失败时如果返回 `ready=0`，对账会认为"没有在途"然后开始修库存——**这是最危险的默认值**。
所以 `Stat` 用三态：`ok=false, ready=-1, consumers=-1`，并把判断收敛成两个方法：

```java
public boolean isIdle()      { return ok && ready == 0; }              // 必须 ok 才算空闲
public boolean isAbandoned() { return ok && ready > 0 && consumers == 0; }
```

`-1` 而不是 `0` 是有意的：`0` 会被任何"顺手写下的 `== 0`"当成空闲，`-1` 不会。

### 6.4 `logs/hmdp.log` 是 GBK，不是 UTF-8

logback 落盘用的是平台默认编码（Windows 上是 GBK）。用 `Select-String -Encoding UTF8` 搜中文永远 0 条命中，
第一反应是"日志没打出来"，其实是**读错了**。两个办法：

```powershell
Get-Content 'logs\hmdp.log' | Select-String '人工重放'        # 默认编码（GBK）能命中
```

或者干脆在 `logback-spring.xml` 里固定 `<charset>UTF-8</charset>`（本项目还没加，记在这里）。

### 6.5 `Start-Process` 起的应用会被"超时命令"一起带走

用一条命令"启动 + 等 30 秒 + 看日志"，命令被工具判超时后**子进程也被杀掉**，
现象是"日志里明明 `Started HmDianPingApplication`，一分钟后再看进程没了"——很容易误判成应用自己崩了。

正确姿势：启动命令**立刻返回**（不 sleep），后面另起命令轮询端口/日志。

### 6.6 重放的锁只保护计数，不保护库存

`lock:seckill:dlq:replay:{id}`（TTL 60s + token 解锁）挡的是"连点两次 / 两个运维同时点"，
它保证 `retry_count` 不会被加两次；**库存安全仍然靠 doneKey**。

把两件事混成一把锁，就会出现"锁过期了库存被补两次"的经典事故：
锁会过期，`SETNX` 的语义（存在即已补过）不会。

## 七、局限与后续

| 局限 | 说明 | 建议 |
|---|---|---|
| **告警只到日志** | 没有钉钉/企微/Prometheus 通道，值班的人不看日志就等于没告警 | 用 `【队列告警】` 做关键字采集（Filebeat/Loki），或加一个 `WebhookNotifier` |
| **告警状态在内存** | 应用重启后计时归零，最长会晚一个确认周期；多实例部署会各自告警（同一条故障 N 份） | 状态上 Redis（`seckill:alert:state:{queue}` + TTL），或统一交给告警平台去重 |
| **探针看不到 unacked** | `queueDeclarePassive` 只给 `ready`，所以"消息正被消费者拿在手里"这段时间看起来像空闲 | 需要更准就用 management API 的 `messages_unacknowledged`；这也是对账必须"两轮确认"的根因 |
| **重放一次一条，没有批量** | 故意不做：批量重放误点一次的后果是几十张券的库存变化 | 真要批量就做"按 `voucherId` + 时间窗"的条件重放，并且写审批 |
| **没有操作人审计** | `retry_count` 只有次数，不知道"谁在什么时候点的" | 加 `tb_seckill_dlq_replay_log`（`dead_letter_id`、`operator`、`ip`、`result`、`create_time`） |
| **`status=2` 重放的语义靠人判断** | 订单被删才该回补，系统无法判断"为什么删" | 与订单删除流程联动：删单时自动生成一条待补偿死信，而不是让人去猜 |
| **死信列表无分页、无脱敏** | `limit ≤ 200`，`payload` 里可能有用户信息 | 游标分页 + 对 `payload` 做字段脱敏 |
| **采样线程被占满时无人知道** | `@EnableScheduling` 默认单线程，对账跑久了会推迟采样 | 给 `TaskScheduler` 配独立线程池；再加"采样心跳"（写 Redis 让外部监控检查） |

## 结论

| 问题 | 答案 |
|---|---|
| 自动对账已经在补，为什么还要人工重放 | 自动重试只覆盖 `status=0`、按 `create_time` 排序、每轮 200 条；`status=2` 与"点名先补"只有人能发起 |
| 重放会不会多补一张 | 不会。三道闸一道都没绕过：`status=1` 直接拒、doneKey 存在只对齐状态、DB 订单存在判为误判 |
| 为什么重放不删 doneKey | doneKey 是"库存已经 +1"的唯一证据；删了再补就是把 +1 变成 +2 |
| 为什么 `retry_count` 要 +1 | 它是唯一能区分"系统自愈"和"人介入"的字段 |
| 告警为什么是 30 秒采样 + 120 秒确认 | 采样密度决定"多久能看到"，确认窗口决定"什么时候敢报"；120 秒与 04 的"两轮确认"同源 |
| 为什么告警要单独抽 `QueueAlertJudge` | 纯逻辑才能单测时间轴；留在 `@Scheduled` 里验一次要两分钟 |
| `readable=false` 该当成有空闲吗 | 绝对不能。对账按"有在途"，告警按 `UNREADABLE`，两者都不允许它变成"可以动手" |

三课串起来一句话：
**02 保证"重复消息不重复扣"，03 保证"失败的消息不丢"，04 保证"丢了的东西能找回来"，05 保证"找回来这件事，人能做、系统能喊"。**
