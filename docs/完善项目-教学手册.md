# 任务 1 · 让 `docker compose up` 真的能跑

`P0` · 半天 · **只改一个文件**：`docker-compose.yml`；另外在 `src/main/resources/db/hmdp.sql` 加 3 行

## 目标

在一台没装 MySQL / Redis / RabbitMQ 的机器上，`git clone` 之后只执行 compose + 启动应用，`/shop/1` 返回 200。

## 现状的两个硬伤

| #   | 问题                                                                       | 后果                                                                              |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 1   | mysql 服务**完全没有** `/docker-entrypoint-initdb.d` 挂载 | 容器里 `hmdp` 是空库，应用启动后所有查询报表不存在 |
| 2   | `image: mysql:8.0`，但 `pom.xml` 的驱动是 `5.1.47`                             | 8.0 默认 `caching_sha2_password`，5.x 驱动连不上：`Unable to load authentication plugin` |

## Step 1 · 先摸清四个 SQL 脚本各自的角色

执行下面几条，把结果记在纸上（表数量、有没有 `USE` 语句）：

```bash
# 每个脚本各建几张表
grep -ci "CREATE TABLE" src/main/resources/db/hmdp.sql
grep -ci "CREATE TABLE" src/main/resources/db/upgrade_v2_coupon_member_ai.sql
grep -ci "CREATE TABLE" db/seckill_dead_letter.sql
grep -ci "CREATE TABLE" src/main/resources/db/day5_reconcile.sql

# 有没有自建库 / 切库语句（决定能不能直接丢进 init 目录）
grep -in "CREATE DATABASE\|^USE \|USE hmdp" src/main/resources/db/hmdp.sql

# 有没有 MySQL 5.7 会拒绝的零值日期
grep -c "0000-00-00" src/main/resources/db/hmdp.sql

# 宿主机 3307 有没有被占
netstat -ano | findstr "3307"
```

> **为什么先查这个**
> 容器初始化目录（`/docker-entrypoint-initdb.d`）里的 `.sql` 会按**文件名字典序**依次执行，且执行时的默认库是 `MYSQL_DATABASE` 指定的那个。所以：
> 有 `USE hmdp` 反而安全（明确切库）；若脚本里写的是 `CREATE DATABASE` 会跟容器已建的库冲突（加 `IF NOT EXISTS` 就没事）。

> **如果你在 PowerShell 里（没有 grep）**
> 先 `cd D:\heimadianping\hm-dianping`，然后用 `Select-String` 代替 `grep`：
>
> ```powershell
> (Select-String -Path src\main\resources\db\hmdp.sql -Pattern 'CREATE TABLE').Count
> Select-String -Path src\main\resources\db\hmdp.sql -Pattern 'CREATE DATABASE|USE '
> Select-String -Path src\main\resources\db\hmdp.sql -Pattern '0000-00-00'
> netstat -ano | Select-String '3307|3306'
> ```
>
> 两套命令别混用：`grep` / `ls` / `cat` 是 Git Bash 的，`Select-String` / `Get-Content` 是 PowerShell 的。

## Step 2 · 用「挂载改名」而不是「复制」，保证单一真实来源

> **这一步我一开始给的方案是错的，已更正。**
> 原方案是"复制到 `db/init/01~03.sql`，然后挂载整个目录"。问题在于：`hmdp.sql` 有 153 KB，
> 复制出去以后**改 DDL 就要改两处**，一处忘了就是"初始化脚本和源码不一致"——正是任务 5 坑位表里第 2 号翻车点。
>
> 你项目里 `docs/项目补强教程.md` 早就选了更好的做法：**挂载改名**。以它为准。

**不新建任何目录、不复制任何文件**，直接在 `docker-compose.yml` 的 mysql 服务里把三个源文件挂进容器的初始化目录，并在**容器内**改成带序号的文件名：

```yaml
volumes:
  - mysql-data:/var/lib/mysql
  - ./src/main/resources/db/hmdp.sql:/docker-entrypoint-initdb.d/01-base.sql:ro
  - ./src/main/resources/db/upgrade_v2_coupon_member_ai.sql:/docker-entrypoint-initdb.d/02-upgrade-v2.sql:ro
  - ./db/seckill_dead_letter.sql:/docker-entrypoint-initdb.d/03-dead-letter.sql:ro
```

三个要点：

| 写法 | 为什么 |
|---|---|
| 宿主机文件名保持原样，序号只出现在冒号**右边** | 单一真实来源：一份文件同时服务"手动导入"和"容器初始化"，不存在副本 |
| 目标名带 `01/02/03` 前缀 | `/docker-entrypoint-initdb.d` 按**容器内文件名**字典序执行，顺序完全由这里控制 |
| 末尾 `:ro` | 初始化脚本是只读资产，容器不该写回宿主机；也防止误操作改坏源文件 |

> ⛔ **`day5_reconcile.sql` 绝对不能挂进去**
> 它开头是 `USE hmdp;`，之后全是 `SELECT`，是**对账巡检脚本，不建表**（`CREATE TABLE` 计数为 0）。
> 挂进 `/docker-entrypoint-initdb.d` 只会往初始化日志里灌一堆查询结果，
> 而且在只建了一部分表时执行还可能报表不存在。它留在 `src/main/resources/db/` 下按需手动跑。

> **另外两个脚本已核对过都不含 `CREATE DATABASE` / `USE`**
> 所以挂进去以后依赖容器的 `MYSQL_DATABASE: hmdp` 默认库即可，不需要额外加 `USE`。

> **编号是契约**
> `02` 依赖 `01` 建好的库，`03` 又是纯增量。以后再加脚本只能往后编 `04-`，**永远不要改已有编号**——因为线上环境的初始化只跑一次，改编号等于改了别人数据库的既成事实。

## Step 3 · 处理 MySQL 5.7 的零值日期问题

本地导入时踩过：`0000-00-00` 在严格模式下会被拒绝。**实测 `src/main/resources/db/hmdp.sql` 里共有 2 处，都在第 92~93 行**：

```sql
-- hmdp.sql:92-93（tb_seckill_voucher 表）
`begin_time` timestamp NOT NULL DEFAULT '0000-00-00 00:00:00' COMMENT '生效时间',
`end_time`   timestamp NOT NULL DEFAULT '0000-00-00 00:00:00' COMMENT '失效时间',
```

严格模式下 `CREATE TABLE` 会直接报 `Invalid default value for 'begin_time'`。有三个选择，自己权衡：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A | 镜像用 `mysql:5.7`，并在 `hmdp.sql` 开头加 `SET SESSION sql_mode='';` | 与 README 声明的 5.7 一致，改动最小 |
| B | 镜像用 `mysql:8.0` + `--default-authentication-plugin=mysql_native_password` + `SET SESSION sql_mode=''` | 驱动兼容问题需自己验证，但镜像更新 |
| C | 把 `0000-00-00` 数据清洗成 `NULL` | 最干净，但要动初始数据 |

**建议 A**：面试时"版本对齐"是加分项，且本机就是 5.7，验证过等于零风险。

**加在哪**：`hmdp.sql` 第 17~18 行是 Navicat 导出的固定头，紧跟着插入即可：

```sql
SET NAMES utf8mb4;
SET FOREIGN_KEY_CHECKS = 0;

-- 本机脚本源自 MySQL 5.6 导出，含 '0000-00-00 00:00:00' 默认值（tb_seckill_voucher 的 begin_time / end_time），
-- 5.7+ 严格模式下会被 NO_ZERO_DATE 拒绝，容器初始化会失败。清空会话级 sql_mode 放行。
-- 注意用 SESSION 而不是 GLOBAL：GLOBAL 需要 SUPER 权限，且对当前会话不生效，设了也白设。
SET SESSION sql_mode = '';

-- ----------------------------
-- Table structure for tb_blog
-- ----------------------------
```

> ⚠️ **sql_mode 的坑**
> 写 `SET GLOBAL` 需要 SUPER 权限且**对当前会话不生效**；必须用 `SET SESSION sql_mode='';`，且要写在**第一个建表语句之前**。
> 这个位置错了，容器会初始化失败并陷入重启循环。

## Step 4 · 改 docker-compose.yml

只改 mysql 服务，四处：

- `image` → `mysql:5.7`（和 README 声明的版本、以及驱动 5.1.47 对齐）
- `volumes` 增加 **3 行**挂载（见 Step 2 的 yaml，注意是逐个文件挂载，不是挂目录）
- `command` 末尾补 `--default-time-zone=+08:00`
- 建议把 `healthcheck` 的 `interval` / `retries` 调宽一点（5.7 首次初始化 24 张表 + 1034 条 INSERT，比 8.0 慢）

> **为什么要 `--default-time-zone=+08:00`**
> 秒杀的时间窗判断（`beginTime` / `endTime`）对时区很敏感。容器默认 UTC 会让"活动 20:00 开始"变成 12:00 开始——
> 这个 bug 很难在日志里看出来，因为 Java 侧和 MySQL 侧各自都"正常"。

## 坑与验收

> ⚠️ **坑 1：改了 SQL 但没生效**
> `/docker-entrypoint-initdb.d` **只在数据卷为空时执行一次**。改了 `hmdp.sql` 却直接 `up -d`，MySQL 会认为"已初始化过"直接跳过。必须 `down -v`。这一条能吃掉一小时。

> ⚠️ **坑 2：容器一直重启**
> `docker compose logs mysql | grep -i error` 看第一个 ERROR。九成是 sql_mode 位置错了、或者脚本里 `USE` 了不存在的库。

> ⚠️ **坑 3：宿主机 3307 可能被占**
> 本机 MySQL 装在 **3306**（已实测占用），所以 compose 才把映射右移到 3307，**当前 3307 / 6380 / 5673 都是空闲的**。
> 但如果哪天又起了别的容器，先 `netstat -ano | Select-String '3307'` 确认，否则 compose 报 `port is already allocated`。

> **PowerShell 里没有 `wc -l`**
> Step 5 第 3 条那条管道末尾的 `| wc -l` 是 bash 写法。PowerShell 换成
> `(docker compose exec mysql mysql -uroot -proot hmdp -e "show tables;" | Measure-Object -Line).Lines`，
> 或者干脆用 `docker compose exec mysql mysql -uroot -proot -N -e "select count(*) from information_schema.tables where table_schema='hmdp';"` 直接要数字（更好，不受表头行干扰）。

# 任务 2 · 秒杀入口的券元数据缓存

`P0-3` · 半天 · 改动：`utils/RedisConstants.java`、`service/ISeckillVoucherService.java`、`service/impl/SeckillVoucherServiceImpl.java`、`service/impl/VoucherOrderServiceImpl.java:65`

## 目标

消灭秒杀入口每一次请求的 `SELECT ... FROM tb_seckill_voucher`。改完之后，即使 500 并发，这张表的 QPS 应该接近 0。

## 为什么这一处最值钱

现在的秒杀链路自认为是"Redis 挡住 99% 流量"，但入口第一行就是：

```java
// VoucherOrderServiceImpl.java:65
SeckillVoucher sv = seckillVoucherService.getById(voucherId);   // ← 每个请求打一次 MySQL
```

被 Lua 拒绝的请求（售罄、重复）**都已经先打了一次数据库**。面试官读到这一行，"Redis 削峰"的可信度直接打折。
修掉它，你就能讲一句非常漂亮的话：**"这个问题是我自己读代码发现的，压测数据也印证了。"**

## Step 1 · 想清楚缓存什么、不缓存什么

| 字段 | 要不要缓存 | 理由 |
|---|---|---|
| `beginTime` / `endTime` | 要 | 几乎不变，正是入口判断要用的两个字段 |
| `voucherId` | 要（作为存在性凭据） | 用来判断"券是否存在"，避免缓存穿透 |
| `stock` | **不要** | 真正扣减在 Redis 的 `seckill:stock:` 里，DB 的 stock 是滞后副本。缓存它只会让你在排查时看到两个不同的数字 |
| `createTime` / `updateTime` | 不要 | 零业务价值，白占内存 |

> **这是一个能直接讲给面试官的取舍**
> "我只缓存时间窗，不缓存库存——因为库存的唯一真相在 Redis 的预扣 key 里，DB 的 stock 是消费端落库后的结果。把两个数字都放进缓存，等于给自己制造一个'到底哪个对'的问题。"

## Step 2 · 加常量

在 `RedisConstants` 里，跟着 `SECKILL_STOCK_KEY` 那一段加两个：

```java
// 秒杀券元数据（时间窗）缓存前缀，完整 key = seckill:meta:{voucherId}
public static final String SECKILL_META_KEY = "seckill:meta:";
// 30 分钟。选这个值的理由要能说出口，见 Step 5 的一致性讨论
public static final Long SECKILL_META_TTL = 30L;
```

## Step 3 · 在 `ISeckillVoucherService` 加一个方法

方法签名先想清楚三件事：返回值类型、找不到时返回什么、要不要暴露"是否来自缓存"。

```java
/**
 * 查券元数据（时间窗），走 Redis 缓存。
 *
 * @return 券存在则返回（只保证 voucherId / beginTime / endTime 有值）；不存在返回 null
 */
SeckillVoucher queryMetaById(Long voucherId);
```

> ⚠️ **不要返回 Result**
> Service 层返回 `Result` 是课程带进来的坏习惯——Controller 才该决定 HTTP 语义。后面任务 3 要加错误码，这一层如果继续返回 `Result`，错误码会散落在各个 Service 里。

## Step 4 · 实现（骨架，逻辑自己补）

```java
// SeckillVoucherServiceImpl
@Override
public SeckillVoucher queryMetaById(Long voucherId) {
    // 1. 空参保护：voucherId 为 null 直接返回 null，别让 Redis 拼出 "seckill:meta:null" 这种脏 key

    // 2. 查 Redis。用 Hash 而不是 String(JSON)——
    //    理由：字段少（3 个），Hash 可以只取需要的字段，而且下一步想下推到 Lua 时能直接 HGET
    //    key = SECKILL_META_KEY + voucherId

    // 3. 命中判断要想清楚"空值缓存"：
    //    如果查不到就每次都回源 DB，缓存穿透的口子就又开了。
    //    两种做法选一种：(a) 缓存一个空标记 (b) 直接把"券不存在"当作高频错误，前置到建券时就预热

    // 4. 未命中 → 查 DB（这里才允许出现 getById）
    //    DB 也没有 → 返回 null
    //    DB 有 → 写 Hash（3 个字段）+ 设置 TTL → 返回

    // 5. 拼装返回值。注意 new SeckillVoucher().setVoucherId(...).setBeginTime(...)
    //    实体有 @Accessors(chain = true)，可以链式 set
}
```

## Step 5 · 想清楚一致性与编译期风险（这段是面试素材）

> **三个必须能答的问题**
>
> 1. **30 分钟 TTL，改券时间窗会延迟多久生效？** 最坏 30 分钟。秒杀券的时间窗基本只在创建时确定、活动前不修改，**业务上可接受**。如果确实要实时，就在建券/改券的 Service 里主动 `delete` 这个 key（Cache Aside）。
> 2. **为什么不干脆把时间窗下推到 Lua？** 可以，而且更彻底（零网络往返）。但那要改 `seckill.lua` 的返回值语义（新增 3=未开始、4=已结束），Java 侧所有判断分支都要跟着改，**改错就是超卖或全量误判**。分两步走：先加缓存（低风险），验证没问题再考虑下推。
> 3. **券不存在时怎么办？** 返回 null，Controller 直接给"秒杀券不存在"，**不进 Lua**——否则会在 Redis 里给非法券建库存 key。

## Step 6 · 改调用点

`VoucherOrderServiceImpl.java:65` 那一行换成新方法即可，后面 `sv.getBeginTime()` / `getEndTime()` 的判断**一行都不用动**——这是"保持方法契约一致"的回报。

## Step 7 · 预热（可选但建议做）

找建券接口（`VoucherController` 或 `SeckillOpsController` 里创建秒杀券的那个方法），在**库存预热到 Redis 的那段代码旁边**，顺手把 meta 也写一次。
好处：第一个用户来的请求就不用等那一次 DB 回源。

## 坑与验收

> ⚠️ **坑 1：Hash 的字段名与实体字段名不一致**
> `HGETALL` 返回的 field 是字符串。如果写 `begin_time` 却按 `beginTime` 取，会静默拿到 null，然后时间窗判断被跳过 → **活动没开始也能抢**。写完一定要 `HGETALL` 亲眼看一下。

> ⚠️ **坑 2：LocalDateTime 的序列化**
> 券体系用的是 `JSONUtil` + `RedisData` 那套。如果这次改成 Hash，时间字段建议存**秒级时间戳字符串**（如 `1735689600`），读出来 `Instant.ofEpochSecond(...)` 转 `LocalDateTime`。存 ISO 字符串也能用，但跨时区/跨 JVM 默认时区时会出问题。

> ⚠️ **坑 3：忘了删旧 key**
> 改完代码后 Redis 里可能残留上一版的 `seckill:meta:*`（如果字段格式变了），调试前先 `DEL` 一次。

### ✅ 验收标准

- [ ] `redis-cli -a 123321 HGETALL seckill:meta:{voucherId}` 三个字段齐全，`TTL` 接近 1800
- [ ] 连续请求秒杀接口 5 次，`logs/hmdp.log` 里**只出现 1 次** `SELECT`（因为 mybatis 配了 Slf4jImpl，debug 级会打 SQL）
- [ ] 不存在的 `voucherId`：返回"秒杀券不存在"，且 Redis 里没有生成 `seckill:stock:` 键
- [ ] 活动未开始 / 已结束的券：判断依然正确（改系统时间或用一张 `begin_time` 在未来的券验证）

**提交**：`perf(seckill): 券元数据走 Redis Hash 缓存，消除秒杀入口的 DB 查询`

# 任务 3 · 统一错误码与参数校验

`P0-4` · 半天 · 改动：新建 `dto/ErrorCode.java`、`dto/Result.java`、`exception/BizException.java`、`config/BizExceptionAdvice.java`、以及 3 个 Controller 入口

## 目标

前端不再靠中文文案判断错误类型；传非法参数返回 `code=4100` 而不是 500；运维能按 `code like '5%'` 筛出真实故障。

## Step 1 · 先设计分段规则，再写枚举

别一上来就罗列错误码，先定规则——这是面试时真正会被问的部分：

| 段位 | 含义 | 谁该处理 |
|---|---|---|
| `0` | 成功 | — |
| `4xxx` | 调用方问题（改参数 / 改状态就能成功） | 前端弹提示 |
| `41xx` | 4xxx 下的"通用入参 / 鉴权"子域 | 前端 |
| `42xx` | 4xxx 下的"秒杀"子域 | 前端 |
| `5xxx` | 服务端故障 | **必须告警** |

按这个规则，最小集合大概是：成功、通用业务失败、参数不合法、未登录、秒杀券不存在、未开始、已结束、库存不足、重复下单、内部错误。
**枚举值自己填**，注意每个都要有 `code` + `msg` 两个字段和一个构造器。

## Step 2 · 给 Result 加 code（注意这会引发编译错误）

> ⚠️ **先做这一步的心理准备**
> `Result` 用了 `@AllArgsConstructor`。加一个 `Integer code` 字段后：
> - 构造器签名从 4 个参数变 5 个 → **所有 `new Result(...)` 的地方编译失败**（先 `grep -rn "new Result(" src/` 看看有多少处）
> - Lombok 生成的 `getCode` / `setCode` 会与手写方法重名冲突（如果写了的话）
>
> 正确姿势：字段加在最前面，**先编译一次看报错清单**，再逐个修。不要凭想象改。

静态工厂要同步改，并且**保留老方法的签名**：

```java
// 老的调用方（16 个 Controller）不想全改，就给一个"归口"重载
public static Result fail(String errorMsg) {
    // 内部映射到 BIZ_GENERAL，返回 false + 该 code + 原文案
}

// 新代码用这个
public static Result fail(ErrorCode ec) { ... }
public static Result fail(ErrorCode ec, Object data) { ... }   // 例如参数校验要带回字段名
```

## Step 3 · BizException 带上 errorCode

```java
// 加一个字段，保留老构造器（默认 BIZ_GENERAL）——否则全项目的 throw new BizException("...") 全炸
private final ErrorCode errorCode;

public BizException(String message) { ... }                     // 老代码走这里
public BizException(ErrorCode errorCode) { ... }                // 新代码走这里
public BizException(ErrorCode errorCode, String message) { ... }
```

## Step 4 · 在两个 Advice 里补校验异常处理

> ⚠️ **先搞清楚你已有的分工，别新建第三个 Advice**
> 已经有 `BizExceptionAdvice`（业务，warn 级日志）和 `WebExceptionAdvice`（兜底，error 级 + 返回"服务器异常"）。
> 校验异常属于"调用方问题"，**应该进 BizExceptionAdvice**，这样不会被当成服务端故障记 error 日志。

要加三种 handler，它们的触发场景不同，这是个高频面试点：

| 异常 | 什么时候抛 |
|---|---|
| `MethodArgumentNotValidException` | `@RequestBody` + `@Valid` 校验失败 |
| `BindException` | 表单 / `@ModelAttribute` 绑定校验失败 |
| `ConstraintViolationException` | 方法参数上的 `@NotNull` 等（需要类上加 `@Validated`） |

handler 里要能提取出**哪个字段**错了：`ex.getBindingResult().getFieldErrors()` → 取第一个 → 拼成 `"字段名: 提示"`。

## Step 5 · 给三个入口加校验

挑真正有价值的加，不要全项目铺：

- **创建券模板**（`CouponController` 已有 `@Valid`，去看实体上的注解是否真的写了 `@NotNull`——**光有 `@Valid` 而实体没注解等于没校验**）
- **秒杀下单**：`voucherId` 加 `@NotNull` + `@Min(1)`
- **死信重放**：`id` 加 `@NotNull` + `@Min(1)`

## Step 6 · 一个必须现在就决定的问题：HTTP 状态码要不要跟着变

> **两种流派，选一个并想清楚理由**
> - **永远 200 + body 里带 code**：前端统一拦截器处理，简单。但监控/网关按 5xx 告警就失效了。
> - **4xxx 映射 400/401，5xxx 映射 500**：语义正确，能接 Prometheus 的 5xx 指标。**推荐这个**，因为任务 6 要接 Actuator。
>
> 做法：`@ExceptionHandler` 方法的返回值如果是 `Result`，状态码默认 200。要改状态码得给方法加 `@ResponseStatus`，或者让方法返回 `ResponseEntity<Result>`。
> 注意 `LoginInterceptor` 里已经 `setStatus(401)` 了，别让两处逻辑打架。

## 坑与验收

> ⚠️ **坑：Lombok 的 `@AllArgsConstructor` 是隐形地雷**
> `Result` 一旦加字段，如果哪里用了全参构造器，参数顺序静默错位也不会报错（类型相同时）。第一个改完先跑一次全量编译，把错误清单贴在旁边改。

### ✅ 验收标准

- [ ] `POST /voucher-order/seckill/0` → `{"code":4201,...,"success":false}`，HTTP 400/404 之一（不是 500）
- [ ] 建券传空 `name` → `{"code":4100,"errorMsg":"name: 不能为空"}`
- [ ] 未登录访问 `/user/me` → `401` + `code=4101`（不是空 body）
- [ ] 故意抛一个 NPE → 仍然返回 `code=5000`，且 `logs/hmdp.log` 里是 ERROR 级（说明两个 Advice 分工没乱）
- [ ] `grep -rn "Result.fail(\"" src/main/java` 还有能编译通过的老调用（证明兼容层有效）

## Step 1 · 先看现有测试是怎么写的，找出缺口

已有的 5 个测试里，`QueueAlertJudgeTest`、`CouponCalcTest`、`RedisIdWorkerTest` 测的都是**纯函数**（没有外部依赖），所以**没有任何一个示范了 Mockito 的用法**。
这一步要自己建立这个模式——它比写业务代码更值得花时间，因为后面所有测试都复用它。

## Step 2 · 建立第一个 Mockito 测试骨架

```java
// 关键三件套：不启动 Spring 容器、只 mock 依赖、只测这一个类
@ExtendWith(MockitoExtension.class)          // JUnit5 的写法，别用 @RunWith
class SeckillDeadLetterServiceTest {

    @Mock  private XxxMapper xxxMapper;      // 有多少个依赖就 mock 多少个
    @Mock  private StringRedisTemplate stringRedisTemplate;
    @InjectMocks private SeckillDeadLetterServiceImpl service;   // 自动把上面 mock 注进去
}
```

> ⚠️ **不要用 `@SpringBootTest`**
> 它要起完整容器 → 要连 MySQL / Redis / RabbitMQ。慢（十几秒/类）、脆（环境没起就全红），而且测出来的是 Spring 配置对不对，不是你的逻辑对不对。单测的意义就是**脱离环境**。

## Step 3 · 处理链式调用的 mock（这一步最容易卡住）

代码里有大量这种写法：

```java
stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
```

直接 `when(stringRedisTemplate.opsForValue().setIfAbsent(...))` 会在准备阶段就 NPE（因为 `opsForValue()` 返回 null）。正确姿势是**两层 mock**：

```java
@Mock private StringRedisTemplate stringRedisTemplate;
@Mock private ValueOperations<String, String> valueOps;

// 在每个用例里（或 @BeforeEach）先打通第一层
when(stringRedisTemplate.opsForValue()).thenReturn(valueOps);
// 然后才能 stub 第二层
when(valueOps.setIfAbsent(anyString(), anyString(), anyLong(), any())).thenReturn(true);
```

> **顺手能学到一个知识点**
> 如果这个 `stringRedisTemplate` 的 mock 在某个用例里**根本用不到**，Mockito 的严格模式会报 `UnnecessaryStubbingException`。
> 这不是 bug，是它在提醒你"你的测试声明了不该走的分支"。解决：把 stub 移到具体用例里，或在该方法上用 `lenient()`。

## Step 4 · 逐个设计 `replay()` 的用例

先读 `SeckillDeadLetterServiceImpl` 第 214 行开始的 `replay`，把它的 if 分支列出来，然后一一对应：

| 用例 | 构造条件 | 断言什么 |
|---|---|---|
| id 为 null | 直接传 null | 抛 `BizException`，且**没有任何一次 Redis / DB 写操作**（用 `verifyNoInteractions`） |
| 记录不存在 | 抢锁成功 + `selectById` 返回 null | 抛 `BizException`；**锁必须被释放**（`verify(delete)`） |
| 已补偿 | record 的 status = 已补偿 | 抛 `BizException`；**绝不能**再调一次 `compensateAndMark` |
| 抢锁失败 | `setIfAbsent` 返回 false | 抛"正在重放中"；同样不做任何写操作 |
| 正常重放 | 锁成功 + 记录是待补偿 + 补偿返回 true | 返回值里"本次是否真的动了库存" = true；`retry_count` 被 +1 |

> **最有价值的一条断言是"锁必须释放"**
> 原来的代码如果某条异常分支提前 return 忘了 `finally` 释放锁，**只有这个断言能发现**。
> 写完这条测试，回头看 `replay` 的 try/finally 结构，很可能真的有收获。

## Step 5 · 设计 `seckillVoucher()` 的用例

| 用例 | 构造 | 断言 |
|---|---|---|
| 未登录 | `UserHolder` 为空 | 返回 fail("请先登录")；**没碰 Redis** |
| 库存不足 | mock `stringRedisTemplate.execute(...)` 返回 1L | 返回 fail；**没有生成 orderId、没有投递 MQ** |
| 重复下单 | execute 返回 2L | 同上 |
| 投递失败回滚 | execute 返回 0L（成功预扣）+ `convertAndSend` 抛异常 | 返回"系统繁忙"；**Redis 里库存被 +1、用户记录被移除**（verify `increment` 和 `remove`） |

> ⚠️ **两个技术难点提前告诉你**
> - `UserHolder` 是静态 ThreadLocal，测试里要手动 `UserHolder.saveUser(...)`，**并且用 `@AfterEach` 调 `removeUser()`**，否则用例之间互相污染，A 用例能过 B 用例莫名失败。
> - `stringRedisTemplate.execute(script, keys, args...)` 是**可变参数泛型方法**，Mockito 匹配时要用 `any()` / `anyList()` 组合，很容易出现"看起来 stub 了但进了默认返回 null"。排查手段：先让 mock 直接 `thenReturn(0L)`，确认能走进成功分支，再加参数匹配。

## 坑与验收

> ⚠️ **坑：`@InjectMocks` 注不进去**
> 如果被测类用的是**构造器注入**，`@InjectMocks` 能自动选最大构造器，没问题。
> 但如果它还注入了你没想到的依赖（比如 `RedisIdWorker`、`SeckillVoucherMapper`），那些会是 null，运行时才 NPE。
> **先把被测类的字段列表抄下来，逐个 `@Mock`**，比事后猜快得多。

- [ ] `mvn -o test` 全绿，用例总数 ≥ 35
- [ ] 两个新测试类的用例数分别是 5 和 4（含边界），每个 `@Test` 方法名能读出"测什么、期望什么"
- [ ] 故意把 `replay` 里某一处 `finally` 删掉 → 对应的测试应该**变红**。这就是测试有效的证明
- [ ] 单个测试类执行时间 < 2 秒（证明没起 Spring 容器）

# 任务 5 · 压测与数据

`P0-2` · 一天 · 产出：`test/jmeter/seckill.jmx`、`docs/压测报告.md` · 前置条件：**任务 2 必须已完成**

## 目标

拿到能支撑主线稿那三句话的真实数字。**没有这组数据，6.1 那段"500 并发、DB 个位数 QPS"就是空口无凭。**

## Step 1 · 先解决"一人一单"这个致命前提

> ⛔ **这是最容易让整场压测作废的点**
> Lua 里有"一人一单"。如果 500 个并发线程共用同一个 token，**会有 499 个请求被"每人限抢一张"挡掉**——你压出来的不是秒杀性能，而是"重复请求的拒绝速度"，所有数据都不可信。
>
> 正确做法分两步：
> 1. 写一个小脚本/测法：批量注册或直接用库里的 1005 个用户，逐个调 `/user/login` 拿 token，写成 CSV（`token`, `userId`）
> 2. JMeter 用 **CSV Data Set Config** 读取，且要开 **Recycle on EOF** 并关闭 **Stop thread on EOF**

## Step 2 · 设计三组对照（每组只改一个变量）

| 组 | 变量 | 想证明什么 |
|---|---|---|
| A | 入口改成"直接查 DB 扣减"（用配置开关，见 Step 3） | Redis 到底挡掉了多少流量。这是最有价值的一条数据 |
| B | `prefetch=1/concurrency=2` ↔ `prefetch=50/concurrency=4` | MQ 参数对吞吐的影响——02 课踩过这个坑，正好用数据复现 |
| C | 并发 500 / 1000 / 2000，库存固定 100 | 拐点在哪、拐点之后是快速失败还是超时堆积 |

## Step 3 · A 组怎么加开关而不污染主分支

三种做法，按能接受的复杂度选：

- **配置开关**（推荐）：`application.yaml` 加 `seckill.naive: false`，在 `seckillVoucher` 开头加一个 `if` 分支走"直接 DB 扣减"。压完把这个分支删掉，或保留并标注"仅用于压测对照"。
- **独立 Controller**：新建 `NaiveSeckillController`，路径 `/naive/seckill`，只用于压测。
- **单独分支**：最干净，但只有一天时间，来回切分支容易乱。

关键纪律：**压测代码不能留在主链路上**。面试官看到 `if (naive)` 会问"这段为什么在生产代码里"，你要能答"这是压测对照开关，默认关闭，报告里有它的用途说明"。

## Step 4 · 压测前重置，压测后核对不变式

每组压测**前后**都要执行这套（否则上一组污染下一组）：

```sql
-- 重置：库存回 100，清空订单与死信
UPDATE tb_seckill_voucher SET stock = 100 WHERE voucher_id = ?;
DELETE FROM tb_voucher_order WHERE voucher_id = ?;
DELETE FROM tb_seckill_dead_letter WHERE voucher_id = ?;
```

```bash
# Redis 侧
redis-cli -a 123321 SET seckill:stock:{id} 100
redis-cli -a 123321 DEL seckill:user:{id}

# 核对（压测结束后跑）
redis-cli -a 123321 GET seckill:stock:{id}        # A: Redis 剩余库存
```

```sql
SELECT stock FROM tb_seckill_voucher WHERE voucher_id = ?;      -- B: DB 剩余库存
SELECT COUNT(*) FROM tb_voucher_order WHERE voucher_id = ?;     -- C: 已落库订单
SELECT COUNT(*) FROM tb_seckill_dead_letter WHERE status = 0;   -- D: 待补偿死信
```

> **把项目里的不变式写成一句话**
> `Redis 剩余库存 = DB 剩余库存 − 待补偿死信数`
>
> 这一条能同时验证三件事：没有超卖、没有少卖、死信账目对得上。
> 建议把上面几行存成 `db/check_invariant.sql`（Redis 部分用注释写命令），README 里放一句"一条命令验证一致性"——这就是路线图里说的"不变式要有可执行的检查"。

## Step 5 · JMeter 必须用非 GUI 模式

```bash
# GUI 只用来调脚本和看结构，真正压测用命令行的非 GUI 模式
jmeter -n -t test/jmeter/seckill.jmx -l result.jtl -e -o report/
# -n 非GUI  -t 脚本  -l 原始结果  -e -o 生成 HTML 报告
```

> ⚠️ **为什么必须非 GUI**
> GUI 模式下 JMeter 自己的界面渲染会吃掉大量 CPU，在 Windows 单机上压到几百并发时，**瓶颈会先出现在压测机自己身上**，你测的是 JMeter 的性能。

## Step 6 · 写报告，结论只写三句

报告结构固定，缺任何一项这组数据就不可信：

1. **环境口径**：CPU 核数 / 内存 / 单机单实例 / 操作系统 / JDK 版本
2. **工具参数**：JMeter 线程数、Ramp-up、循环次数、是否复用连接
3. **初始状态**：Redis 库存初值、DB 库存初值、订单表行数、死信表行数
4. **结果表**：QPS / P95 / P99 / 错误率 / 超卖数 / 少卖数 / 死信数
5. **结论三句**：只写能被数据指到的判断，不写"性能优秀"这种形容词

## 坑与验收

> ⛔ **坑 1：数据自相矛盾**
> 典型翻车：报"超卖 0"但订单数明明超过库存；报"DB 个位数 QPS"但没排除 Nginx 缓存。
> **每个结论都要能指到某一节数据**，指不到就删掉那句话。

> ⚠️ **坑 2：`correlationData.getFuture().get(1, SECONDS)` 会成倍拖慢吞吐**
> 它占着 Tomcat 线程等 broker 确认。压测时会看到 QPS 上不去且 RT 很稳定地卡在 1 秒附近——**这不是 Redis 慢，是这里有同步等待**。
> 被问到就答"单机吞吐 ≈ worker 数 / RT，生产替代方案是异步 confirm + 本地消息表 + 定时补偿，我这套死信+对账正是补偿面的雏形"。

> ⚠️ **坑 3：跑完不清理，第二组数据全废**
> 尤其是连接池和 Tomcat 线程池的预热状态。建议每组之间重启一次应用，并在报告里注明。

# 任务 6 · 可观测性与包装（收尾）

`P2` · 一天 · 改动：`pom.xml`、`application.yaml`、`config/MvcConfig.java`、新建 Filter、`README.md`

## ① Actuator 健康检查（1 小时，最优先）

加两个依赖：`spring-boot-starter-actuator` + `micrometer-registry-prometheus`（Boot 2.3 对应 micrometer 1.x）。

`application.yaml` 里把端点暴露出来：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus
```

> ⛔ **这一步 100% 会遇到的问题**
> `MvcConfig` 里 `RefreshTokenInterceptor` 拦的是 `/**`，`LoginInterceptor` 也覆盖了 `/actuator/**`。
> 于是你访问 `/actuator/health` 会拿到 **401**，然后误以为 Actuator 没生效。
>
> 修法：把 `/actuator/**` 加进 `LoginInterceptor` 的 `excludePathPatterns`。
> **这就是"加依赖五分钟、接进拦截器一小时"的真实原因，面试时讲这个小坑比讲"我加了 Actuator"有价值得多。**

## ② traceId 串起全链路（1 小时）

写一个 `OncePerRequestFilter`：

- 从请求头取 `X-Trace-Id`，没有就生成一个（UUID 去掉横杠）
- 塞进 `MDC.put("traceId", ...)`
- **`finally` 里 `MDC.clear()`**——不清会污染线程池里的下一个请求（和 ThreadLocal 同一个坑）
- logback 的 pattern 里加 `%X{traceId}`

> **最难的一环是跨 MQ**
> HTTP 链路的 traceId 传不到消费者线程。要在投递时用 `MessagePostProcessor` 把它写进消息 header，消费端再从 `Message.getMessageProperties().getHeaders()` 里取出来重新 `MDC.put`。
> 这块做完，你就能讲"一条秒杀日志能按 traceId 串起 生产→消费→死信 三段"——这是真正的工程能力信号。

## ③ 加固 AdminInterceptor（半小时，建议做）

现状是硬编码：

```java
// utils/AdminConst.java
public static final Long ADMIN_ID = 1L;    // ← 认 ID 不认身份
```

问题：**任何能把自己变成 userId=1 的路径都能调运维接口**，而 `/seckill/ops/**` 里有死信重放——写库存的操作。

两种改法，按时间选：

| 方案 | 做法 | 能讲的话术 |
|---|---|---|
| 轻量 | 管理端单独一套 token：单独的登录接口 + 单独的 Redis key 前缀 + `AdminInterceptor` 校验这个 token | "管理端和用户端鉴权链路完全隔离，运维接口不依赖用户登录态" |
| 完整 | 加 `role` 字段或角色表，拦截器校验角色 | "RBAC 的最小实现，生产会接统一权限中心" |
| 不改 | 但必须能答：直接承认"这是 demo 简化，userId 白名单，生产走 RBAC" | **承认取舍永远比硬撑好** |
