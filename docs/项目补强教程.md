# 第 0 章 · 先给你的项目画一张地图

## 0.1 一次秒杀请求，在你项目里走了 9 步

这是全项目最值钱的一条链路。下面每一步都标了**真实类 + 方法 + 行号**，你可以逐个点开对照。

| 步   | 发生了什么                                              | 代码位置                                                         | 关键技术                    |
| --- | -------------------------------------------------- | ------------------------------------------------------------ | ----------------------- |
| 1   | 请求带 `authorization` 头进来                            | `RefreshTokenInterceptor`（order=0）                           | 双拦截器                    |
| 2   | 从 Redis 取 `login:token:{token}`，把用户放进 `UserHolder` | 同上                                                           | Redis 存会话 + ThreadLocal |
| 3   | 需要登录的接口才校验，未登录直接 HTTP 401                          | `LoginInterceptor`（order=1）                                  | 拦截器分层                   |
| 4   | 查券信息（**每个请求都打一次 MySQL**）                           | `VoucherOrderServiceImpl:65`                                 | ⚠️ 待优化点                 |
| 5   | 校验时间窗（未开始/已结束）                                     | 同上 `:70-75`                                                  | 业务校验                    |
| 6   | 执行 Lua：判断库存 → 判断一人一单 → 扣库存 → 记用户                   | `resources/seckill.lua`                                      | **原子性**                 |
| 7   | 生成全局订单号                                            | `RedisIdWorker.nextId("voucher-order")`                      | 分布式 ID                  |
| 8   | 投 MQ 并**同步等 broker 确认**，失败就回滚 Redis                | `:98-114`                                                    | 生产端可靠性                  |
| 9   | 消费者异步落库：幂等门禁 → CAS 扣 DB 库存 → 插订单                   | `VoucherOrderConsumer`                                       | 消费端幂等                   |
| 10  | 失败 → 本地重试 3 次 → 还失败 → 进死信队列 → 落库对账 → 人工重放          | `SeckillDeadLetterConsumer` / `SeckillDeadLetterServiceImpl` | 补偿闭环                    |

**顺序上的两个关键设计**（面试必问，先记结论）：

- 「扣 Redis 库存」在「发消息」**之前** → 因为 Redis 快、能扛住 99% 的无效流量，
  让 MySQL 只看见"真正抢到了的人"。这叫**流量削峰**。
- 「扣 DB 库存」在「插订单」**之前**，且带 `stock > 0` 条件 → 即使 Redis 全崩了，
  MySQL 也不会卖超。这叫**最终兜底**。

## 0.2 三条主线，别把项目看成 14 个 Controller 的堆叠

新手最容易犯的错：按包结构（controller/service/mapper）去理解项目，结果一个都讲不清。
正确的切法是**按问题域切成三条线**：

```
主线 A：读多写少的流量        主线 B：秒杀的一致性           主线 C：钱和券的正确性
-------------------          -------------------          -------------------
商铺/分类缓存                  Lua 预扣                    优惠券计算(满减/折扣/叠加)
缓存穿透/击穿/雪崩             MQ 异步落库                  会员券幂等发放
双拦截器 + token 续期          消费幂等 + 死信 + 对账        成长值幂等(+1 只能一次)
Feed 流滚动分页                队列水位告警                  临期券 ZSet 扫描
```

**为什么这样切**：每一条线都能独立回答"最难的地方是什么"，而按包结构讲，你只会念目录。
面试时你说"我这个项目有三条线，我先讲一致性这条"——开场就赢一半。

## 0.3 第一个练习：用 3 条命令验证你的地图对不对

```powershell
cd D:\heimadianping\hm-dianping

# ① 秒杀相关的类一共几个？（地图 A 的落点）
Get-ChildItem -Recurse src\main\java -Filter *.java | Select-String -Pattern 'seckill|Seckill' -List | ForEach-Object { $_.Filename }

# ② Lua 脚本里到底有几次 Redis 调用？（原子性的证据）
Get-Content src\main\resources\seckill.lua -Encoding UTF8

# ③ 死信相关的类/表/配置分别是哪些？（补偿闭环的证据）
Get-ChildItem -Recurse src\main -Include '*DeadLetter*','*dlq*' | ForEach-Object { $_.Name }
Select-String -Path src\main\resources\application.yaml -Pattern 'dead-letter|deadLetter|queues'
```

**做完这一步你应该能回答**：Lua 里 4 次 Redis 调用（GET / SISMEMBER / DECR / SADD），
返回值 0/1/2 分别代表什么，以及为什么这 4 次调用必须写在**同一个脚本**里。

> 💡 **专业名词：原子性（Atomicity）**
> 人话：一件事要么全做完，要么一点没做，中间不会被人插队。
> 你项目里：`seckill.lua` 的那 4 次调用如果拆成 4 次 Java 调用，那么在 DECR 和 SADD 之间
> 就会有别的请求插进来 → 同一个人可能抢到 2 张（**超卖**）。
> 放进 Lua 后，Redis 保证整个脚本执行期间不处理别的命令（Redis 单线程 + 脚本是原子的）。
> 面试话术：「我把'查库存、判重、扣减、记人'四步塞进一个 Lua 脚本，利用 Redis 单线程执行脚本
> 的原子性，把并发窗口压到零——这不是加锁，是让竞争条件根本不存在。」

# 第 1 章 · 术语地图（这些词你得能一句话解释）

面试官不会问"什么是幂等"这种教材题，他会问"你这条链路重复消费了怎么办"。
所以下面每个词都写成三段：**人话 → 你项目里的位置 → 被问到怎么答**。

## 1.1 一页速查表

| 术语 | 一句话人话 |
|---|---|
| 原子性 | 多步操作当成一步做，中间不被打断 |
| 竞态条件（Race Condition） | 两个线程按不可预测的顺序读写同一份数据，结果看运气 |
| 超卖 | 库存只有 100，却卖出 101 单 |
| 幂等（Idempotency） | 同一个操作做 1 次和做 N 次，结果一样 |
| CAS（Compare-And-Swap） | "库存还大于 0 才扣"，靠条件更新代替加锁 |
| 乐观锁 / 悲观锁 | 乐观锁先干、冲突了再说；悲观锁先锁住、谁也别动 |
| 分布式锁 | 多台机器之间也能互斥的锁（你项目里用 Redis `SETNX + TTL`） |
| TTL | Time To Live，键的存活时间，到点自动删 |
| 缓存穿透 / 击穿 / 雪崩 | 查不存在的数据 / 热点 key 突然失效 / 大批 key 同时失效 |
| 空值缓存 | 查不到也往缓存写个空串，挡住反复打库 |
| 逻辑过期 | 缓存不设 TTL，值里存"过期时间戳"，过期后异步重建 |
| 互斥锁重建 | 缓存失效时只让一个线程去查库，其他线程等 |
| MQ / 生产者 / 消费者 | 消息队列 / 发消息的 / 收消息的 |
| ACK | 消费者告诉 broker"我处理完了，可以删这条消息" |
| prefetch | 每个消费者最多同时拿几条未确认消息 |
| requeue | 处理失败后把消息塞回队列重来 |
| 死信队列（DLQ） | 重试耗尽的"尸体收容所"，等人处理 |
| 补偿（Compensation） | 已经做的操作反向撤销/补齐，让数据回到一致 |
| 对账（Reconciliation） | 定期比对多方数据，找出不一致并修 |
| 削峰填谷 | 把瞬时洪峰挡在快存储前，让慢存储平稳消费 |
| 最终一致性 | 中途可能不一致，但**保证最后一致** |
| QPS / TPS / RT / P99 | 每秒请求数 / 每秒事务数 / 响应时间 / 99% 的请求快于这个值 |
| traceId / MDC | 一次请求的全局编号 / 日志框架里"随线程走"的上下文容器 |
| 健康检查（healthcheck） | 容器/网关定时探活，判断这个实例能不能接流量 |

## 1.2 深潜 ①：幂等 —— 你项目里出现过 3 次，写法完全不同

这是面试最爱追的词，而你的项目恰好有 3 种层次，讲出来很有层次感：

| 位置 | 手段 | 挡的是什么 |
|---|---|---|
| `seckill.lua` 的 `SISMEMBER` | Redis Set 判重 | 同一用户并发点击，第 2 次直接被拒 |
| `VoucherOrderConsumer:43` `selectById(orderId)` | **前置门禁**（先查订单是否存在） | 消息被重复投递（ack 丢失、broker 重投） |
| `VoucherOrderConsumer:70` `catch (DataIntegrityViolationException)` | **数据库唯一约束兜底** | 两条重复消息同时穿过门禁（RR 隔离级别下互相看不见对方的 insert） |

**为什么必须两层**：前置门禁是"检查后执行"（check-then-act），天生有窗口 —— 两个消费者
同时 `selectById` 都返回 null，然后都去插。这时候只有**唯一索引**是数据库层面的真锁。
你代码注释里写得很准："RR 隔离级别互相看不见对方的 insert"。

> 面试话术：「幂等我有两层。第一层是消费前查订单号，挡掉绝大多数重复投递；
> 第二层是订单表主键唯一约束兜住并发窗口 —— 因为 check-then-act 一定有窗口，光靠查询
> 不可能绝对，必须让数据库来当最后一道锁。冲突后我把本次多扣的 1 张补回去，
> 但**绝不动 Redis**，否则会把已成功的用户重新解锁，凭空多卖一张。」

## 1.3 深潜 ②：CAS 与"乐观锁" —— 你项目里那行 `gt("stock", 0)`

```java
// VoucherOrderConsumer:49
seckillVoucherService.update(new UpdateWrapper<SeckillVoucher>()
        .setSql("stock = stock - 1")
        .eq("voucher_id", voucherId)
        .gt("stock", 0));     // ← 这一行就是乐观锁
```

翻译成的 SQL 是：

```sql
UPDATE tb_seckill_voucher SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0;
```

**为什么这比 `if (stock > 0) { update... }` 安全**：后者是"先读再写"，两步之间别人可能已经把库存扣到 0；
而上面这条 SQL 里"判断"和"扣减"是**同一条语句**，InnoDB 执行时会加行锁，无法插入。

**返回值也是信息**：`update` 返回 false 说明 `stock > 0` 不成立 → DB 侧真没库存了 →
你代码在这里 `rollbackRedis` 并 return，把 Redis 的预扣还回去。这叫**DB 是最终真值，Redis 只是闸门**。

> 面试话术：「DB 扣库存我没用 select 再 update，而是用了带条件的 update，
> 靠'affected rows 是否为 0'判断结果。这是乐观锁的思路 —— 不提前加锁，让条件本身成为锁。」

## 1.4 深潜 ③：prefetch 与 requeue —— `application.yaml` 里那几个反直觉的配置

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 2
        prefetch: 1                            # 每个消费者最多 1 条未 ack
        default-requeue-rejected: false        # 失败不要塞回队列，直接走死信
        retry:
          max-attempts: 3                      # 总共 3 次 = 首次 + 重试 2 次
          multiplier: 2                        # 1s → 2s 退避
```

**人话解释这三个数字在干什么**：

- `prefetch: 1`：不给消费者"囤货"。如果设成 250（默认），一个消费者会把队列里 250 条全抓在手里，
  另外 3 个消费者干看着 —— 你以为开了 4 个线程，实际还是串行。这就是你注释里写的坑。
- `default-requeue-rejected: false`：默认 `true` 时，处理失败的消息会被塞回**队头**，
  立刻又被同一个消费者捞到 → 无限重投。你注释里记了实测："2 秒 82 次"。设成 false 才会走死信。
- `retry.max-attempts: 3` + `multiplier: 2`：这是**本地重试**（在消费者线程里循环），
  不经过 MQ、不产生 `redelivered` 标记。退避是给下游自愈时间，避免抖动被放大。

> 面试话术：「我把重试分成两层：本地重试 3 次带 1s/2s 退避，处理瞬时抖动；
> 3 次还失败就 reject 进死信，等人处理。关键是要关掉 default-requeue-rejected，
> 否则 broker 会无限重投，把消费线程彻底堵死 —— 我实测过 2 秒 82 次。」

## 1.5 深潜 ④：为什么"回补 Redis"绝不能写在会被重试的方法里

看你自己的代码注释（`VoucherOrderConsumer:85-88`），这是全项目**最值钱的一句经验**：

```java
// ⚠️ 绝不能在这里回补 Redis：本地重试会重复调用本方法，回补会被放大 N 倍。
//    实测：失败 82 次 → Redis 库存 97 被回补到 179，闸门彻底失效。
```

**这个 bug 的本质**：补偿操作本身不幂等，而它被放在了一个会被执行 N 次的位置。

```
一次失败 → 本地重试 3 次 → 回补 3 次 → 再进死信再补 1 次 → 库存凭空变多 → 超卖
```

**正确做法（你现在的做法）**：回补统一挪到"重试彻底耗尽之后"，也就是
`SeckillDeadLetterConsumer` 里，每条死信只补一次；并且用 `seckill:dlq:done:{orderId}`
这个标记键做**补偿幂等**（见 `RedisConstants:29`）。

> 面试话术：「我更愿意讲这个 bug 而不是讲我写了多少功能。起因是我把回补写在了
> 会被重试的方法里，实测失败 82 次把 Redis 库存从 97 补到 179，闸门直接失效。
> 修法是把补偿挪到死信消费端，并且给补偿加一个 done 标记做幂等。
> 由此我总结出一条原则：**补偿操作必须幂等，且只能在一个'确定不会重复'的位置执行**。」

# 第 2 章 · 阶段一：让别人能一键跑起来

> **现状**：`docker-compose.yml` 已经把三份 SQL 挂成初始化脚本，这一步 90% 已完成。
> **剩下要做**：`upgrade_v2` 幂等化 + README 补全 + 亲手验证一次。

## 2.1 先理解「可复现」到底在考什么

面试官问你项目，第一句话往往是"这项目我能跑起来吗"。他真正想确认三件事：

1. 你有没有把**环境当成代码**来管理（Infrastructure as Code）；
2. 你的 SQL 是不是**幂等**的（跑两遍会不会报错）；
3. 你的默认配置是不是**不给别人添麻烦**（端口冲突、缺库、缺表）。

这三件事跟你写了多少业务代码毫无关系，但它是**工程素养的第一眼**。

## 2.2 专业名词：初始化脚本（initdb）与数据卷（volume）

> 💡 **initdb 脚本**：MySQL 官方镜像的约定 —— 容器**第一次**启动、且数据目录为空时，
> 会按**文件名字母序**执行 `/docker-entrypoint-initdb.d/` 下的 `.sql` / `.sh` 文件。
> 你的 compose 就是把仓库里三份 SQL 挂进去并改名成 `01/02/03`，从而锁死顺序。

> 💡 **数据卷（volume）**：容器删了数据还在的存储。`mysql-data` 这个卷一旦有了数据，
> initdb 就**再也不会执行**。所以"我改了 SQL 但没生效"的根因永远是这个 —— 用 `down -v`。

这两句合起来就是一个高频追问：

> 面试官：「你改了 SQL 怎么让它生效？」
> 你：「`docker compose down -v` 删卷再 `up`，因为 initdb 只在数据目录为空时执行一次。
> 生产环境当然不会这么干，生产是版本化的 migration（Flyway/Liquibase）。」

## 2.3 专业名词：DDL 幂等（`IF NOT EXISTS`）

你现在的三份脚本状态不同，这正好是一道教学题：

| 脚本 | 建表语句 | 幂等？ | 结论 |
|---|---|---|---|
| `src/main/resources/db/hmdp.sql` | 11 个 `CREATE TABLE` + 11 个 `DROP TABLE` | ✅（先删后建） | 能重复跑，但会**清空数据** |
| `src/main/resources/db/upgrade_v2_coupon_member_ai.sql` | 12 个裸 `CREATE TABLE` | ❌ | 第二次跑报 `Table already exists` |
| `db/seckill_dead_letter.sql` | `CREATE TABLE IF NOT EXISTS` | ✅ | 天然幂等，不用改 |

**动手（唯一要改的地方）**：把 `upgrade_v2` 里 12 处 `CREATE TABLE ` 全部换成
`CREATE TABLE IF NOT EXISTS `。

> 幂等的两种做法「先删后建」和「存在则跳过」，前者安全但**丢数据**，后者才是升级脚本该用的。

## 2.4 专业名词：单一真实来源（Single Source of Truth）

你的 compose 用的是**挂载改名**：

```yaml
- ./src/main/resources/db/hmdp.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
```

而不是"再复制一份到 `db/init/`"。这个选择的专业说法叫 **单一真实来源**：
仓库里 SQL 只有一份，改了就同时影响"手动导入"和"容器初始化"两条路径。

反例（很多教程这么教，但会留坑）：复制两份 → 某天只改了一份 → 新人按 README 跑，
表结构是旧的 → 排查半天。

> 面试话术：「初始化脚本我用挂载而不是复制，保证仓库里只有一份真实来源；
> 文件名改成 01/02/03 锁住执行顺序，因为官方镜像按字母序跑。」

# 第 3 章 · 阶段二：让线上问题「一次就能定位」

> **现状**：没有 actuator、没有 traceId。日志里认不出"这 20 行属于哪一次请求"。
> **成本**：半天。**收益**：面试官问"线上出问题你怎么查"时，你能现场演示。

## 3.1 先想清楚：可观测性要解决的是"三个不知道"

| 不知道 | 需要什么 | 专业名词 |
|---|---|---|
| 这个报错属于哪次请求？ | 一次请求一个编号，贯穿所有日志 | **traceId** + **MDC** |
| 服务现在活得怎么样？ | 能问服务要状态 | **健康检查 / 指标（metrics）** |
| 慢在哪一段？ | 每段耗时可查 | 埋点 / 链路追踪 |

你现在三条全缺。**不要一次补齐**，先做前两条，半天就能完成，收益最大。

## 3.2 专业名词：MDC 到底是什么

> 💡 **MDC（Mapped Diagnostic Context）**：SLF4J 提供的一个"绑定在当前线程上的 Map"。
> 你往里放 `traceId=abc123`，之后这个线程打的所有日志，都能用 `%X{traceId}` 取出来。
> 本质是 **ThreadLocal** —— 所以它只对"当前线程"有效。

这带出**两个必考坑**（你能讲出来就赢了）：

1. Tomcat **线程是复用的**。如果你不清理，下一个请求会带着上一个请求的 traceId 打日志，串号。
   → 所以 `finally { MDC.remove(...) }` 是必需的，不是可选。
2. 你一旦 `new Thread(...)` 或丢进线程池（比如 `ShopServiceImpl` 里那个
   `CACHE_REBUILD_EXECUTOR`），MDC **就断了**，异步日志没有 traceId。
   → 生产做法是 `TaskDecorator` 传递 MDC；你项目里可以先接受"异步任务日志无 traceId"，但**要能说出这句话**。

## 3.3 动手①：一个 Filter 就能覆盖所有请求

新建 `src/main/java/com/hmdp/config/TraceIdFilter.java`：

```java
package com.hmdp.config;

import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import javax.servlet.FilterChain;
import javax.servlet.ServletException;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.UUID;

/**
 * 请求级 traceId：进来时生成（或沿用上游传来的），出口塞进响应头，日志里靠 MDC 打出来。
 * <p>
 * 为什么用 Filter 而不是 Interceptor：拦截器只能拦住"进入 Controller 的请求"，
 * 404、静态资源、异常在进入 Controller 之前就已经发生了；Filter 更靠外层，能兜住全部。
 */
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID = "traceId";
    public static final String HEADER = "X-Trace-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        // 上游（网关/前端）已经传了就复用，这样跨服务还能串起来
        String traceId = request.getHeader(HEADER);
        if (traceId == null || traceId.trim().isEmpty()) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }
        MDC.put(TRACE_ID, traceId);
        response.setHeader(HEADER, traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(TRACE_ID);   // 线程池会复用线程，不清就会串号
        }
    }
}
```

再改 `application.yaml` 的日志格式（**加**到已有 `logging` 下面，别覆盖原有 `level` / `file`）：

```yaml
logging:
  level:
    root: info
    com.hmdp: debug
    org.springframework: info
  file:
    name: logs/hmdp.log
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [%X{traceId:-no-trace}] %logger{36} - %msg%n"
    file:    "%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%X{traceId:-no-trace}] %logger{36} - %msg%n"
```

> `%X{traceId:-no-trace}` 的含义：取 MDC 里的 traceId，**取不到就显示 `no-trace`**。
> 定时任务、启动日志都取不到，正好用 `no-trace` 区分 —— 比打印空方括号清晰。

**✅ 验证**：

```powershell
mvn -o -q spring-boot:run
# 另开窗口
curl.exe -i http://localhost:8081/shop/1 | Select-String "X-Trace-Id"
Select-String -Path logs\hmdp.log -Pattern 'a1b2c3d4'   # 换成上一步拿到的 id
```

期望：响应头有 `X-Trace-Id`，日志里用同一个 ID 能 grep 出这次请求的**全部** SQL 和业务日志。

## 3.4 动手②：Actuator，先加依赖再想暴露什么

`pom.xml`（版本由 parent 管理，不用写 `<version>`）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

`application.yaml`：

```yaml
management:
  server:
    port: 8089            # ★ 独立端口：不跟业务端口混，也不被你的拦截器拦住
    address: 127.0.0.1    # 只监听本机，别暴露到公网
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  endpoint:
    health:
      show-details: always
```

**为什么必须用独立端口 —— 这是本步最重要的一个坑**：

你 `MvcConfig` 里注册了 `LoginInterceptor.addPathPatterns("/**")`。
如果 actuator 和业务共用 8081，那 `/actuator/health` 也会被当成"需要登录的接口"→ 返回 **401**，
而且因为它 **不抛异常**、只是 `setStatus(401)`，`@RestControllerAdvice` 也管不到，
排查时会非常迷惑（"我明明没配鉴权，为什么监控探活一直是红的"）。

两条解法，选一条并说得出理由：

| 解法 | 做法 | 取舍 |
|---|---|---|
| **独立端口（推荐）** | `management.server.port: 8089` + `address: 127.0.0.1` | 彻底隔离，顺便解决"不能暴露公网"的问题 |
| 同端口 + 放行 | `excludePathPatterns("/actuator/**")` | 简单，但监控端点就暴露在业务域名下了 |

**✅ 验证**：

```powershell
curl.exe -s http://127.0.0.1:8089/actuator/health     # {"status":"UP"}
curl.exe -s http://127.0.0.1:8089/actuator/metrics/http.server.requests
curl.exe -i http://localhost:8081/actuator/health     # 期望 401 —— 证明业务端口没暴露监控
```

最后那条 **401 反而是对的**：它说明你把监控和业务隔开了。

> 监控走 actuator 的独立端口 8089 且只绑 127.0.0.1 —— 因为我的登录拦截器拦的是 `/**`，
> 同端口会让健康检查返回 401，而且监控端点不该暴露在业务域名下。」

# 第 4 章 · 阶段三：让「不会超卖」变成可执行的断言

> **现状**：24 个 `@Test` 全在工具类 / Mapper / 告警判定，**核心链路 0 个**。
> **成本**：1 天。**收益**：面试官问「你凭什么保证正确」时，你能打开 IDE 跑给他看。

## 4.1 先纠正一个误区：单测不是"覆盖率数字"

实习简历上写「单测覆盖率 80%」几乎不加分，因为面试官知道那可以是刷出来的。
真正加分的是**你测在了对的地方**：

| 该测（纯逻辑 + 分支） | 不该测（依赖真实中间件） |
|---|---|
| 拒绝分支：未登录 / 券不存在 / 时间窗 / 库存不足 / 重复下单 | 真连 Redis 跑 Lua（那是集成测试） |
| 消费端幂等：重复消息 / 扣减失败 / 主键冲突 | 真发 MQ 验证 confirm（要 broker） |
| 补偿状态机：不存在 / 已补偿 / 待补偿 / 补偿失败 | 定时对账任务全流程（要三件套） |

判断标准一句话：**「输入 → 输出/副作用」能不依赖外部就确定的，才写单测。**
剩下的是集成测试，靠 `docker compose` 跑，两者别混在一起。

## 4.2 专业名词：Mockito 到底在干什么

> 💡 **Mock（假对象）**：一个假的依赖。你告诉它"别人问你要 `getById(99)` 就返回 null"，
> 它照做，不会真的去连 MySQL。
>
> 💡 **Stub（打桩）**：`when(假对象.方法(参数)).thenReturn(值)` —— 定义假对象的行为。
>
> 💡 **Verify（验证）**：`verify(假对象, times(2)).update(any())` —— 断言"这个方法被调了 2 次"。
> 对**写操作**（扣库存、插订单、回补）来说，**调用次数**才是正确性。

| 注解 | 人话 |
|---|---|
| `@ExtendWith(MockitoExtension.class)` | 让 JUnit 5 帮你初始化下面那些注解（JUnit 4 时代是 `@RunWith`） |
| `@Mock` | 造一个假依赖 |
| `@InjectMocks` | 造真对象，并把上面那些假依赖塞进去（构造器/setter/字段注入） |
| `never()` / `times(n)` | 一次都没调 / 正好调 n 次 |

**为什么不用 `@SpringBootTest`**：那会启动整个 Spring 容器 + 连 Redis + 连 MySQL，
跑一个断言要 5 秒，还动不动因为环境没起而红。
你现有的 `RedisIdWorkerTest` 是 `@SpringBootTest`（它**确实**需要 Redis），
而下面两个类纯 Mockito，**12 条用例 1.7 秒跑完**。

## 4.3 动手①：秒杀入口的 9 条拒绝分支

> **这 9 条用例里，最值钱的是最后两条**：它们不测业务，测的是**约定**
> （"第三个参数必须是 userId""key 前缀必须是这个"）。这类错误不会让程序报错，
> 只会让功能静默失效 —— 也就是最难排查的那类 bug。

## 4.4 动手②：消费端幂等的 3 条用例（用 verify 断言副作用）

新建 `src/test/java/com/hmdp/service/impl/VoucherOrderConsumerTest.java`：

```java
package com.hmdp.service.impl;

import com.hmdp.dto.SeckillOrderMessage;
import com.hmdp.entity.VoucherOrder;
import com.hmdp.mapper.VoucherOrderMapper;
import com.hmdp.service.ISeckillVoucherService;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.data.redis.core.StringRedisTemplate;

import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.times;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

/**
 * 消费端幂等单测：三个分支都必须"不多扣、不少扣"。
 * <p>
 * 注意这里断言的不是返回值（方法是 void），而是<b>副作用次数</b> ——
 * verify(...) 才是这类"写操作"测试的核心：调用了几次、有没有误调。
 */
@ExtendWith(MockitoExtension.class)
class VoucherOrderConsumerTest {

    @Mock private ISeckillVoucherService seckillVoucherService;
    @Mock private VoucherOrderMapper voucherOrderMapper;
    @Mock private StringRedisTemplate stringRedisTemplate;

    @InjectMocks
    private VoucherOrderConsumer consumer;

    private SeckillOrderMessage msg() {
        return new SeckillOrderMessage(10001L, 1001L, 99L);
    }

    /** 分支 1：订单已存在 → 直接 return，绝不能扣库存 */
    @Test
    void duplicateMessageIsIgnored() {
        when(voucherOrderMapper.selectById(10001L)).thenReturn(new VoucherOrder());
        consumer.handleSeckillOrder(msg());
        verify(seckillVoucherService, never()).update(any());
        verify(voucherOrderMapper, never()).insert(any());
    }

    /** 分支 2：DB 扣库存失败（stock 已到 0）→ 回补 Redis，不插订单 */
    @Test
    void dbStockZeroRollsBackRedis() {
        when(voucherOrderMapper.selectById(10001L)).thenReturn(null);
        when(seckillVoucherService.update(any())).thenReturn(false);
        consumer.handleSeckillOrder(msg());
        verify(voucherOrderMapper, never()).insert(any());
        verify(stringRedisTemplate).opsForValue();   // 调到回补逻辑了
    }

    /** 分支 3：并发下主键冲突 → 把多扣的 1 张还回 DB，但绝不动 Redis */
    @Test
    void duplicateKeyRestoresDbStockButNotRedis() {
        when(voucherOrderMapper.selectById(10001L)).thenReturn(null);
        when(seckillVoucherService.update(any())).thenReturn(true);
        when(voucherOrderMapper.insert(any())).thenThrow(new DuplicateKeyException("dup"));
        consumer.handleSeckillOrder(msg());
        verify(seckillVoucherService, times(2)).update(any());   // -1 一次，+1 一次
        verify(stringRedisTemplate, never()).opsForValue();      // Redis 一次都不能碰
    }
}
```

**逐条讲这三个断言的"为什么"**：

| 用例 | 断言 | 如果写错会怎样 |
|---|---|---|
| `duplicateMessageIsIgnored` | `update` 0 次 | 重复消息把库存扣穿 → 超卖 |
| `dbStockZeroRollsBackRedis` | 插订单 0 次、Redis 被回补 | DB 没货却生成订单 → 脏数据 |
| `duplicateKeyRestoresDbStockButNotRedis` | `update` 2 次、Redis 0 次 | 回补 Redis → 把成功用户解锁 → 又多卖一张 |

第三条对应你代码里那句注释："绝对不能动 Redis —— 那会把一个已经下单成功的用户重新解锁"。
**这条注释现在有测试保护了**，这就是「工程化」和「写了个 demo」的区别。

# 第 5 章 · 阶段四：把「优化」变成「一张能拿出手的表」

> **现状**：0 张压测数字。
> **成本**：1 天。**收益**：全项目 ROI 最高 —— 没有这张表，前面所有优化在面试里都只是"我觉得快了"。

## 5.1 专业名词：QPS / TPS / RT / P99

| 指标 | 人话 | 你项目里怎么用 |
|---|---|---|
| **QPS** | 每秒能处理多少请求 | 压测的"吞吐"侧 |
| **TPS** | 每秒完成多少"事务"（一个事务=一次完整业务） | 秒杀里 1 TPS = 1 单 |
| **RT**（响应时间） | 一个请求从发出到收到响应花多久 | 平均 RT 会骗人，看 P99 |
| **P99** | 99% 的请求都快于这个值 | "平均 20ms 但 P99 800ms" = 有长尾卡顿 |
| **连接池** | 复用数据库连接，避免每次 TCP 握手 | HikariCP 默认 10，并发 200 时会排队 |

**为什么必须看 P99 而不是平均值**：100 个请求 99 个 5ms、1 个 2s，平均值才 25ms 看着很漂亮，
但那 1 个用户就是超时退款的人。**平均值掩盖长尾，P99 暴露长尾。**

## 5.2 压测的三个铁律（不做这三条，数字就是编的）

1. **同一台机器、同一份数据**。改前改后必须用**同一台电脑**、**同样的初始库存（100）**、
   同样的并发数，否则数字没有可比性。
2. **预热**（warm-up）。JVM 前几千次调用在解释执行，之后才 JIT 编译成本地码。
   **丢掉前 30% 的请求**再统计，或者先单独跑一轮热身。
3. **跑三次取中位数**。GC、后台任务、Windows 索引都会造成抖动，一次的结果不可信。

> 面试话术：「我不信单次压测的数字。我的做法是固定机器和初始数据、先预热一轮、
> 连跑三次取中位数，并且主要看 P99 而不是平均值 —— 平均值会把长尾藏起来。」

## 5.3 你项目特有的一个坑：一人一单会让压测"看起来没效果"

你 `seckill.lua` 里有 `SISMEMBER` —— 同一个 userId 第二次请求直接返回 2。
所以：

- ❌ 用**同一个 token** 发 200 次 → 只有第 1 次成功，其余 199 次全被"每人限购"挡掉，
  压出来的是"判重逻辑"的性能，不是"下单链路"的性能；
- ✅ 用**200 个不同用户**各请求 1 次（库存 100）→ 期望 100 成功 100 售罄，
  这才测到了完整链路。

**怎么快速造 200 个 token**：你项目登录接口是 `POST /user/login`（`code` 从日志里取）。
写个脚本：先请求验证码 → 从日志 grep → 登录 → 拿到 token 存 CSV。
如果嫌麻烦，**退一步的方案**：直接把 `seckill:user:{id}` 这个 Set 在每次请求前清掉，
用同一个 token 压 —— 这是"放宽业务约束专测技术链路"的做法，**但报告里必须写明**，
否则就是数据造假。

## 5.4 动手：一个 40 行的 PowerShell 压测脚本（不用装 JMeter）

你的 compose 只有 3 个依赖服务（`hmdp-mysql` / `hmdp-redis` / `hmdp-rabbitmq`），
应用用 `mvn spring-boot:run` 跑在 8081。先准备 `tokens.txt`（每行一个 token），
再放这个脚本到项目根目录 `loadtest.ps1`：

```powershell
param(
    [string]$Url    = "http://localhost:8081/voucher-order/seckill/99",
    [int]$N         = 200,
    [string]$Tokens = "tokens.txt"
)
$ErrorActionPreference = "Stop"

$tokens = Get-Content $Tokens -Encoding UTF8 | Where-Object { $_.Trim() -ne "" }
if ($tokens.Count -lt $N) { throw "token 不足：需要 $N，实际 $($tokens.Count)" }

$client = New-Object System.Net.Http.HttpClient
$client.Timeout = [TimeSpan]::FromSeconds(30)

$tasks = New-Object System.Collections.ArrayList
$sw = [System.Diagnostics.Stopwatch]::StartNew()
for ($i = 0; $i -lt $N; $i++) {
    $req = New-Object -TypeName System.Net.Http.HttpRequestMessage `
                      -ArgumentList ([System.Net.Http.HttpMethod]::Post), $Url
    $req.Headers.Add("authorization", $tokens[$i].Trim())
    [void]$tasks.Add($client.SendAsync($req))
}
# 一把梭：所有请求先全部发出去，再等全部结束 —— 这才叫"并发"
[System.Threading.Tasks.Task]::WaitAll($tasks.ToArray())
$sw.Stop()

$elapsed = $sw.Elapsed.TotalSeconds
"请求数 = $N ; 墙钟耗时 = {0:N2}s ; 吞吐 = {1:N0} QPS" -f $elapsed, ($N / $elapsed)

# 按响应体分组：这是"正确性"证据，比 QPS 重要
$tasks | ForEach-Object { $_.Result.Content.ReadAsStringAsync().Result } |
    Group-Object | Sort-Object Count -Descending |
    ForEach-Object { "{0,5} 条 -> {1}" -f $_.Count, $_.Name }
```

跑法：

```powershell
cd D:\heimadianping\hm-dianping
.\loadtest.ps1 -N 200
```

**两个必须知道的细节**：

1. `HttpClient` 是"先全部 `SendAsync` 再 `WaitAll`"。如果你写成 `foreach { await }`，
   那就是**串行**压测，测出来的是单请求延迟，不是并发能力 —— 这是压测新手最常见的假数据。
2. Windows 默认 Tomcat 的 `max-threads` 是 200。你正好压 200 并发，
   如果 RT 突然从 20ms 跳到 500ms，**先怀疑线程池排队**，而不是"代码慢"。
   可以 `management.metrics` 看 `tomcat.threads.busy`。

## 5.5 采集"三个必须相等"的数字（这是验收，不是装饰）

压测结束后立刻采集，**顺序不能乱**（先读 Redis 再读 DB，否则对账任务可能已介入）：

```powershell

docker exec hmdp-mysql mysql -uroot -proot -N -e "select stock from hmdp.tb_seckill_voucher where voucher_id=99"
docker exec hmdp-mysql mysql -uroot -proot -N -e "select count(*) from hmdp.tb_seckill_dead_letter"
```

初始库存 100、200 个不同用户压一轮，**这三个等式必须同时成立**：

```

    = tb_voucher_order 里 voucher_id=99 的行数
    = 100

DB 剩余库存 = Redis 剩余库存 = 0
死信条数 = 0
```

| 现象 | 最可能的原因 |
|---|---|
| 订单数 < 100 且死信 > 0 | 消费失败，去 `tb_seckill_dead_letter` 看 `reason` |
| 订单数 > 100 | Redis 库存没清理干净 / 回补逻辑被重复执行 |
| Redis 剩余 ≠ DB 剩余 | 有请求在 Lua 成功但 MQ 投递失败（被 `rollbackRedis` 补回），查日志 |
| 死信 = 0 但订单数 < 成功数 | 响应成功但消息没落库 → 生产端 confirm 逻辑有洞 |

## 5.6 采集 DB 的真实压力：`Com_select` 增量

这是**证明优化有效**的关键证据。优化前每次请求都查一次券（`VoucherOrderServiceImpl:65`），
优化后走 Redis 元数据缓存 —— 这个差别只有计数器能证明：

```powershell

# 压测后（同一个容器，不要重启）
docker exec hmdp-mysql mysql -uroot -proot -N -e "show global status like 'Com_select'"
```

`(压测后 - 压测前) ÷ 压测秒数 = 平均 SELECT QPS`。

> 💡 **为什么用 `Com_select` 而不是 `Questions`**：`Questions` 把 `SET`、`COMMIT`、
> 事务控制语句都算进去，而且健康检查也会污染。`Com_select` 只统计 SELECT，
> 正好对应"你多打了几次库"这件事。

# 第 6 章 · 阶段五：让 API 变「专业」—— 错误码与参数校验

> **现状**：`Result` 只有 `success` + `errorMsg`，前端只能靠**中文文案**判断，改一个字就崩。
> `BizException` 只有 message，没有 code。参数校验基本靠 if。
> **成本**：半天。**收益**：体现"接口是给机器用的，不是给人看的"。

## 6.1 专业名词：HTTP 状态码 vs 业务错误码

> 💡 **HTTP 状态码**：描述「这次 HTTP 交互本身」的结果 —— 200 收到了、401 没认证、404 地址不对、500 服务端炸了。
>
> 💡 **业务错误码**：描述「业务为什么没成功」—— 库存不足？已过期？重复领取？
> 这些都属于"请求本身处理成功"，所以 HTTP 依然是 200。

**两层是正交的**。你的项目（和很多国内团队一样）**统一返回 200**，
把失败信息放 body 里。这个选择有代价也有理由：

| 方案 | 优点 | 代价 |
|---|---|---|
| 只用 HTTP 状态码 | 符合 REST 语义，网关/监控天然能统计 | 业务失败种类远多于 HTTP 码，塞不下 |
| **统一 200 + 业务码（你的现状）** | 前端只写一套解析逻辑；业务码可无限扩展 | HTTP 层失去含义，必须靠 code 补回来 |

所以你现在最缺的不是"改 HTTP 状态码"，而是 **`code` 字段** —— 否则前端在拿中文文案做 `if`。

## 6.2 编码规则：第一位代表「谁的责任」

这是本章唯一需要背下来的设计原则：

```
0        成功
4xxx     调用方/业务状态问题（重试没用，要用户改行为）
5xxx     服务方问题（用户重试也许有用，要报警/排查）
```

再按模块细分后三位（`42xx` = 秒杀模块）：

| code | 含义 | 谁的问题 |
|---|---|---|
| `0` | 成功 | — |
| `4000` | 通用业务失败（老代码 `throw new BizException("文案")` 的兜底） | 业务 |
| `4100` | 参数不合法 | 调用方 |
| `4101` | 未登录/登录过期 | 调用方 |
| `4201` | 秒杀券不存在 | 调用方 |
| `4202` | 秒杀尚未开始 | 调用方（来早了） |
| `4203` | 秒杀已结束 | 调用方（来晚了） |
| `4204` | 库存不足 | 业务状态 |
| `4205` | 每人限购一件 | 调用方（重复请求） |
| `5000` | 服务内部异常 | 服务方 |

**为什么这个规则值钱**：监控可以据此告警 —— `5xxx` 比例上升要打电话叫醒人，
`4xxx` 上升只说明运营活动太火。**一个数字同时解决了前端分支和运维告警。**

> 完整代码见 `docs/改进执行手册.md` 的 Step 6（`ErrorCode` 枚举 + `Result.code` +
> `BizException` 增强 + advice 合并），这里只讲**为什么那样写**，避免两份文档打架。

## 6.3 三个必须理解的技术点（不看会踩坑）

### ① 不要新建第二套异常体系

你**已经有**三个类：

| 文件 | 职责 |
|---|---|
| `exception/BizException` | 可预期失败的载体（现在缺 code） |
| `config/BizExceptionAdvice` | `BizException` → warn + `Result.fail`；`DuplicateKeyException` → "请勿重复提交" |
| `config/WebExceptionAdvice` | `RuntimeException` 兜底 → error + "服务器异常" |

再加一个 `GlobalExceptionHandler` 声明 `@ExceptionHandler(Exception.class)` 会怎样？
Spring 在多个 advice 里选"最具体"的处理器，但**两个都声明 `Exception.class` 时是不确定的**，
你的 `4100` 可能被 `5000` 抢走，而且不会报错，只是行为飘忽。

> 面试话术：「我没有新建一套异常体系，而是在已有 `BizException` 上挂 `ErrorCode`。
> 因为两个 `@RestControllerAdvice` 都声明 `Exception.class` 时，处理器选择是不确定的 ——
> 这种 bug 不会报错，只会'有时对有时不对'，是最难查的一类。」

### ② Spring 5.2 的坑：`MethodArgumentNotValidException` **不是** `BindException`

你的项目是 Spring Boot **2.3.12** → Spring Framework **5.2.x**。
在这个版本里：

```
MethodArgumentNotValidException extends Exception      （JSON body 校验失败）
BindException                    extends Exception      （表单/查询参数绑定失败）
```

两者**没有继承关系**（Spring 6.0 才让前者继承后者）。
而且还有**第三种**：类上标了 `@Validated` 之后，`@PathVariable` / `@RequestParam` 上的约束失败，
抛的是 `javax.validation` 的 `ConstraintViolationException`。

所以校验失败一共三个入口，**三个都要接**，否则会掉到 `Exception` 兜底 → 返回 5000：

| 触发方式 | 异常类型 |
|---|---|
| `@RequestBody @Valid` | `MethodArgumentNotValidException` |
| 表单 / 查询参数绑定 | `BindException` |
| `@PathVariable` / `@RequestParam` + 类上 `@Validated` | `ConstraintViolationException` |

三个 handler 的代码如下：

```java
/**
 * JSON body 上的 @Valid 失败（Spring 5.2 里它不继承 BindException，必须单独接）。
 * 用 stream 把每个字段的错误拼起来，前端能一次看到所有问题，而不是改一个报一个。
 */
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
    String detail = e.getBindingResult().getFieldErrors().stream()
            .map(fe -> fe.getField() + " " + fe.getDefaultMessage())
            .collect(Collectors.joining("; "));
    log.warn("参数校验失败：{}", detail);
    return Result.fail(ErrorCode.PARAM_INVALID, detail);
}

/** 查询参数/表单绑定失败（@ModelAttribute、URL 参数类型不匹配） */
@ExceptionHandler(BindException.class)
public Result handleBindException(BindException e) {
    String detail = e.getBindingResult().getFieldErrors().stream()
            .map(fe -> fe.getField() + " " + fe.getDefaultMessage())
            .collect(Collectors.joining("; "));
    log.warn("参数绑定失败：{}", detail);
    return Result.fail(ErrorCode.PARAM_INVALID, detail);
}

/**
 * 方法参数校验失败：Controller 类上标了 @Validated，且 @PathVariable/@RequestParam 带了约束。
 * 这个异常来自 javax.validation，跟前两个不是同一套体系 —— 不接就会变成 5000。
 */
@ExceptionHandler(ConstraintViolationException.class)
public Result handleConstraintViolation(ConstraintViolationException e) {
    String detail = e.getConstraintViolations().stream()
            .map(v -> v.getPropertyPath() + " " + v.getMessage())
            .collect(Collectors.joining("; "));
    log.warn("参数校验失败：{}", detail);
    return Result.fail(ErrorCode.PARAM_INVALID, detail);
}
```

### ③ `@ExceptionHandler` 的形参类型必须和声明类型一致

```java
@ExceptionHandler(BizException.class)
public Result handleBizException(Exception e) { ... }   // ❌ 启动时/运行时抛 IllegalStateException
```

Spring 会在处理异常时再抛一个异常，**原始错误被彻底掩盖**，前端只看到一个无关的 500。
这个坑很隐蔽，因为编译不报错。

## 6.4 参数校验：把 if 从 Controller 挪到注解里

你现在的 `VoucherOrderController` 是这样（真实代码）：

```java
@RestController
@RequestMapping("/voucher-order")
public class VoucherOrderController {

    @Resource
    private IVoucherOrderService voucherOrderService;

    @PostMapping("seckill/{id}")
    public Result seckillVoucher(@PathVariable("id") Long voucherId) {
        return voucherOrderService.seckillVoucher(voucherId);
    }
}
```

**它的问题不是"差一行校验"，而是职责错位**：`voucherId <= 0` 这种约束，
现在只能靠 Service 里"查不到券 → 秒杀券不存在"间接兜住 —— 前端拿到的是 `4201` 而不是 `4100`，
而且每个非法请求还白跑一次缓存/DB 查询。

改成注解只需要两处（类上 `@Validated` + 参数上 `@Min`）：

```java
@RestController
@RequestMapping("/voucher-order")
@Validated                                    // ← 类级别：开启方法参数校验
public class VoucherOrderController {

    @Resource
    private IVoucherOrderService voucherOrderService;

    @PostMapping("seckill/{id}")
    public Result seckillVoucher(
            @PathVariable("id") @Min(value = 1, message = "voucherId 不合法") Long voucherId) {
        return voucherOrderService.seckillVoucher(voucherId);
    }
}
```

如果是 `@RequestBody` 的 DTO，就把约束写在字段上、参数加 `@Valid`：

```java
public class SeckillRequest {
    @NotNull(message = "voucherId 不能为空")
    @Min(value = 1, message = "voucherId 不合法")
    private Long voucherId;
}

@PostMapping("/seckill")
public Result seckill(@Valid @RequestBody SeckillRequest req) { ... }
```

**收益不是"少写几行"**，而是：

- 校验规则**长在数据结构上**，看 DTO 就知道约束；
- 错误文案**集中**，不用在 14 个 Controller 里找；
- 校验失败**统一**走 advice，返回格式一致（`code=4100`）。

# 第 7 章 · 阶段六：把「一个已知的性能坑」变成「一段能讲 5 分钟的经历」

> **现状**：`VoucherOrderServiceImpl:65` 每个请求都 `getById` 打一次 MySQL，**连被拒绝的请求也打**。
> **成本**：半天。**收益**：这是你简历上唯一一个"有 before/after 数字"的技术点。

## 7.1 怎么"读"出问题：三个自问

很多人读自己代码只看"功能对不对"。要发现性能问题，换三个角度问：

| 自问 | 在你代码里的答案 |
|---|---|
| **一次请求打了几次库 / 几次 Redis？** | 入口 1 次 MySQL（第 65 行）；Lua 4 次 Redis；消费端 2 次 SQL |
| **被拒绝的请求，也付出这些成本吗？** | **是** —— 库存不足的请求同样先查了券，然后才被 Lua 拒掉 |
| **这个成本的量级是"每请求"还是"每 N 秒"？** | 每请求 → 放大系数 = 全量 QPS |

**结论**：你对外说"Redis 挡住了 99% 的流量"，但这一行让 DB 收到的 QPS ≈ **全量请求 QPS**。
优化方向不是"让 SQL 更快"（加索引到极限也还是网络往返），而是**让这个查询根本不发生**。

> 面试话术：「我发现问题的办法不是看监控，是读代码时问自己'这个方法的调用频率是多少'。
> `getById` 写在 Lua 之前，意味着连被售罄挡掉的请求都要先打一次库 ——
> 也就是说我引以为傲的 Redis 闸门，省下的是 DB 的写，不是读。」

## 7.2 专业名词：Cache-Aside（旁路缓存）

最常用的缓存模式，三句话：

```
读：先查缓存 → 命中就返回 → 未命中查 DB → 写回缓存 → 返回
写：先更新 DB → 再删缓存（不是改缓存）
```

> 💡 **为什么是"删"而不是"改"**：两个并发写，改缓存的顺序可能和改 DB 的顺序相反，
> 缓存就会留下旧值；而"删"是幂等的，下一次读自然会回源拿到最新值。

> 💡 **为什么是"先 DB 后删缓存"**：先删缓存再写 DB 的窗口里，别的请求会把**旧值**读回来写进缓存，
> 然后你才写完 DB —— 缓存里就长期是旧值（这个现象叫"缓存污染"）。

你手册 Step 4 里 `VoucherController` 建券后那行 `seckillMetaCache.evict(id)`，就是"先 DB 后删缓存"。

## 7.3 三个设计取舍（这才是面试真正在考的东西）

### ① 缓存什么？—— 只缓存"时间窗"，**不缓存库存**

| 数据 | 放哪 | 为什么 |
|---|---|---|
| 开始/结束时间 | Redis Hash（30 秒 TTL） | 读极多、几乎不变，用来做**快速失败** |
| 库存 | Redis 单值 + Lua 扣减 | **只能有一个真值**，多存一份就多一个不一致来源 |
| 券详情（标题/面值） | DB / 已有的券缓存 | 秒杀入口用不到，别顺手带进来 |

这是**单一真值（Single Source of Truth）**原则的具体应用：
同一份数据有两个可写副本时，你必须回答"谁赢"，答不上来就会出现"Redis 显示有货、DB 显示没货"。

### ② TTL 为什么是 30 秒，不是 30 分钟

```
TTL 短 → 数据新鲜，但回源次数多
TTL 长 → 回源少，但"运营改了时间窗"要等很久才生效
```

**判断依据是"数据变更频率 × 变更的容忍延迟"**：
券的时间窗几乎不会在开抢前 30 秒内被改，所以 30 秒的**陈旧窗口**业务可接受，
而它把 DB 查询量从"每请求一次"压到"每券每 30 秒一次"—— 这就是 4~5 个数量级的差距。

### ③ 为什么不用 `@Cacheable`（Spring Cache）

看起来一行注解更优雅，但在这个场景有三个硬伤：

1. **空值穿透不好处理** —— `@Cacheable` 对 `null` 默认不缓存，正好穿透；
2. **TTL 只能全局配**，你这里要"命中 30 秒 / 空值 2 分钟"两套；
3. **序列化不可控** —— 默认 JDK 序列化，Redis 里是乱码，排查时 `redis-cli` 看不懂。

> 面试话术：「我没用 `@Cacheable`，因为它的空值策略、TTL 粒度和序列化方式都不符合这个场景。
> 我手写了 Cache-Aside：命中返回、未命中回源、空值用哨兵 `-1` 缓存 2 分钟防穿透，
> 写入口显式 `evict`，TTL 30 秒兜底。这个组合每一处都能说出理由。」

# 第 9 章 · 追问演练：三层，共 18 问

面试官的问题几乎都能归到三层：**机制**（怎么实现的）、**边界**（出错怎么办）、**取舍**（为什么不选另一个）。
下面每问都只给"能说出口的答法"，细节回看对应章节。

## 9.1 第一层：机制（8 问）

**Q1. 为什么用 Lua 而不是分布式锁？**
A：锁是"把并发变串行"，Lua 是"让竞争条件不存在"。加锁至少要 3 次往返（加锁→查→扣→解锁），
Lua 是 1 次往返、且天然原子。锁还有续期、误删、锁超时等一堆坑，能不用就不用。

**Q2. `seckill.lua` 里为什么先 `GET` 判断再 `DECR`，直接 `DECR` 不行吗？**
A：直接 `DECR` 会把库存扣成负数，虽然可以在返回负值时再 `INCR` 回补，
但"回补"本身又是一次写、又是一个不一致窗口。先判后扣，在脚本内部是原子的，不会出现负数。
**代价是**：判断和扣减分成了两条 Redis 命令，但它们在同一个脚本里执行，Redis 单线程保证不被插入。

**Q3. "本地事务 + 消息"的坑是什么？你现在怎么规避的？**
A：经典坑是"DB 提交成功但消息没发出去"（本地事务和 MQ 不原子），用户没成功却扣了库存。
你的链路绕开了它：**生产端不写 DB**，只做 Redis 预扣 + 发消息，两者都不在 DB 事务里，
失败都有显式补偿（`rollbackRedis`）。
真正需要事务的是消费端：扣库存 + 插订单放在同一个 `@Transactional` 里，要么都成，要么都不成。
**代价**：极端情况"Redis 扣了、消息丢了、回滚也失败" → 少卖一张，由对账兜底。

**Q4. `CorrelationData` 的 `isAck()` 为 true，是不是就代表消息一定进队列了？**
A：不是。`ack` 只代表 **exchange 收到了**。如果路由键写错、队列没绑定，消息会被丢弃（或退回）。
所以你代码里还检查了 `getReturnedMessage() != null` —— 那才是"路由不到队列"的信号。
这两个检查必须成对，少一个就会"以为发出去了，其实没人收"。

**Q5. 死信是怎么进 `seckill.dlq` 的？**
A：三步：① 队列声明时带 `x-dead-letter-exchange` / `x-dead-letter-routing-key`；
② 本地重试 3 次耗尽后，容器按 `default-requeue-rejected: false` 执行 `basicReject(requeue=false)`；
③ broker 发现消息被拒且不重入队，按死信参数转发到 DLX → DLQ。

**Q6. 双拦截器为什么是两个？`order` 决定什么？**
A：`RefreshTokenInterceptor`（order=0）拦 `/**`，只做"有 token 就续期 + 填 `UserHolder`"，**从不拦截**；
`LoginInterceptor`（order=1）只做"没用户就 401"。
分开的原因是**关注点不同**：续期是所有请求都要做的事，鉴权只有部分接口需要。
`order` 越小越先执行，所以续期一定在鉴权之前 —— 否则"token 快过期但还能用"的请求会被误判 401。

**Q7. `UserHolder` 为什么用 ThreadLocal？会不会有坑？**
A：一次请求一个 Tomcat 线程，用 ThreadLocal 传递用户最省参数。
坑有两个：**线程池复用**必须 `remove()`（你 `afterCompletion` 里做了），
**异步线程**读不到（如果丢进线程池，需要手动传递）。

**Q8. 定时对账任务到底在算什么？**
A：三个数对比：`DB 剩余库存` vs `Redis 剩余库存` vs `死信里未补偿的条数`。
不一致时用 CAS 修正（而不是直接覆盖），并把结果打日志。
它是"最后一道保险"——用来兜住"MQ 丢了/补偿失败/人工误操作"这类无法在链路上拦住的问题。

## 9.2 第二层：边界（6 问）

**Q9. 消息投递成功，但消费者一直失败，最后会怎样？**
A：本地重试 3 次（1s/2s 退避）→ 仍失败 → 进死信队列 → `SeckillDeadLetterConsumer` 落库到
`tb_seckill_dead_letter` 并回补 Redis（用 `seckill:dlq:done:{orderId}` 做幂等）→
运维通过 `/seckill/ops/**`（管理员权限）重放，或由定时任务 `settlePending` 批量处理。
**用户的视角**：接口当时返回了订单号，所以必须提供"按订单号查状态"的能力，否则就是"显示成功但没券"。

**Q10. `rollbackRedis` 本身失败了（Redis 挂了）怎么办？**
A：主流程仍然返回失败给用户，但 Redis 里那次预扣就没还回去 → 库存被"少卖"。
你代码里 `catch (Exception ignored)` 是**故意的**：不能在回滚失败时再抛异常，否则用户看到 500 而实际是"没抢到"。
兜底靠对账任务：它比对 Redis 与 DB 的差额，把多扣的库存补回去。
**这个取舍的口径是：宁可少卖，不可超卖。**

**Q11. DB 扣库存成功，但插订单失败（非重复键异常）？**
A：`@Transactional` 会把**同一事务里的扣减回滚**，然后异常抛给容器 → 本地重试。
所以不会出现"扣了库存没订单"的脏数据。**前提是扣减和插入在同一个事务里**——
这也是为什么消费端要单独写一个 `@Transactional` 方法，而不是在 Controller 里串两个 service 调用。

**Q12. 为什么并发主键冲突时，"还回 DB 库存"却"绝不动 Redis"？**
A：因为 Redis 预扣和"用户是否下过单"是**同一个事实**：用户已经成功下单了。
如果这时把 Redis 库存 +1 并把人从 Set 里删掉，这个用户就能再抢一张 → 超卖。
DB 侧多扣的那 1 张是"本事务自己的重复扣减"，必须还。

**Q13. 定时任务在多实例部署时会不会重复执行？**
A：会。Spring 的 `@Scheduled` 是每实例各自触发。你的做法是加 Redis 互斥锁
（`lock:seckill:reconcile:{voucherId}`），并且修正逻辑用 CAS，即使真的并发也不会算错。
**更彻底的方案是 Redisson 的看门狗锁或调度中心（XXL-Job）**，但成本更高。

**Q14. 一人一单的 Set 什么时候清理？**
A：⚠️ **这是你项目里目前的一个真实缺口**：`seckill:user:{voucherId}` 这个 Set 现在**没有设 TTL**，
活动结束后会永久占用内存，同一个券 id 复用还会导致老用户抢不了。
修法：预热库存时顺手 `EXPIRE seckill:user:{id}` 到券的结束时间 + 1 天。
**这条要主动讲**——主动暴露自己项目的缺陷，比被面试官挖出来强十倍。

## 9.3 第三层：取舍（4 问）

**Q15. 既然都异步了，为什么 DB 扣库存不也"彻底异步"给对账去修？**
A：因为**超卖是不可接受的**。异步修数据只能修"少卖"（补回来），修不了"多卖"（用户已经拿到券了）。
所以"能不能卖"必须有一个**同步的、强一致的判断**（DB 的 `stock > 0` CAS），
异步只负责"卖完之后把账记上"。这就是为什么你链路里有两道扣减，而不是一道。

**Q16. 那为什么不干脆只留 DB 扣减，去掉 Redis 预扣？**
A：因为 DB 扛不住。200 并发下每条 `update ... where stock > 0` 都要抢同一行锁，
QPS 会掉到几百甚至几十，而且大量请求是"注定失败"的，白占连接池。
Redis 预扣的价值是**把注定失败的请求挡在 DB 之前**——这是"削峰"，不是"存数据"。

**Q17. 为什么不上 Seata / RocketMQ 事务消息？**
A：成本与收益不匹配。Seata 的 AT 模式要额外的 TC 服务 + undo_log 表，本地单机项目里
等于为了一个"最终一致"引入三个新故障点；RocketMQ 事务消息需要换中间件。
我现在的方案（Redis 预扣 + MQ + 幂等消费 + 死信 + 对账）用**已有组件**达到了同样的最终一致性，
而且每一环都能单独测试。**技术选型的第一原则是"用已经会维护的东西"。**

**Q18. 如果 QPS 再翻 10 倍，你先改哪里？**
A：按"最先崩的地方"排序：
① **入口的元数据查询**（已用缓存解决）；
② **Tomcat 线程数 / 连接池**（`max-threads` 200、Hikari 10 → 会先在队列里排队）；
③ **Redis 单实例**（Lua 是单线程执行，热点 key 会成为瓶颈 → 分片：按 voucherId 取模）；
④ **MQ 消费能力**（`concurrency` + `prefetch` 调优，或按 voucherId 分队列保证顺序）；
⑤ 最后才是**限流/排队**（网关层令牌桶、或前端答题/验证码）。
**注意**：我不会一上来就说"加机器"，因为面试官想听的是**你知道瓶颈在哪**。

# 附录 C：仓库治理实操（D0，面试前必须先做完）

> 10.1 的 D1 写的是「确认 Step 1/2/3 + 一个 commit」。
> 实操上你会发现**连 commit 都做不干净**，所以先做这里的 D0，再做 Step 1 验收。

## C.1 为什么这是第一优先级

开工前这个仓库的真实状态是：

```
$ git log --oneline
00191f2 Initial commit          ← 只有 1 条，而且是一年前的样子

$ git status --porcelain | Group-Object { $_.Substring(0,2) }
[ M] x11   [D ] x1   [AM] x23   [RD] x1   [??] x38
```

一次性扣三笔分：

1. **代码不在仓库里**。会员券、死信、巡检这 30+ 个类全是未跟踪状态，别人 `git clone` 下来看到的是旧骨架——你讲一小时，面试官打开仓库一分钟就否掉了；
2. **仓库里有一年前的日志**。`logs/hmdp.log`（含 SQL 语句、用户手机号、内网地址）+ 9 个 gz 归档，几百 KB 的运行时垃圾被当成源码提交了；
3. **索引本身是坏的**。`RD`、`AA` 这类状态说明有人用 `git add .` 吞过路径写错的文件，git 的 rename 探测把两个无关文件凑成了一对。

**结论：先把仓库整理成人能看懂的样子，再谈优化。** 优化做不出来只是少一个亮点，仓库不体面是直接出局。

## C.2 动手前先看清三件事

```powershell
# 1) 索引里到底有哪些状态（第一列是暂存区，第二列是工作区）
git status --porcelain | Group-Object { $_.Substring(0,2) }

# 2) 哪些文件被跟踪了但其实该忽略
git ls-files logs .workbuddy

# 3) 本地和远端是否分叉
git fetch origin --prune
git log --oneline --graph --all -6
git merge-base HEAD origin/master
```

第 3 步最容易被忽略：本次实测本地 `00191f2`、远端 `841c1d4`，**远端多一条**（在 GitHub 网页上点过一次 "Add README.md"）。这种情况下直接 `git push` 会被拒，必须先 rebase。

## C.3 命令序列（严格按顺序）

```powershell
# ① 清空可能已经错乱的暂存区。--quiet 只是不打印；mixed 模式只动索引，工作区文件一个不动
git reset --quiet

# ② 把「已跟踪但不该跟踪」的目录移出索引。--cached = 磁盘文件保留
git rm -r --cached --quiet logs .workbuddy

# ③ 之后一条一条来，禁止 git add . / git add -A
git add <本批的具体路径>
git diff --cached --stat      # 先看这次到底要提交什么，超过 20 个文件就重新想
git commit -m "<type>(<scope>): 做了什么" -m "<为什么这么做 / 边界是什么>"
```

`type` 只用五种：`feat` / `fix` / `refactor` / `chore` / `test`(+`docs`)。
`-m` 的第二段不是客套话——面试官点开任意一条提交，看到的是「为什么」，这才是你区别于"照教程敲完"的证据。

## C.5 四个坑（这次全部真实踩到）

**坑 1：索引里的「幽灵 rename」。**
`git status` 出现这一行：

```
RD logs/startup.err.log -> src/main/resources/mapper/docker-compose.yml
```

意思是：索引里有一条"把日志重命名成 docker-compose.yml"的记录，而目标文件在工作区里不存在。
成因是 `src/main/resources/mapper/docker-compose.yml` 被误建成了**空文件**（blob `e69de29` 就是空文件），git 的 rename 探测拿它跟"被删的空日志"配成了一对。
**处理**：别去手工解，`git reset` 把索引退回 HEAD，再按路径精确重新 `add`。
**教训**：凡是 `status` 第一列出现 `R`、`AA`、`RD`，先停下来搞清楚，别在上面继续叠提交。

**坑 2：`git rm --cached` 保护不了工作区文件。**
`--cached` 只是"从索引里删、磁盘保留"。但你把这条删除**提交**之后，任何一次 checkout / rebase / 切分支，git 都会按提交内容把工作区里这些文件删掉。
本次 `git rebase origin/master` 一路重放到第 10 条，`logs/` 下 7 个文件当场消失（含正在写入的 796 KB 主日志）。
**能救回什么**：已提交的部分可以从历史里捞——
```powershell
git checkout 00191f2 -- logs   # 从 Initial commit 把删除的文件写回工作区
git reset --quiet              # 立刻取消暂存，否则又被跟踪上
```
**救不回什么**：`hmdp.log` 从 796 KB 恢复到 149 KB，**未提交的 647 KB 增量永久丢失**。
**规矩**：提交"删除日志"之前，先把还要用的文件复制到仓库外；`--cached` 不等于"以后不会再删"。

**坑 3：rebase 时的 ours / theirs 是反的。**
`git rebase origin/master` 报 `AA README.md`（两边都新增了同名文件）。
rebase 过程中 `--ours` = 你 rebase 到的上游，`--theirs` = 正在被重放的那条提交（**你的新版本**）。
所以想保留自己的 README 就是 `git checkout --theirs -- README.md`；记反了就会把 GitHub 上那份 212 行的旧 README 覆盖上来。
拿不准时用绝对引用，绕开语义陷阱：

```powershell
git checkout <你的提交sha> -- README.md   # 明确要哪个版本
git add README.md
git rebase --continue
```
（`--continue` 会弹编辑器改消息，非交互环境先设 `$env:GIT_EDITOR='true'`。）

**坑 4：`push` 报 403 不是仓库不存在。**
`fatal: unable to access ...: The requested URL returned error: 403` = 认证通过了但**身份没有写权限**，或 token 已过期/缺 `repo` scope。
排查顺序：`git remote -v` 看地址 → Windows 凭据管理器里删掉 `git:https://github.com` → 重新 push 走浏览器登录，或用带 `repo` 权限的 PAT。
顺带一句：`GIT_TERMINAL_PROMPT=0` 能让它在无凭据时立刻失败而不是挂住等输入。

## C.6 以后保持的习惯

1. **做完一个 Step 就提交**，不要攒到"全部做完"——攒到最后一定会出现 C.5 那种混合 diff；
2. **提交前必过 `git diff --cached --stat`**，文件数超预期就说明 `add` 的路径写宽了；
3. **不要把日志/凭据/token 放进仓库**；需要留证的片段摘进 `docs/`；
4. 每条提交的正文写**边界和取舍**（"这里为什么放在重试之后，而不是方法里"），这是面试官唯一能看到的你的思考过程。
