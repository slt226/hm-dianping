## 一、做了什么

### 1.1 表结构（3 张）

| 表 | 作用 | 关键设计 |
|---|---|---|
| `tb_coupon_template` | 券模板（长什么样、有多少张） | `total_stock = -1` 表示不限量；`shop_id = 0` 表示全平台；`valid_type` 区分固定区间与领取后 N 天 |
| `tb_user_coupon` | 用户手里的券实例 | `uk_user_coupon` + `uk_member_period` 两个唯一索引，前者防同一张券重复核销，后者防会员月度券重复发放 |
| `tb_coupon_use_log` | 核销流水（只增不改） | `pay_amount` 只写第一行，其余为 0；`uk_user_coupon` 保证一张券一辈子只有一条流水 |

三张表的分工是一条线：**模板定规则 → 实例记归属 → 流水记事实**。
对账时的所有问题，都是在问"这三层有没有对齐"。

### 1.2 接口（8 个）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/coupon/template` | 否 | 建券模板，跨字段语义校验集中在一处 |
| GET | `/coupon/center` | 否 | 券中心分页，返回 `CouponVO`（元、`remainStock`、`expired`） |
| GET | `/coupon/shop/{shopId}` | 否 | 店铺可领券列表 |
| POST | `/coupon/claim/{templateId}` | 是 | 领券，Redis 计数 + DB 扣库存 + 唯一索引三层 |
| GET | `/coupon/my` | 是 | 我的券，按状态分页，返回 `UserCouponVO` |
| GET | `/coupon/available` | 是 | 可用性判断 + 最优组合（枚举 `2^n`） |
| POST | `/coupon/use` | 是 | 下单核销，单事务 |
| POST | `/coupon/revert/{orderId}` | 是 | 退券，按订单号批量回退 |

## 二、并发实测

测试方法：SQL 直接建一张限量券，5 个独立用户用 `WebClient.UploadStringTaskAsync` 同时发起领券，
避免串行等待；结束后对比「DB 库存 / 实际发券数 / Redis 副本」三者。

### 2.1 抢 1 张：5 人并发

| 指标 | 结果 |
|---|---|
| 成功 | **1** |
| 失败（已抢光） | **4** |
| 总耗时 | 18 ms |
| DB `remain_stock` | 1 → **0** |
| `tb_user_coupon` 实际行数 | **1** |
| Redis `coupon:stock:8` | **0** |

### 2.2 抢 3 张：5 人并发

| 指标 | 结果 |
|---|---|
| 成功 | **3** |
| 失败 | **2** |
| 总耗时 | 25 ms |
| DB `remain_stock` | 3 → **0** |
| 发券数 / 去重用户数 | **3 / 3** |
| Redis 副本 | **0** |

### 2.3 这一轮额外验证的两件事

- **Redis 键缺失时能自愈**：压测前手工 `DEL coupon:stock:8`，模拟 Redis 重启。
  领券仍然成功，键被 `setIfAbsent` 按 DB 值回填，之后扣到 0，与 DB 完全一致。
- **不误杀**：3 张库存来了 5 个人，恰好 3 个成功。说明预检没有把可领的请求挡掉。

**结论：没有超发，也没有误杀。**

## 三、踩过的坑（8 条，全部真实发生）

### 坑 1：`LambdaQueryWrapper` 在 JDK 17 下直接炸

- **现象**：`/coupon/**` 全部返回 500，日志里是
  `InaccessibleObjectException: module java.base does not "opens java.lang.invoke"`。
- **根因**：MyBatis-Plus 3.4.3 的 `LambdaQueryWrapper` 靠 `SerializedLambda` 反射拿方法名，
  JDK 16+ 的模块系统默认不允许这种反射。
- **修法**：全部换 `QueryWrapper`，字段名写数据库列名（`user_id`、`create_time`）。
- **教训**：**这个项目里禁止用 `LambdaQueryWrapper`。** 编译期不会报，只有运行时才炸，
  而且报错信息跟 SQL 毫无关系。

### 坑 2：异常处理器自己把异常吃成了 500

- **现象**：`BizException("券已使用")` 抛出去，前端收到的是 `服务器异常`。
- **根因**：写成 `@ExceptionHandler(Exception.class) public Result BizException(BizException e)`——
  注解声明的是 `Exception`，形参却是 `BizException`，Spring 无法绑定参数，
  异常处理本身又抛了 `IllegalStateException`。
- **修法**：`@ExceptionHandler(BizException.class)`，注解与形参类型必须一致。
- **教训**：`@ExceptionHandler` 按继承树距离匹配最具体的那个。声明类型和形参类型不一致时，
  它不会报错，只会在真正出错的那天才暴露——而那天你已经在查业务逻辑了。

### 坑 3：401 掩盖了后面的两个 bug

- **现象**：`/coupon/**` 全部 401，但 `/shop/**` 正常。
- **根因**：`LoginInterceptor` 只写了 `excludePathPatterns`，没写 `addPathPatterns("/**")`。
  排除列表看起来对，实际匹配行为不稳定。另外 `/error` 没排除，
  导致**404 被伪装成 401**（Spring Boot 的 404 会内部转发到 `/error`）。
- **修法**：显式 `addPathPatterns("/**")`，exclude 里补 `/error`。
- **教训**：拦截器两个方法要么都写，要么都别写。只看 exclude 列表判断"白名单生效了"
  是不可靠的——尤其当 404 会被转成 `/error` 再被拦一次时。

### 坑 4：`pay_amount` 每行都写，对账放大 N 倍

- **现象**：一笔订单用 2 张券，流水 2 行，`SUM(pay_amount)` 算出来是实付的 2 倍。
- **根因**：DDL 注释写的是「仅第一张券写入，其余为 0」，实现时按直觉每行都填了。
- **修法**：`log.setPayAmount(i == 0 ? finalPay : 0)`。
- **教训**：**DDL 里的 COMMENT 是业务规则，不是装饰。** 这个坑只有真去对账才会发现，
  接口返回的一切都是正确的。

### 坑 5：记「券面值」而不是「实际抵扣」

- **现象**：订单 5 分钱，用一张 10 元无门槛券，流水里 `discount_amount = 1000`，
  比订单金额还大。
- **根因**：`Math.max(pay, 1)` 会把实付兜底成 1 分，实际只抵了 4 分，但记的是券面值。
- **修法**：记 `before - pay`，即这一段代码真正减少了多少钱。
  这样 `sum(eachCut) + payAmount = originAmount` 永远成立。
- **教训**：**流水要记「发生了什么」，不是「规则允许什么」。**

### 坑 6：`pickedIds` 与 `eachCut` 统计范围不一致

- **现象**：订单 30 元却传了两张「满 100 减 15」，流水写出 2 条 `discount_amount = 0` 的记录，
  券还被标成已使用。
- **根因**：`pickedIds` 取的是入参 `combo` 的全部元素，`eachCut` 只含真正扣减成功的券。
- **修法**：`r.setPickedIds(new ArrayList<>(eachCut.keySet()))`，让"生效的券"只有一个来源。
- **教训**：两个字段描述同一件事时，必须让一个从另一个派生，不能各算各的。

### 坑 7：`status = 2`（已过期）是个没人写的派生状态

- **现象**：「已过期」Tab 永远是空的，过期的券混在「未使用」里。
- **根因**：表里定义了 `2 = 已过期`，但没有任何定时任务会去写它。
- **修法**：查询时按 `expire_time` 现算——未使用 = `status=0 AND expire_time > now()`，
  已过期 = `status=0 AND expire_time < now()`。
- **教训**：**能用现有字段算出来的状态，不要单独存一列。** 存了就得有人维护，
  没人维护就是永久错误。这和"客户端算过期时间不可信"是同一条原则的两面：
  派生状态必须由可信的一方现算。

### 坑 8：`coupon:stock:` 只写不读，Redis 一重启就是一堆空键

- **现象**：Redis 里 7 个 `coupon:stock:*` 全部消失，但领券功能看起来正常。
- **根因**：这个键只在建券时写一次，全项目**没有任何地方读它**。Redis 重启后自然全丢。
- **修法**：把它变成真正的预检缓存——
  启动时 `@PostConstruct` 从 DB 全量校准；领券时 `setIfAbsent` 回填 + `decrement` 预检；
  DB 扣减失败或唯一索引冲突时把预检扣的那 1 个加回去。
  **DB 的 `remain_stock` 始终是唯一真源，Redis 只是可丢弃的副本。**
- **教训**：**一个缓存如果没有读取方，它就不是缓存，是垃圾。**
  加缓存之前先问：谁读它？读不到怎么办？能不能重建？

## 四、工具链上的三个坑（跟业务无关，但很费时间）

| 坑 | 现象 | 解 |
|---|---|---|
| 端口莫名变成 62240 | 命令行启动报 `Port 62240 already in use`，配置里明明写的 8081 | 执行环境有 `PORT` 变量会覆盖配置，启动时显式加 `--server.port=8081` |
| `redis-cli --no-auth-warning` 报错 | `Unrecognized option`，命令直接失败返回空 | 这版 Windows redis-cli 不支持该参数，用 `2>$null` 吞掉警告即可 |
| `curl.exe` 发 JSON 被剥引号 | 后端报 `Unexpected character ... expecting double-quote` | Windows 会再解析一遍参数，JSON 里的双引号丢了。改用 `Invoke-WebRequest` + UTF-8 字节流 |

第三条值得单独记：**排查时如果工具本身在骗你，你会一路查到业务代码里去。**
那次"Redis 里没有验证码"其实是 `--no-auth-warning` 让命令失败返回空，
真正的发码逻辑一直是好的。

## 六、面试口径

### 6.1 「你的券体系怎么保证不超发？」

> 三道闸，任何一道单独失效都不会超发：
> 第一道 Redis 计数挡住重复点击，减少打库；
> 第二道数据库条件更新 `UPDATE ... WHERE status=0 AND remain_stock>0`，**影响行数是唯一判据**；
> 第三道唯一索引兜底，同一张券重复插入会直接冲突。
> 判据永远是影响行数，不是先查后判断——先查后改在并发下必然重复扣减。
>
> 实测：限量 1 张的券，5 个用户并发抢，只有 1 个成功，DB、Redis、实际发券数三者都是 1/0/1，
> 耗时 18 毫秒。

### 6.2 追问「Redis 和数据库库存不一致怎么办？」

> Redis 只是预检，不参与最终判断。真源是 `tb_coupon_template.remain_stock`。
> 所以允许它不一致，也允许它整个丢掉——启动时会从 DB 全量校准，
> 键缺失时按 DB 值 `setIfAbsent` 回填。方向只能是 DB → Redis，反过来就是资损。

### 6.3 追问「为什么不在 Java 里判断库存够不够？」

> 因为"判断"和"扣减"必须是同一条 SQL。分成两步，中间就有窗口：
> 两个请求同时读到 `remain_stock=1`，都判断通过，都扣一次，库存变成 -1。
> 写进 `WHERE` 之后，第二个事务的行锁条件不成立，`UPDATE` 影响 0 行，天然被挡住。
