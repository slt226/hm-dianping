# 秒杀 P0 · 02 消费端幂等 · 复盘

> 第二课。核心一句话：**消费端必须假设"同一条消息会来 N 次"，幂等门禁要放在副作用之前，冲突兜底只能做对自己无害的补偿。**
>
> 上一课（01 消息投递静默失败）解决的是「消息能不能到」；这一课解决的是「到了之后会不会被重复执行 N 次」。
> 所有数字都是本地实测（8081 / MySQL 3306 / Redis 6379 / RabbitMQ 15672）。

---

## 一、一句话概括

修复前，一条重复消息会让**一个已经下单成功的用户被重新解锁**、**Redis 库存凭空 +1**，
而 DB 侧看起来完全正常——净效果为 0 的假象掩盖了两处状态漂移。

修复后，重复消息在**扣库存之前**就被门禁拦下；真撞上并发时，主键冲突分支只回补 DB 库存，
**绝不碰 Redis**。

## 三、问题现场（实验 2-A：复现）

手工往 `seckill.queue` 投一条**已经成功处理过**的消息：

```json
{"orderId":656795491350085637,"userId":12,"voucherId":10}
```

| 观测项 | 修复前 | 判定 |
|---|---|---|
| Redis `seckill:stock:10` | 98 → **99** | ❌ 库存虚增 |
| Redis `SISMEMBER seckill:user:10 12` | 1 → **0** | ❌ 用户被重新解锁，能再抢一张 |
| DB `tb_seckill_voucher.stock` | 98 → 98 | 看不出问题 |
| DB 订单数 | 1 → 1 | 看不出问题 |
| 日志 | `唯一索引冲突` + `UPDATE stock = stock + 1` | 只有这里露馅 |

**关键点：DB 侧净效果为 0，所以"库存对得上"根本不能当作验证通过的标准。**
真正的伤害全在 Redis：用户被解锁 = 多卖一张；Redis 库存 +1 = 这一张永远卖不出去。

### 为什么会这样

那时的 catch 分支是这样写的（错误示范）：

```java
catch (DataIntegrityViolationException dup) {
    rollbackRedis(voucherId, userId);   // ← 全案最致命的一行
    ...
}
```

`rollbackRedis` 的语义是「我这张券没卖出去，把 Redis 预扣还回去」。
可它在**主键冲突**这条路径上被执行了——而主键冲突恰恰说明**这单已经有人建成功了**。
于是它撤销的不是自己的预扣，是**别人的成功**。

## 四、修复：三道防线，各管一段

### 4.1 第一道：门禁，放在副作用之前

```java
// 0.幂等门禁：消息可能被投递多次（网络重投 / ack丢失 / 生产端补偿 / 集群切换）。
//   订单已存在就直接返回，绝不能重复扣库存，更不能回滚一笔已经成功的好单。
//   注意：必须放在"扣库存"之前，否则副作用已经发生，再拦就晚了。
if (voucherOrderMapper.selectById(orderId) != null) {
    log.info("订单已存在，忽略重复消息 | orderId={}", orderId);
    return;
}
```

三个细节，少一个都不成立：

1. **位置**：第 44 行，在第 50 行 `stock = stock - 1` 之前。放在扣库存之后，副作用已经发生，拦了也没用。
2. **判据**：`orderId`，因为它是**生产端生成、随消息一起投递、且在 DB 里是主键**的东西——三个属性缺一不可。
3. **`return` 而不是 `throw`**：正常返回 → 消息 ACK → 不重投。抛异常会触发重投，反而放大问题。

### 4.2 第二道：唯一约束，兜住并发

门禁是 `select`，`select` 和 `insert` 之间有窗口。MySQL 默认 **RR 隔离级别**下，两个并发事务**互相看不见对方未提交的 insert**，所以两条重复消息可以同时通过门禁。

此时能救命的只有主键：

```java
catch (DataIntegrityViolationException dup) {
    //2.兜底：并发下两条相同 orderId 的消息可能同时通过门禁（RR 隔离级别互相看不见对方的 insert），
    //  主键冲突说明"别人已经把这单建好了"。此时本事务自己扣掉的那 1 张要还回去，
    //  但绝对不能动 Redis —— 那会把一个已经下单成功的用户重新解锁，凭空多出一张券。
    log.warn("订单已存在（并发重复），回补本次预扣 | orderId={}, userId={}, voucherId={}",
            orderId, userId, voucherId);
    seckillVoucherService.update(
            new UpdateWrapper<SeckillVoucher>()
                    .setSql("stock = stock + 1")
                    .eq("voucher_id", voucherId)
    );
    return;          // ← 注意是 return，不是 throw
}
```

这解释了「为什么先查一遍还要留唯一约束」：先查是给 99% 的情况省一次失败路径的代价，唯一约束是给那 1% 的并发兜命。**两层都不能删。**

### 4.3 第三道：补偿的边界——只做对自己无害的事

| 分支 | 该不该回滚 Redis | 为什么 |
|---|---|---|
| 门禁命中（订单已存在） | ❌ 不动 | 别人的成功，不是我的预扣 |
| 主键冲突 | ❌ 不动（本次修复点） | 同上，且此时 DB 库存要 +1 回补 |
| DB 扣库存失败（stock=0） | ✅ 回滚 | 单没建成、库存没扣，Redis 预扣确实是多余的 |
| 其他异常 + `throw` | ✅ 回滚 | 事务会整体回滚，Redis 预扣也应当撤销 |

**判据不是"我失败了"，而是"这笔预扣到底还算不算数"。** 只要订单已经存在于 DB，Redis 里的预扣就是有效的，任何回滚都是凭空造券。

### 4.4 一个容易漏的坑：事务边界

`@RabbitListener` 方法和 `@Transactional` 写在**同一个方法**上：

```java
@RabbitListener(queues = "seckill.queue")
@Transactional(rollbackFor = Exception.class)
public void handleSeckillOrder(SeckillOrderMessage msg) {
```

- catch 里 `return` 的分支（门禁、主键冲突、扣库存失败）**吞掉了异常** → 事务提交、消息 ACK。正确。
- 最后一个 catch 里 `throw e` → 事务回滚、异常抛给容器 → 消息重投。这是**第三课（重试 + 死信）**要处理的：不配置 retry 的话，这里会无限重投。

## 五、验证

### 5.1 实验 2-B：串行重复（先到先占）

修复后重新投同一条重复消息（`orderId=656795491350085637`），日志：

```
22:43:06.869  INFO  收到秒杀订单消息: SeckillOrderMessage(orderId=656795491350085637, userId=12, voucherId=10)
22:43:06.877  DEBUG  ==>  Preparing: SELECT id,user_id,voucher_id,... FROM tb_voucher_order WHERE id=?
22:43:06.879  DEBUG  <==      Total: 1
22:43:06.880  INFO   订单已存在，忽略重复消息 | orderId=656795491350085637
```

**此后再无任何 SQL、无任何 Redis 操作。** 数据核对：

| 项 | 投消息前 | 投消息后 |
|---|---|---|
| Redis stock | 98 | **98** |
| `SISMEMBER 12` | 1 | **1** |
| DB stock | 98 | **98** |
| 订单数 | 1 | **1** |

对照 2-A：同样的操作，修复前 Redis 99 / member 0，修复后一动不动。

### 5.2 实验 2-C：并发重复（唯一约束兜底）

单消费者永远是串行，走不到兜底分支。所以临时把消费改成 `concurrency: 2` + `prefetch: 1`，
在**应用停止**时投 2 条完全相同的消息（`orderId=700000000000000002`），再启动应用——
两个消费线程会在连接建立的瞬间同时拿到消息：

```
18:36:03.254  INFO  [#0-1] 收到秒杀订单消息: SeckillOrderMessage(orderId=700000000000000002, ...)
18:36:03.254  INFO  [#0-2] 收到秒杀订单消息: SeckillOrderMessage(orderId=700000000000000002, ...)   ← 同一毫秒
18:36:03.260  DEBUG [#0-1] selectById → （空）
18:36:03.260  DEBUG [#0-2] selectById → （空）                                                     ← 双双通过门禁
18:36:03.269  DEBUG [#0-2] UPDATE tb_seckill_voucher SET stock = stock - 1 WHERE (voucher_id = ? AND stock > ?)
18:36:03.269  DEBUG [#0-1] UPDATE tb_seckill_voucher SET stock = stock - 1 WHERE (voucher_id = ? AND stock > ?)  ← 各扣 1
18:36:03.281  DEBUG [#0-1] INSERT INTO tb_voucher_order ...
18:36:03.284  INFO  [#0-1] 秒杀订单创建成功，orderId=700000000000000002
18:36:03.299  DEBUG [#0-2] INSERT INTO tb_voucher_order ...                                        ← 主键冲突
18:36:03.383  WARN  [#0-2] 订单已存在（并发重复），回补本次预扣 | orderId=700000000000000002, userId=88888, voucherId=10
18:36:03.383  DEBUG [#0-2] UPDATE tb_seckill_voucher SET stock = stock + 1 WHERE (voucher_id = ?)   ← 只回补 DB
```

账目（这才是验收标准）：

```
DB stock  98 → 97   （-1 -1 +1 = 净 -1，恰好等于 1 单）
订单数     0 → 1
Redis     98 → 98   （一动不动）
members   {12,1016} 不变
```

**从"各扣 1"到"回补 1"，三步都能在日志里对上号，这才叫验证过。**

## 六、踩过的两个坑（都会让你误以为实验成功/失败）

### 6.1 `concurrency: 2` 不等于并发消费，`prefetch` 才是分发开关

第一次实验：`concurrency: 2`，投 3 条重复消息，结果 **3 条全被 `#0-1` 一个线程消费**，
门禁全拦、兜底分支一次没进——看起来"验证通过"，其实**根本没验证到并发路径**。

原因：`spring.rabbitmq.listener.simple.prefetch` 默认 **250**。消息在队列里时，
先连上的消费者可以一次性把 250 条全部预取走，第二个消费者只能干等。
把 `prefetch` 压到 **1**，消息才会被真正分给不同线程。

> 生产含义：`concurrency` 决定"有几个工人"，`prefetch` 决定"每个工人一次能抱走多少活"。
> 压测时把 `prefetch` 调回 10~50，否则吞吐会被 `prefetch=1` 限制成串行速度。

### 6.2 实验环境里的 Redis 挂了，但"看起来一切正常"

实验中途发现 `seckill:stock:10` 变空、Redis 连不上（前一天的 `redis-server` 控制台被关掉了）。
但应用照样启动、MQ 照样消费、订单照样入库。原因有两个，都值得记住：

- `initSeckillStock()` 是 `@PostConstruct` + `try-catch`，**Redis 不可用时只打一行 ERROR，不影响启动**；
- **消费端完全不依赖 Redis**（除了真正的回滚分支），所以 MQ 侧照常工作，只有 DB 在扣。

结论：**DB 是唯一账本，Redis 只是预扣闸门。** 闸门坏了，已经进队列的单照样能落库。

## 七、边界与遗留（分别由第三课、第四课接着修）

| # | 遗留问题 | 影响 |
|---|---|---|
| 1 | 门禁只按 `orderId` 查重，不按 `(userId, voucherId)` | Redis 的 `seckill:user:*` 集合一旦丢失，同一用户能拿到第二个 `orderId` → 门禁放行 → 撞 `uk_uid_vid` → 被 catch 静默吞掉（**消息 ACK，用户查不到单**，只留一条措辞误导的 WARN） |
| 2 | `catch (DataIntegrityViolationException)` 不区分冲突类型 | 主键冲突和业务唯一冲突被当成同一件事，日志误导排查 |
| 3 | 重启不修 `seckill:user:*` | `initSeckillStock()` **只 `set` 库存，不修已抢集合**，"重启修一切"是幻觉，幽灵锁只能手工 `SREM` |
| 4 | 最后一个 catch `throw e` 无重试/无死信 | 毒消息无限重投，拖死消费线程 |

分工是这样的：

- **第 4 条** → 第三课《秒杀 P0 · 03 重试与死信》：本地重试 3 次 + `reject(requeue=false)` → DLX → `seckill.dlq`；
- **第 1–3 条**的共同点是「Redis 和 DB 的偏差没有任何机制去发现」，光靠消费端做不到，
  因为偏差可能早就发生在"消息之外"（重启、flush、人工改数）→ 第四课《秒杀 P0 · 04 死信落库与对账》：
  死信落 `tb_seckill_dead_letter` 留下凭据，`SeckillReconcileTask` 每分钟按 `Redis = DB − P` 收敛四类偏差。

> 04 之后仍有两个"自动收敛不了"的口子，由第五课《秒杀 P0 · 05 死信重放与告警》收口：
> `status=2`（已忽略）后来确认误判、以及"点名先补"需要人发起 → `POST /seckill/ops/dead-letters/{id}/replay`；
> 消费者全挂时对账会永远拒绝修复但没人知道 → `seckill.alert.*` + `SeckillQueueAlertTask`（`ready>0 且 consumers=0` 持续 120 秒告警）。

## 八、附录：复现命令

投一条消息到队列（RabbitMQ 管理台 API，`content_type` 必须是 `application/json`）：

```powershell
$b64 = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes('guest:guest'))
$payload = '{"orderId":700000000000000002,"userId":88888,"voucherId":10}'
$body = @{
  properties = @{ content_type = 'application/json'; delivery_mode = 2 }
  routing_key = 'seckill.queue'
  payload = $payload
  payload_encoding = 'string'
} | ConvertTo-Json -Depth 5 -Compress
Invoke-RestMethod -Uri 'http://127.0.0.1:15672/api/exchanges/%2F/amq.default/publish' `
  -Method Post -Headers @{ Authorization = "Basic $b64" } `
  -ContentType 'application/json' -Body $body
```

> 注意：`redis-cli` 直接传含双引号的 JSON 会被 PowerShell 吞掉引号（存进去变成 `{nickName:regress}` 这种非法 JSON）。
> 需要给 Redis 写 JSON 时改用 stdin：`'{"id":88888}' | redis-cli -a 123321 -x SET key`。

自查 SQL：

```sql
SELECT stock FROM tb_seckill_voucher WHERE voucher_id = 10;
SELECT COUNT(*) FROM tb_voucher_order WHERE voucher_id = 10;
```

## 九、结论

| 问题 | 答案 |
|---|---|
| 判据用什么 | `orderId`（生产端生成 + 随消息传递 + DB 主键） |
| 门禁放哪 | **副作用之前**，扣库存之前 |
| 并发怎么办 | 靠主键/唯一索引，不靠 `select` |
| 冲突了怎么补偿 | 只回补**自己扣掉的 DB 库存**；Redis 预扣只要订单在库里就有效，绝不动 |
| 怎么证明修好了 | 不是"库存对得上"，而是 **Redis stock / 用户集合 / DB stock / 订单数** 四项 + 日志三步对得上号 |
