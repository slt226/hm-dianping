## 1. 环境口径

**必须说明的三点口径**（不写清就等于数据不可信）：

1. **同机压测**：JMeter 与应用抢同一份 CPU，绝对 QPS 偏低于真实部署；本报告只用它做**两组实现的横向对比**，不当作容量结论。
2. **`SeckillReconcileTask` 每 30 秒扫一次表**，报告中的 QPS 含约 **0.033 QPS 底噪**，与压测流量无关。
3. **每组之间都执行了 `db/reset_seckill.ps1`**（MySQL 订单/死信/库存 + Redis stock/已购集合/meta/lock + MQ 队列三处一致），并用 `db/check_invariant.sql` 对账后才开始下一组。

## 2. 工具参数

```powershell
# 重置（库存 100，开 2 小时窗口）
.\db\reset_seckill.ps1 -Stock 100 -Reopen -Hours 2

# 千人登录态：一次写 1000 个 login:token:tk{id}，导出 test/jmeter/users.csv
.\db\gen_tokens.ps1 -Count 1000

# 主链路
jmeter -n -t test/jmeter/seckill.jmx -Jthreads=1000 -Jloops=1 -Jramp=1 `
       -l test/jmeter/result-main-1000.jtl -e -o test/jmeter/report-main-1000

# 对照组（DB 直扣）
jmeter -n -t test/jmeter/seckill.jmx -Jthreads=1000 -Jloops=1 -Jramp=1 `
       -Jtarget=/naive/seckill -l test/jmeter/result-naive-1000.jtl -e -o test/jmeter/report-naive-1000
```

**为什么必须先批量造 token**：Lua 里有 `SISMEMBER seckill:user:{id}`（一人一单）。500 个线程共用一个 token，只有第 1 个能拿到库存，其余 499 个都返回「每人限抢一张」——压出来的是「拒绝得有多快」。所以 CSV 里是 1000 个不同用户，一个请求一个账号。

## 4. 结果

### 4.1 A 组：100 张券被抢（真实秒杀场景）

| ------- | ---- | ---- | --- | ------- | ----- | --- | --- | --- | --- |
| 主链路     | 100  | 100  | 100 | 89.7/s  | 254.7 | 237 | 565 | 569 | 569 |
| 主链路     | 500  | 500  | 100 | 475.7/s | 104.2 | 78  | 278 | 305 | 311 |
| 主链路     | 1000 | 1000 | 100 | 807.1/s | 253.1 | 245 | 448 | 545 | 574 |
| 主链路（复跑） | 1000 | 1000 | 100 | 685.9/s | 316.9 | 309 | 531 | 631 | 730 |
| DB 直扣对照 | 500  | 500  | 100 | 428.4/s | 153.6 | 145 | 408 | 454 | 536 |
| DB 直扣对照 | 1000 | 1000 | 100 | 558.7/s | 645.0 | 630 | 865 | 887 | 898 |

**账目核对（每组结束后立刻执行 `db/check_invariant.sql`）**

| 轮次       | DB 剩余 | 订单数 | 死信（待补偿） | Redis 剩余 | Redis 已购人数 | `stock + orders` | 超卖/少卖 |
| -------- | ----- | --- | ------- | -------- | ---------- | ---------------- | ----- |
| 主链路 100  | 0     | 100 | 0       | 0        | 100        | 100              | 无     |
| 主链路 500  | 0     | 100 | 0       | 0        | 100        | 100              | 无     |
| 主链路 1000 | 0     | 100 | 0       | 0        | 100        | 100              | 无     |
| 对照 500   | 0     | 100 | 0       | —        | —          | 100              | 无     |
| 对照 1000  | 0     | 100 | 0       | —        | —          | 100              | 无     |

> **读这组数据要先排除一个陷阱**：`100 线程` 的 Avg（254ms）比 `500 线程`（104ms）还高，看着反直觉。原因是分母不同 —— 100 线程时 100 个请求**全部成交**，每个都要同步等 MQ 的 publisher-confirm；500/1000 线程时 80%~90% 的请求在 Redis 就被「库存不足」快速拒掉，把均值拉低了。  
> 所以**看均值必须分组**：成交请求看主链路 1000 那行的 P95=448ms，拒掉的那些是 Redis 单次往返级别（<10ms）。

### 4.2 B 组：1000 张券 + 1000 请求全成交（纯写入路径对比）

这一组把「拒绝」这个干扰项去掉（`-Stock 1000`），**1000 个请求全部成交**，两组做的是同一件事，只是写入发生在不同线程。

ramp=3s（避免连接风暴，见第 6 节）：

| 实现              | 请求线程内的 DB 操作        | 吞吐      | Avg       | P50     | P95 | P99 | Max |
| --------------- | ------------------- | ------- | --------- | ------- | --- | --- | --- |
| 主链路（Redis + MQ） | **0 条**             | 314.2/s | **40.1**  | **10**  | 240 | 253 | 256 |
| DB 直扣对照         | 1 UPDATE + 1 INSERT | 322.6/s | **282.1** | **286** | 533 | 719 | 828 |

**SQL 写入量对比**（`SHOW GLOBAL STATUS` 前后差值，MySQL 8.0.36）

| 指标           | 主链路            | DB 直扣对照         |
| ------------ | -------------- | --------------- |
| `Com_insert` | +1000          | +1000           |
| `Com_update` | +1000          | +1000           |
| 写入发生在        | MQ 消费线程（响应已返回） | HTTP 请求线程（同步阻塞） |

> **这是本报告最重要的一条结论，而且和很多人的直觉相反**：  
> Redis 预扣**并没有减少**数据库写入次数——两条链路最终都是 1000 次 UPDATE + 1000 次 INSERT。  
> 它改变的是**写入发生的时机与线程**：主链路的写全在消费线程异步完成，请求线程只做一次 Redis Lua 和一次 MQ 投递。  
> 因此 P50 从 286ms 降到 10ms（**28 倍**），P99 从 719ms 降到 253ms。  
> 换一个说法：秒杀场景里 Redis 挡的不是「写」，是**把用户从"等数据库"变成"等内存"**；真正减少 DB 写的场景是「库存远小于请求量」，那时 90% 的请求在 Redis 就被拒，压根不会产生写。

### 4.3 三档并发的趋势（主链路）

| 线程   | 成交率            | P95 | 说明                     |
| ---- | -------------- | --- | ---------------------- |
| 100  | 100/100 = 100% | 565 | 全部成交，每个请求都要等 broker 确认 |
| 500  | 100/500 = 20%  | 278 | 400 个请求在 Lua 处快速失败     |
| 1000 | 100/1000 = 10% | 448 | 竞争加剧，Lua 抢锁的排队时间开始显现   |

## 5. 结论

1. **正确性优先于吞吐**：五轮压测、跨 100~1000 并发，`stock + orders` 恒等于初始库存、死信恒为 0、Redis 已购人数恒等于订单数。超卖与少卖都没有出现，说明 Lua 的「判库存 + 判重 + 扣减」原子性与消费端的幂等门禁是有效的。
2. **Redis 的价值是"搬运"而不是"消除"**：同样的 DB 写入量，从请求线程搬到了消费线程，P50 从 286ms → 10ms、P99 从 719ms → 253ms。这个措辞比「减少 90% DB 写」更准确，也更禁得起追问。
3. **高并发下的瓶颈不在 Redis，而在同步等待**：`correlationData.getFuture().get(1, SECONDS)` 是同步等 broker 确认，成交请求的 RT 下限就被它钉住；这解释了为什么「成交请求 P95 ≈ 450ms」而「被拒请求 < 10ms」。真要再提吞吐，第一步是把 confirm 改成异步回调，而不是换 Redis 集群。

## 6. 踩坑与偏差记录（写进报告才叫可复现）

| 现象                                                               | 原因                                                                      | 处理                                                                                                                     |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 1000 线程、ramp=1s 的对照组出现 **219 次 `Connection refused`**（21.9% 错误率） | 1000 个 TCP 连接在 1 秒内涌入，Tomcat 默认 `accept-count=100` 的等待队列被打满，多余连接被内核直接拒绝 | 把 ramp 拉到 3s 后错误率归零。**这不是被测系统的错，是压测机的连接风暴**——报告里必须区分「客户端拒绝连接」与「服务端返回 5xx」，前者 `responseCode` 是 `Non HTTP response code` |
| 首轮主链路 P95 明显高于复跑                                                 | 重置删除了 `seckill:meta:10`，第一个请求要回源 DB 重建缓存（缓存击穿的最坏情况）                     | 属预期行为；预热后（第 2 个请求开始）稳定                                                                                                 |
| `stock + orders` 一开始对不上（98 + 5）                                  | 课程种子数据不自洽（5 条历史订单但库存没扣）                                                 | 压测前一律用 `reset_seckill.ps1` 显式指定初始库存，**不反推**                                                                            |
| 200 响应里混着「库存不足」                                                  | 业务失败走 `code=4000` + HTTP 200（见任务 3 的状态码策略）                              | 统计成交率要看 DB 订单数，不能看 JTL 的 success 列——JTL 只反映 HTTP 是否成功                                                                  |

## 7. 复现步骤

```powershell
# 1. 起依赖
docker compose up -d
# 2. 起应用
mvn spring-boot:run
# 3. 造数据 + 造登录态
.\db\reset_seckill.ps1 -Stock 100 -Reopen -Hours 2
.\db\gen_tokens.ps1 -Count 1000
# 4. 压
jmeter -n -t test/jmeter/seckill.jmx -Jthreads=1000 -Jloops=1 -Jramp=3 `
       -l result.jtl -e -o report
# 5. 对账
mysql -t hmdp < db/check_invariant.sql
redis-cli -a *** GET seckill:stock:10
redis-cli -a *** SCARD seckill:user:10
```
