### 1.1 先看清现状（3 条命令，别跳）

```powershell
# ① 基础脚本建了几张表？
(Select-String -Path src\main\resources\db\hmdp.sql -Pattern 'CREATE TABLE' | Measure-Object).Count
```

你会看到 **11 / 12 / 24**（11 + 12 + 死信表 1 = 24）。我这边实测更细一层：
脚本建表语句去重 **24** 张、线上库 **24** 张，`[库里有、脚本没建]` 与 `[脚本建、库里没有]` 两个差集**都是空** ——
**表结构本身没有缺口**，缺的只是"怎么在别人机器上复现这 24 张"。

> ⚠️ **更正**：本步原来的结论是"别人 clone 只跑 `hmdp.sql` 会缺 13 张表，项目起不来"。
> 但你仓库的 `docker-compose.yml` 已经把三份脚本挂到 `docker-entrypoint-initdb.d`（`01/02/03` 固定顺序），
> **这个缺口其实已经被堵上了**（见 Step 3 的更正）。所以 Step 1 剩下的价值只有两条，不大但都该做：
> 1. `upgrade_v2` 不幂等（12 个裸 `CREATE TABLE`），改成 `IF NOT EXISTS` 后能在**已有库**上重复执行；
> 2. README 的"初始化数据库"只提了 `hmdp.sql`，补上另外两份 + "必须 24 张表"的验收数字。
>
> 顺带一个**方法论**（面试可讲）：别用 `Select-String 'CREATE TABLE'` 数表，
> `db/seckill_dead_letter.sql` 的注释里就有这句字串，会多算成 2 张。要用
> `'CREATE TABLE( IF NOT EXISTS)?\s+`?(tb_\w+)`?'` 精确匹配，或者干脆以 `information_schema` 的真值为准。

### 1.2 再看完这两个脚本的"脾气"

```powershell
# 有没有硬编码库名？（有 USE 的话，换库名就挂）
Select-String -Path src\main\resources\db\upgrade_v2_coupon_member_ai.sql,db\seckill_dead_letter.sql -Pattern '^\s*USE '

# 是不是幂等的？（IF NOT EXISTS / INSERT IGNORE 有 0 个 = 重复执行会报表已存在）
(Select-String -Path src\main\resources\db\upgrade_v2_coupon_member_ai.sql -Pattern 'CREATE TABLE IF NOT EXISTS|INSERT IGNORE' | Measure-Object).Count
```

结论（三条，都是我实际跑出来的）：

- 两个脚本都**没有 `USE`** —— 好事，可以指定任意库执行；
- `db\seckill_dead_letter.sql` 已经是 `CREATE TABLE IF NOT EXISTS`，**天然幂等**，不用改；
- `src\main\resources\db\upgrade_v2_coupon_member_ai.sql` **不幂等**（12 个 `CREATE TABLE` 全是裸的），
  重复执行会报 `Table already exists`。

所以只需改 upgrade_v2 一个文件，两条路选一条：

- **省事**：在 README 里写明"只在空库执行一次"；
- **推荐**：让脚本幂等，重复执行不炸。改法（一条命令，改完自己 `git diff` 看一眼）：

```powershell
$p = 'src\main\resources\db\upgrade_v2_coupon_member_ai.sql'
$enc = New-Object Text.UTF8Encoding($false)
$t = [IO.File]::ReadAllText((Resolve-Path $p))
$t = $t -replace 'CREATE TABLE `', 'CREATE TABLE IF NOT EXISTS `'
$t = $t -replace '(?m)^INSERT INTO ', 'INSERT IGNORE INTO '
[IO.File]::WriteAllText((Resolve-Path $p), $t, $enc)
```

> ⚠️ 一个必须知道的前提：`INSERT IGNORE` **只在目标表有唯一键时才真的防重复**。
> 如果种子数据没有唯一索引，第二次执行会**插入重复的券模板/知识库**。
> 所以最稳的说法是：**结构（`CREATE TABLE`）幂等，种子数据只在空库执行一次**——
> 把这句话写进 README 的注释里，比假装全幂等更专业。

## Step 2 · 配置外置（✅ 已完成，10 分钟确认）

> **状态：这项你已经做完了。** `application.yaml` 里 DB / Redis / RabbitMQ / 上传目录**全部**是 `${ENV:默认值}`，
> 而且默认值保留了"本机不设环境变量也能 `mvn spring-boot:run`"的体验 —— 这正是这道题的标准答法，**别再改**。
>
> 唯一要你做取舍的地方：默认值里仍是 `root` / `123321` 这种真实口令。
> 严格的说法是"仓库里不该出现可用口令"，工程的说法是"本地开发默认值很常见，生产靠注入"。
> 建议**保留默认值**，但在 README 补一句："默认值仅用于本地开发，生产请用环境变量覆盖"。
> 面试被追问就这么答：`${ENV:default}` 里的默认值是**开发体验**，不是密钥管理；
> 生产要么 K8s Secret、要么配置中心，口令一律由环境注入。

**你现在的样子**（下面就是当前 yaml，对照一下即可，不需要动手）：

```yaml
  datasource:
    url: ${DB_URL:jdbc:mysql://127.0.0.1:3306/hmdp?useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&characterEncoding=utf8&useUnicode=true}
    username: ${DB_USER:root}
    password: ${DB_PASSWORD:root}
  redis:
    host: ${REDIS_HOST:127.0.0.1}
```

**为什么用 `${ENV:默认值}` 而不是直接删掉**：默认值保证你本机不设环境变量也能起，
公司/CI 里靠环境变量覆盖同一个 jar，**一份配置到处跑**——这正是面试里"配置外置"的标准答法。

## Step 3 · docker-compose：**验证**而不是重写（30 分钟）

**目标**：说清"新机器怎么起来"，并亲手验证一次。

> ⚠️ **重要更正**：这一步原来写的是"新建 `docker-compose.yml`"。但你仓库里**早就有了**，而且比这里的极简版强得多：
> 5 个服务（MySQL / Redis / RabbitMQ / backend / frontend）、每个都带 `healthcheck`、
> `depends_on: condition: service_healthy` 保证后端不抢跑、宿主机端口全部错开本机已装的服务
> （3307 / 6380 / 5673 / 8082 / 8080）。**不要推倒重写**，本步只做"验证 + 补两句说明"。

**它为什么已经解决了 Step 1 的核心问题** —— 看这三行挂载：

```yaml
volumes:
  - ./src/main/resources/db/hmdp.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
  - ./src/main/resources/db/upgrade_v2_coupon_member_ai.sql:/docker-entrypoint-initdb.d/02-upgrade.sql:ro
  - ./db/seckill_dead_letter.sql:/docker-entrypoint-initdb.d/03-deadletter.sql:ro
```

这三行有三个可以拿去面试讲的事实：

1. 官方 mysql 镜像按**文件名字母序**执行 `docker-entrypoint-initdb.d` 下的脚本，改名成 `01/02/03` 就把顺序锁死了；
2. **挂载而不是复制** —— 脚本仍然只有仓库里那一份真实来源，不会出现"两份 SQL 不一致"；
3. 只在 **volume 为空**时执行 —— 想重跑必须 `down -v`，这正是新人最常问的"我改了 SQL 怎么没生效"。

### 3.1 从零验证一次（唯一能证明"可复现"的动作）

```powershell
docker compose down -v        # 关键：带 -v 删 volume，否则初始化脚本不会再跑
docker compose up -d --build
docker compose ps             # 等 mysql / redis / rabbitmq 全部 healthy
```

### 3.2 三个真会踩的坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 只 `down` 没 `-v` | 改了 SQL 完全不生效 | `docker compose down -v`，然后再 `up` |
| 前端 `context: ../hmdp-web` 在仓库外 | 别人只 clone 后端就 `--build` 失败：`path ../hmdp-web not found` | 给 `frontend` 加 `profiles: ["full"]`，默认不构建；或在 README 写明"只跑后端：`docker compose up -d mysql redis rabbitmq`" |
| 本机 3306/6379/5672 已被占用 | `port is already allocated` | 你已经错开成 3307/6380/5673；换机器时记得同步改 `DB_URL` 的端口 |

**✅ 验收**（三条都要给数字/状态，别只说"起来了"）：

```powershell

docker exec hmdp-mysql mysql -uroot -proot -N -e "select count(*) from information_schema.tables where table_schema='hmdp'"   # 必须输出 24
```

### 4.1 先确认问题存在（读代码，别听我说）

### 4.4 新增缓存组件（`src/main/java/com/hmdp/service/SeckillMetaCache.java`）

```java
package com.hmdp.service;

import com.hmdp.dto.SeckillMetaVO;
import com.hmdp.entity.SeckillVoucher;
import com.hmdp.utils.RedisConstants;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import javax.annotation.Resource;
import java.time.Instant;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.TimeUnit;

/**
 * 秒杀券元数据缓存：把"每请求一次 getById"变成"30 秒一次"。
 * <p>
 * 只缓存时间窗，不缓存库存 —— 库存的唯一出口是 Redis 预扣（seckill.lua），
 * 缓存里多存一份库存只会多一个不一致来源。
 */
@Slf4j
@Component
public class SeckillMetaCache {

    private static final String F_BEGIN = "begin";
    private static final String F_END = "end";
    /** 空值标记：防"查不存在的券"把 DB 打穿 */
    private static final String NULL_MARK = "-1";

    @Resource
    private StringRedisTemplate stringRedisTemplate;
    @Resource
    private ISeckillVoucherService seckillVoucherService;

    /** @return null 表示券不存在 */
    public SeckillMetaVO get(Long voucherId) {
        String key = RedisConstants.SECKILL_META_KEY + voucherId;
        Map<Object, Object> cache = stringRedisTemplate.opsForHash().entries(key);
        if (!cache.isEmpty()) {
            String begin = (String) cache.get(F_BEGIN);
            if (NULL_MARK.equals(begin)) {
                return null;                      // 命中空值缓存：券确实不存在
            }
            return new SeckillMetaVO(voucherId, toTime(begin), toTime((String) cache.get(F_END)));
        }
        SeckillVoucher sv = seckillVoucherService.getById(voucherId);
        Map<String, String> toSave = new HashMap<>(4);
        if (sv == null) {
            toSave.put(F_BEGIN, NULL_MARK);
            stringRedisTemplate.opsForHash().putAll(key, toSave);
            stringRedisTemplate.expire(key, RedisConstants.CACHE_NULL_TTL, TimeUnit.MINUTES);
            return null;
        }
        toSave.put(F_BEGIN, toEpoch(sv.getBeginTime()));
        toSave.put(F_END, toEpoch(sv.getEndTime()));
        stringRedisTemplate.opsForHash().putAll(key, toSave);
        stringRedisTemplate.expire(key, RedisConstants.SECKILL_META_TTL, TimeUnit.SECONDS);
        return new SeckillMetaVO(voucherId, sv.getBeginTime(), sv.getEndTime());
    }

    /** 建券/改时间窗后调用，别干等 TTL 到期 */
    public void evict(Long voucherId) {
        stringRedisTemplate.delete(RedisConstants.SECKILL_META_KEY + voucherId);
    }

    private static String toEpoch(LocalDateTime t) {
        return t == null ? NULL_MARK
                : String.valueOf(t.atZone(ZoneId.systemDefault()).toInstant().toEpochMilli());
    }

    private static LocalDateTime toTime(String epochMillis) {
        if (epochMillis == null || NULL_MARK.equals(epochMillis)) {
            return null;
        }
        return LocalDateTime.ofInstant(Instant.ofEpochMilli(Long.parseLong(epochMillis)), ZoneId.systemDefault());
    }
}
```

### 6.3 挂错误码到**已有的**异常体系（关键：不要新建第二套）

先看清你手上已经有什么——`git ls-files` 能查到的这三个文件是**早就写好并带注释的**，Step 6 是「增强」而不是「新建」：

| 文件 | 现状职责 |
| --- | --- |
| `src/main/java/com/hmdp/exception/BizException.java` | 可预期失败的载体，**目前只有 message，没有错误码** |
| `src/main/java/com/hmdp/config/BizExceptionAdvice.java` | `BizException` → warn + `Result.fail(msg)`；`DuplicateKeyException` → 「请勿重复提交」 |
| `src/main/java/com/hmdp/config/WebExceptionAdvice.java` | `RuntimeException` 兜底 → error + 「服务器异常」 |

> ❌ **不要**再新建 `BusinessException` / `GlobalExceptionHandler`。
> 一旦出现第三个 `@RestControllerAdvice` 且也声明 `@ExceptionHandler(Exception.class)`，同一个异常就有两个候选处理器，
> 你的「BusinessException → 4100」很可能被「Exception → 5000」或 `WebExceptionAdvice` 抢走，排查起来极其浪费时间。
> 正确做法：**给 `BizException` 加码，把校验异常并进 `BizExceptionAdvice`**。这也是 `docs/实习冲刺-补强路线图.md` 里写的方案。

**① `BizException` 加 `errorCode`，老构造器保留**（现有 `throw new BizException("...")` 一行都不用改）：

```java

import com.hmdp.dto.ErrorCode;
import lombok.Getter;

@Getter
public class BizException extends RuntimeException {
```

**② 在 `BizExceptionAdvice` 里补三件事**（原有注释和 `DuplicateKeyException` 分支全部保留，只改 `handleBizException` 一行 + 追加三个方法）：

```java
// src/main/java/com/hmdp/config/BizExceptionAdvice.java —— 需要新增的 import
import com.hmdp.dto.ErrorCode;
import org.springframework.validation.BindException;
import org.springframework.validation.BindingResult;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import javax.validation.ConstraintViolationException;
```

```java
    // 改：原来只打 message，现在把 code 一起打出来，日志里能直接 grep 4204
    @ExceptionHandler(BizException.class)
    public Result handleBizException(BizException e) {
        log.warn("业务异常：code={}, msg={}", e.getErrorCode().getCode(), e.getMessage());
        return Result.fail(e.getErrorCode(), e.getMessage());
    }

    /** @RequestBody + @Valid 校验失败 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
        return failFirst(e.getBindingResult());
    }

    /** 表单 / 查询参数绑定失败 */
    @ExceptionHandler(BindException.class)
    public Result handleBind(BindException e) {
        return failFirst(e.getBindingResult());
    }

    /** 类上 @Validated 时，方法参数上的 @Min/@NotBlank 失败 */
    @ExceptionHandler(ConstraintViolationException.class)
    public Result handleConstraint(ConstraintViolationException e) {
        log.warn("参数校验失败：{}", e.getMessage());
        return Result.fail(ErrorCode.PARAM_INVALID);
    }

    private Result failFirst(BindingResult br) {
        FieldError fe = br.getFieldError();
        String detail = fe == null
                ? ErrorCode.PARAM_INVALID.getMsg()
                : fe.getField() + " " + fe.getDefaultMessage();
        log.warn("参数校验失败：{}", detail);
        return Result.fail(ErrorCode.PARAM_INVALID, detail);
    }
```

> ⚠️ **两个实测过的版本坑**（我在这套依赖上真编译过，EXIT=0）：
> 1. Spring Boot 2.3 带的是 Spring 5.2，`MethodArgumentNotValidException` **还没有**继承 `BindException`。
>    所以网上那种「一个 handler 同时 `@ExceptionHandler({MethodArgumentNotValidException.class, BindException.class})`、
>    参数写 `BindException`」的写法**在本项目直接编译不过**，必须拆成两个方法（如上）。
> 2. `WebExceptionAdvice` 里已经兜了 `RuntimeException`，**不要再给它加 `Exception` 分支**，也不要新建第三方 advice。
>
> 这两条本身就是面试素材：说明你真读过依赖版本和已有的 advice 分工，而不是照抄博客。

**③ 为什么 `BizException` 仍然打 warn、`WebExceptionAdvice` 打 error？**
这是你原有设计里最有价值的一段注释：业务失败一天几千次是常态，打 error 会把真正需要告警的 NPE 淹掉。
面试时可以直接讲这个分级取舍。

### 7.2 traceId 过滤器（`src/main/java/com/hmdp/utils/TraceIdFilter.java`）

```java
package com.hmdp.utils;

import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import javax.servlet.FilterChain;
import javax.servlet.ServletException;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.UUID;

/** 每个请求一个 traceId，写进 MDC；日志 pattern 里 %X{traceId} 即可串起整条链路 */
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID = "traceId";
    public static final String HEADER = "X-Trace-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp, FilterChain chain)
            throws ServletException, IOException {
        String traceId = req.getHeader(HEADER);
        if (traceId == null || traceId.isEmpty()) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }
        MDC.put(TRACE_ID, traceId);
        resp.setHeader(HEADER, traceId);          // 回给前端，用户报障时直接发这串
        try {
            chain.doFilter(req, resp);
        } finally {
            MDC.remove(TRACE_ID);                 // Tomcat 线程复用，不清会串号
        }
    }
}
```

`application.yaml` 里改日志格式：

```yaml
logging:
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [%X{traceId:-}] %logger{36} - %msg%n"
```

**注意**：`VoucherOrderConsumer` 里面的**异步线程**不会自动继承 MDC。
讲这一层就够加分了：MQ 消费端要么从消息头取 traceId 手动 `MDC.put`，要么接受"消费链路单独 traceId"。

### 8.3 写法（模板照这个来，类名/方法名换成你实际的）

```java
@ExtendWith(MockitoExtension.class)
class SeckillDeadLetterServiceTest {

    @Mock private SeckillDeadLetterMapper deadLetterMapper;
    @Mock private StringRedisTemplate stringRedisTemplate;
    @Mock private ValueOperations<String, String> valueOps;
    @InjectMocks private SeckillDeadLetterServiceImpl service;   // 字段注入用 @InjectMocks 即可

    @Test
    @DisplayName("已补偿过的死信重放：不再扣减/回补库存，只返回幂等成功")
    void replay_whenAlreadyDone_isIdempotent() {
        // given：doneKey 已存在
        given(stringRedisTemplate.opsForValue()).willReturn(valueOps);
        given(valueOps.get(RedisConstants.SECKILL_DLQ_DONE_KEY + 1L)).willReturn("1");

        // when
        boolean ok = service.replay(1L);

        // then
        assertTrue(ok);
        verify(deadLetterMapper, never()).updateById(any());   // 一行 update 都不许有
    }
}
```
