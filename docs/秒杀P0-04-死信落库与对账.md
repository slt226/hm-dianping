# 秒杀 P0 · 04 死信只进日志、坏账无人收敛 · 复盘

> 第四课。一句话：**死信只写日志等于没有死信，坏账只靠人眼等于永远有坏账。**
> 这一课做两件事：把死信**落库**（让"未补偿的预扣"这个不可见量 P 变得可计算），
> 再加一个**每分钟对账**任务，把 Redis 闸门和 DB 账本的四类偏差自动拉回一致。
>
> 上一课（03 重试与死信）解决的是「失败消息不要无限重投、彻底失败后别再乱回补」；
> 这一课解决的是「彻底失败之后，凭据存哪、谁来补、补不掉怎么办」以及
> 「没人报错的那些悄悄发生的坏账，谁负责发现」。
> 所有数字都是本机实测（8081 / MySQL 3306 / Redis 6379 / RabbitMQ 15672）。

---

## 一、一句话概括

第三课结束时，系统的状态是：

1. 毒消息被 `reject(requeue=false)` 送进 `seckill.dlq`，死信消费者回补 Redis，**然后只留下一行 ERROR 日志**；
2. 日志里没有 `payload`、没有状态，**换台机器、日志一滚（或按天归档）就再也没人知道这张券少卖了一张**；
3. 回补失败（Redis 抖动 / DB 抖动）时，代码 `catch` 一下就结束了 —— **这一张库存永久蒸发**，没有任何人会重试；
4. Redis 闸门与 DB 账本之间的偏差（超卖 / 少卖 / 集合缺人 / 集合幽灵）**只能靠人肉发现**，
   `initSeckillStock()` 重启时只 `SET` 库存，**不修已抢集合**（02 课第 5.4 节已记录），"重启修一切"是幻觉。

修复后：

| | 修前（03 结束） | 修后（04） |
|---|---|---|
| 死信凭据 | 一行 ERROR 日志 | **`tb_seckill_dead_letter` 一行**（orderId / userId / voucherId / payload / reason / 状态机） |
| 重复进死信 | 可能重复回补 | `uk_order_id` + 状态机 → **只补一次** |
| 补偿失败 | 永久丢失（只留日志） | `status=0` + 每分钟 `settlePending` **重试到成功为止** |
| Redis > DB（A 类超卖） | 无收敛机制 | 每分钟 CAS **压回** DB |
| Redis < DB（B 类少卖） | 无收敛机制 | 每分钟 CAS **抬回** DB |
| Redis 集合缺人（C 类） | 该用户可重复抢 → 撞 `uk_uid_vid` → 静默失败 | 每分钟 **SADD** 补齐 |
| Redis 集合多幽灵（D 类） | 该账号被永久"已抢" | 每分钟 **SREM** 清理 |
| 重启能否自愈 | 不能（只设库存） | **能**（库存 + 集合都由对账负责） |
| 是否有人工入口 | 无 | 表里能查、能按 `reason` 分类、`retry_count` 支持重放 |

## 三、地基：账本不变式（先把它写下来，代码才有对错标准）

```
DB_stock    = S0 - 已落库订单数
Redis_stock = S0 - 已落库订单数 - 在途预扣数 P
⇒  Redis_stock = DB_stock - P ，且 P ≥ 0
```

`P` 的构成（这就是"死信必须落库"的真正原因）：

```
P = 主队列 ready + 主队列 unacked（正在被消费、还没 ack）
  + 死信队列 ready + 死信队列 unacked
  + 待补偿死信数（已 reject 出队、但 Redis 还没回补）
```

**推论一**：`Redis > DB` ⇒ `P < 0` ⇒ **一定是坏账**（不可能存在负的在途），对账可以无条件压回。
**推论二**：`Redis < DB` **可能只是有在途**，盲目抬到 DB 会**多卖 P 张**。
所以"少卖"方向的修复必须比"超卖"方向更保守 —— 这正是下面四条防护存在的理由。

### 3.1 四类坏账

| 类型 | 现象 | 检测条件 | 修法 | 风险 |
|---|---|---|---|---|
| **A 超卖** | 闸门虚高，卖出 DB 没有的货 | `Redis_stock > DB_stock` | CAS 压回 `DB_stock` | 修错 = 回滚真实扣减 |
| **B 少卖** | 明明有货却提示售罄 | `Redis_stock < DB_stock - P` | CAS 抬到 `DB_stock - P`（P=0 时即 DB） | 修错 = 多卖 P 张 |
| **C 集合缺人** | 已下单用户还能再抢 → 撞 `uk_uid_vid` → 消息 ACK 但用户查不到单 | `DB_users - Redis_users ≠ ∅` | `SADD` 缺失者 | 修错 = 用户被误锁（可再修回来） |
| **D 集合幽灵** | 没下单的人永远"已抢" | `Redis_users - DB_users ≠ ∅` | `SREM` 多余者 | 修错 = 同一人可抢两张（DB 唯一键兜底） |

> A/B 与 C/D 是**两个独立维度**：集合里多一个人不代表库存错了，库存对也不代表集合对。
> 所以 `reconcileOne` 里两个方法都要跑，任一有动作就算"本轮修正了这张券"。

## 四、死信落库：先有凭据，才谈得上补偿

### 4.1 表设计（`db/seckill_dead_letter.sql`）

```sql
CREATE TABLE IF NOT EXISTS tb_seckill_dead_letter (
  id             bigint      NOT NULL AUTO_INCREMENT COMMENT '主键',
  order_id       bigint      NOT NULL COMMENT '业务订单号（消息里的 orderId）',
  user_id        bigint      NOT NULL COMMENT '下单用户id',
  voucher_id     bigint      NOT NULL COMMENT '秒杀券id',
  payload        varchar(512)         DEFAULT NULL COMMENT '原始消息 JSON，便于人工还原与重放',
  reason         varchar(255)         DEFAULT NULL COMMENT '失败原因摘要（x-death 或异常信息）',
  status         tinyint     NOT NULL DEFAULT '0' COMMENT '0待补偿 1已补偿 2已忽略(误判死信)',
  retry_count    int         NOT NULL DEFAULT '0' COMMENT '人工重放次数（自动对账不增加）',
  compensate_time timestamp           DEFAULT NULL COMMENT '补偿完成时间',
  create_time    timestamp   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time    timestamp   NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_id (order_id),
  KEY idx_status_create (status, create_time),
  KEY idx_voucher_status (voucher_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='秒杀死信记录表';
```

三个索引各有用处，缺一个都会在真实规模上出事：

| 索引 | 服务的查询 | 不加会怎样 |
|---|---|---|
| `uk_order_id` | 重复死信去重（`DuplicateKey` 即"已存在"） | 至少一次投递 ⇒ 同一条订单落两行 ⇒ **补偿两次 ⇒ 库存 +2** |
| `idx_status_create` | `settlePending`：`where status=0 and create_time<? order by create_time limit 200` | 每分钟全表扫，死信一多就把对账线程拖死 |
| `idx_voucher_status` | 对账门禁：`count(status=0 and voucher_id=?)` | 每分钟按券扫全表，`P` 算不准 ⇒ 门禁失效 |

`compensate_time` 单独一列，**不能复用 `update_time`**：`update_time` 会被任何一次 UPDATE（包括状态回写、人工改备注）改写，到时候说不清"到底哪一刻补的"。

脚本还条件补了 `tb_voucher_order.idx_voucher_id`：对账每分钟按券查用户列表（`select user_id from tb_voucher_order where voucher_id=?`），
没这个索引就是每分钟一次全表扫描。用 `information_schema` 判断后再建，**可重复执行**（MySQL 8 没有 `ADD INDEX IF NOT EXISTS`）：

```sql
SET @exist := (SELECT COUNT(*)
                 FROM information_schema.statistics
                WHERE table_schema = DATABASE()
                  AND table_name   = 'tb_voucher_order'
                  AND index_name   = 'idx_voucher_id');
SET @ddl := IF(@exist = 0,
    'ALTER TABLE tb_voucher_order ADD INDEX idx_voucher_id (voucher_id)',
    'SELECT ''idx_voucher_id already exists'' AS msg');
PREPARE stmt FROM @ddl; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

### 4.2 三条铁律（`SeckillDeadLetterServiceImpl.handle`）

```java
// ① 凭据优先：先落库，再补偿；落库失败也照旧补偿
try { deadLetterMapper.insert(record); stored = record; }
catch (DuplicateKeyException dup) {           // ② 唯一键 = 去重开关
    stored = deadLetterMapper.selectOne(...eq("order_id", orderId));
    if (stored != null && stored.getStatus() != STATUS_PENDING) {
        log.warn("【死信】该订单此前已处理，本次仅告警不重复回补 | orderId={}, status={}", ...);
        return;                               // 已经补过 → 只告警
    }
} catch (Exception e) {
    log.error("【死信】落库失败，仍先执行库存补偿（宁可少凭据，不可少卖）| ...");
}
// ③ 绝不重复回补：误判校验 + SETNX 抢执行权
if (voucherOrderMapper.selectById(orderId) != null) {                 // DB 有单 ⇒ 不是坏账
    markStatus(record, SeckillDeadLetter.STATUS_IGNORED, "订单已落库，误判死信，未回补");
    return false;
}
Boolean first = redis.opsForValue()
        .setIfAbsent(DONE_KEY + orderId, "1", 168, TimeUnit.HOURS);    // 抢执行权
if (!Boolean.TRUE.equals(first)) {                                    // 补过 → 只对齐状态，不动库存
    markStatus(record, SeckillDeadLetter.STATUS_COMPENSATED, null);
    return false;
}
```

三条铁律分别对应三种事故：

1. **凭据优先**：`insert` 失败（表还没建、DB 抖动）时若直接 `return`，库存就永久少一张 —— **少一条记录只是少证据，少一张库存是真的少卖**。
2. **唯一键去重**：消息是"至少一次"投递，同一条死信可能被投多次；用 `uk_order_id` 把去重交给 DB，比在应用里判断并发安全得多。
3. **SETNX 抢执行权**：`selectById` 过门禁后、`INCR` 之前仍有一个窗口，两个线程可能同时进（死信消费者 + 对账任务）。`SETNX` 是这条兜底的最后一道锁。

`DONE_KEY` 的 TTL 是 **168 小时（7 天）** 而不是 24 小时：这个 key 是"已经补过"的唯一证据，
TTL 一到而记录又还停在 `status=0`（比如状态回写失败），重试就会**再补一次**，库存凭空 +1。
7 天远大于"DB 连续不可用"的合理窗口，留足人工介入时间。

补偿失败时**删掉 doneKey 并保持 `status=0`**，让下一轮对账还能再试：

```java
catch (Exception e) {
    releaseDoneKey(doneKey);
    log.error("【死信】回补 Redis 失败，保持待补偿 | orderId={}", orderId, e);
    return false;                 // status 不动 ⇒ 下一分钟 settlePending 会重来
}
```

本类**不加 `@Transactional`**：补偿只有 Redis 写、没有 DB 写，事务既保护不了 Redis，
还会把"已改 Redis、DB 回滚"变成一条新的不一致。

### 4.3 消费者只做翻译（`SeckillDeadLetterConsumer`）

```java
@RabbitListener(queues = "seckill.dlq")
public void handleDeadLetter(SeckillOrderMessage msg, Message rawMessage) {
    String reason = describe(rawMessage.getMessageProperties());   // 从 x-death 提炼死因
    log.error("【死信告警】秒杀订单重试耗尽，进入死信队列 | orderId={}, ..., {}", ..., reason);
    String payload = new String(rawMessage.getBody(), StandardCharsets.UTF_8);  // 原文，不重新序列化
    deadLetterService.handle(msg, payload, reason);
}
```

两个细节：

- **payload 用原始字节**：Jackson 反序列化会丢未知字段和格式细节，将来人工重放必须投"原样报文"；
- **死因取 `x-death`**：消息被 `reject` 之后异常对象已随线程消失，broker 能带进死信队列的只有 `x-death`（`reason` / `count` / `queue` / `time`）。

## 五、对账任务：四条防护，缺一条就会由"修复者"变成"破坏者"

### 5.1 防护清单与它们各自防的是哪一次事故

| # | 防护 | 代码 | 不加会怎样 |
|---|---|---|---|
| ① | **在途门禁** | 主队列 / 死信队列 `ready>0`、或该券 `status=0` 死信 `>0` ⇒ 本轮跳过 | 把"消费者正拿在手里还没 ack"的消息当成丢单，把库存抬回去 ⇒ **多卖** |
| ② | **两轮确认** | `quietRounds` 连续两轮安静才动手，第一轮只观察 | `queueDeclarePassive` **只报 ready、不报 unacked**，单轮 0 不能证明 P=0 |
| ③ | **CAS 写入** | Lua：`if GET==我读到的原值 then SET` | "读-比-写"之间被人扣走一张，`SET` 会把这次**真实扣减抹掉** ⇒ 脚本亲手制造超卖 |
| ④ | **多实例互斥** | `SETNX seckill:reconcile:lock:{id}` + TTL 120s + token 解锁 | 两个实例同时修，A 读到 98 写 98，B 读到 97 写 98 ⇒ 又把 A 的动作抹掉 |

关于 ②：为什么"1 分钟一轮 × 两轮"就够？消费端的重试窗口是 **1s + 2s ≈ 3 秒**（03 课配的 `max-attempts: 3`），
死信消费者也是瞬时处理。3 秒 ≪ 60 秒，所以只要**连续两个整分**都没动静，就可以认为没有在途了。
反过来，如果把扫描间隔调到 1 秒再配两轮确认，门禁就会被"消费端正常处理耗时"反复骗过。

关于 ③，**必须拿 Redis 原串比较，不能拿 `parseInt` 后的结果**：

```java
String redisRaw = redis.opsForValue().get(stockKey);        // "098" 也可能是 "098"
Integer.parseInt(redisRaw.trim());                           // → 98
redis.execute(CAS, keys, redisRaw, String.valueOf(dbStock)); // 拿原串比较，"098" 永远不匹配
```

真出事的时候，`Redis > DB` 是最危险的方向：闸门虚高意味着"DB 已经没有货了，Redis 还让人扣"，
每一次扣减都会在 `insert` 时撞库存 CAS 失败（DB `stock>0` 不成立）→ 变成死信 → 用户端表现为"抢到了但没订单"。
**这个方向的修复必须是无条件、最快速度的**；`Redis < DB` 则要更谨慎（可能就是有在途）。

### 5.2 一轮的执行顺序

```java
@Scheduled(cron = "0 */1 * * * ?")            // 整分触发：日志时间戳对齐，便于按分钟 grep
public void scheduledReconcile() {
    try { reconcileAll(); }
    catch (Exception e) { log.error("【对账】本轮整体失败（不影响下一轮）", e); }
}

reconcileAll()
  ├─ ① deadLetterService.settlePending(200)        // 先把"补偿失败的死信"再补一次
  └─ ② for each 券 (begin_time<=now, end_time>=now-24h)
        └─ reconcileOne(voucherId)
             ├─ 门禁：mainReady / dlqReady / pendingDeadLetter
             ├─ 两轮确认：quietRounds
             ├─ Redis 锁（120s，token 解锁）
             ├─ reconcileStock()   // CAS 压/抬到 DB
             └─ reconcileUsers()   // SADD 缺失 / SREM 幽灵
```

顺序很重要：**先自愈死信，再对账**。因为待补偿死信本身就是 `P` 的一部分，
若先对账，门禁会一直因为"还有一条没补的死信"而拒绝修库存 —— 而那条死信之所以没补，可能正是因为 Redis 抖动。
先补它，`P` 才会归零，门禁才会放行。

只扫 `begin_time <= now` 的券：未开始的券 Redis 值就应该等于 DB 值，扫了纯属浪费；
结束超过 24 小时的券没人买了，改数字没有意义（留给归档）。

### 6.3 死信真实链路（毒消息 → 落库 → 补偿失败 → 对账兜底）

造毒消息的办法：把 `tb_voucher_order` 临时 rename 走 12 秒（消费端每次 insert 都会 `BadSqlGrammar`），
同时按正常下单的样子先把 Redis 预扣掉，再投一条合法报文。

```
16:11:35  RENAMED / DECR=97 / SADD=1 / PUBLISHED {"routed":true}
16:11:38  【死信告警】...orderId=888001, userId=1005, voucherId=10, 重试耗尽 reason=rejected, count=1, queue=seckill.queue
16:11:39  【死信】同一订单重复进入死信，复用已有记录 | orderId=888001, id=4
16:11:41  （第三次投递，同上）
16:11:46  RESTORED / STOCK=97        ← 补偿没成功，库存还是 97
16:12:00  【对账】存在在途，本轮跳过 | pendingDeadLetter=1
16:13:00  【死信】已回补 Redis 预扣 | orderId=888001, voucherId=10, userId=1005
16:13:00  【死信】待补偿清单重试完成 | 本次成功 1/1
16:13:00  【对账】本轮汇总 | 待补偿死信成功 1 条，修正券 0 / 1
```

表里的最终记录（补偿成功后 `status=1`）：

```sql
mysql> select order_id,user_id,voucher_id,status,retry_count,compensate_time,reason,payload
    -> from tb_seckill_dead_letter where order_id=888001\G
   order_id: 888001
     status: 1
retry_count: 0
compensate_time: 2026-11-07 16:13:00
     reason: 重试耗尽 reason=rejected, count=1, queue=seckill.queue
    payload: {"orderId":888001,"userId":1005,"voucherId":10}
```

这一条链路把三个设计点全都验证了：

1. **死信只落一行**：同一条消息被 DLQ 监听器投递了 3 次（`16:11:38 / 39 / 41`），
   `uk_order_id` 让第 2、3 次走 `DuplicateKey` 分支，日志明确写着"复用已有记录"；
2. **补偿失败不会误标已补偿**：DLQ 监听器当时也在查 `tb_voucher_order`（`selectById` 误判校验），
   表被 rename 走了 ⇒ 校验抛异常 ⇒ `catch` 里删掉 doneKey、`status` 保持 0 ⇒ 16:12 的门禁因此拒绝修库存；
3. **对账兜底**：16:13 `settlePending` 成功补上 → `status=1` + `compensate_time`，Redis 97 → **98**，`SREM 1005`。

顺带也证明了对账**不会误伤正常下单**：16:12 那一刻 `Redis 97 < DB 98`，
如果对账只看"数字不等就抬"，它会把这次真实预扣抹掉 → 多卖 1 张；
实际它因为 `pendingDeadLetter=1` 直接跳过，`修正券 0 / 1`。

### 6.4 验收判据（10/10）

| # | 判据 | 期望 | 实测 |
|---|---|---|---|
| 1 | 表与唯一键 | `uk_order_id` 生效 | `ERROR 1062 ... uk_order_id` ✅ |
| 2 | A 类（闸门虚高） | 压回 DB | `109 -> 98` ✅ |
| 3 | B 类（闸门偏低） | 抬回 DB | `80 -> 98` ✅ |
| 4 | C 类（集合缺人） | `SADD` 补齐 | `补回 3 人` / `补回 5 人` ✅ |
| 5 | D 类（集合幽灵） | `SREM` 清理 | `清理 1 个幽灵用户` ✅ |
| 6 | 在途门禁 | 有在途不修 | `存在在途，本轮跳过` ✅ |
| 7 | 两轮确认 | 首轮只观察 | `安静窗口第 1 轮（仅观察）` ✅ |
| 8 | 大集合熔断 | 超限跳过 | `size=5005, limit=5000` ✅ |
| 9 | 死信落库 + 去重 | 一条消息一行 | 3 次投递只 1 行 `id=4` ✅ |
| 10 | 死信补偿可重试 | 失败留存 → 成功置 1 | `status=0 → 1` + `compensate_time` ✅ |

额外一项（不算判据，但要看）：**稳定态业务零写入**。用 `INFO commandstats` 取相邻两轮的增量：

| 命令 | 16:38 修复轮后 | 16:39 下一轮后 | 增量 |
|---|---|---|---|
| `incr`（回补库存） | 2 | 2 | **0** |
| `sadd`（补回已抢） | 13 | 13 | **0** |
| `srem`（清幽灵） | 8 | 8 | **0** |
| `set`（含抢锁 `SET NX`） | 87 | 88 | +1 |
| `evalsha`（解锁脚本） | 45 | 46 | +1 |

结论要说准：**业务数据零写入**，但每轮固定付"抢锁 1 次 + 解锁 1 次"的开销。
日志侧对应地只有一条 `SELECT user_id`，没有 `库存已修正`、没有 `补回`、没有 `清理` ——
这说明系统处在**收敛态**而不是**震荡态**（震荡的典型表现是每轮都 `A→B→A` 地来回改，把 AOF 和从库都拖垮）。

## 七、踩过的坑

### 7.1 死信消费者自己也有重试，一条死信会被处理 3 次

第一眼看到 `【死信告警】` 在同一秒出现三遍会以为哪里写错了。其实是**同一条 MQ 消息被 DLQ 监听器消费了 3 次**
（`16:11:38 / 39 / 41`，间隔正好是 03 课配的 `1s → 2s`）—— 因为这次监听器内部也抛了异常（查订单表校验时表被 rename 走了）。

`spring.rabbitmq.listener.simple.retry` 是**全局**配置，主队列和死信队列都会套用。
所以死信处理逻辑必须自己也幂等 —— 这就是 `uk_order_id` + `status` 状态机 + `SETNX` 存在的原因，
少一层都会出现"补偿 3 次 = 库存 +3"。

### 7.2 `SMEMBERS` 是"内存炸弹"，全量差集必须设上限

5005 个 member 看着不多，但热门券十万级时一次 `SMEMBERS` 就是上百 MB 的瞬时堆分配，
对账线程（`@EnableScheduling` 只有 1 个线程）一旦 OOM，**所有券都不再收敛**。
`USER_SET_DIFF_LIMIT = 5000` 的取舍是明确的：**漏修不会超卖**（DB 的 `uk_uid_vid` 是最后一道闸），
但把对账任务自己搞崩会造成全局失效。

### 7.3 定时任务必须自己兜异常

```java
try { reconcileAll(); } catch (Exception e) { log.error("【对账】本轮整体失败（不影响下一轮）", e); }
```

`@Scheduled` 方法抛出的异常会被 `ThreadPoolTaskScheduler` 的 `ErrorHandler` 处理（默认只打一行日志），
看起来"任务还在跑"，但如果是**每轮都抛**（比如 SQL 写错了），你会看到一堆日志却修不掉任何东西。
显式 `catch` 至少能保证"这一轮失败"被清清楚楚记录成一条 `【对账】本轮整体失败`。

### 7.4 实验污染：`rename table` 的 12 秒窗口要避开整分

对账是每整分跑一次。做"表不可用"实验时如果跨过整分边界，对账那一轮会因为 `SELECT` 抛异常而整体失败（被 7.3 的 catch 兜住），
日志里会多一条 `【对账】本轮整体失败`，容易让人误判成代码 bug。所以实验都安排在整分后 30 秒内开始、12 秒内结束。

### 7.5 `redis-cli` 版本差异：`--no-auth-warning` 不一定有

本机 `redis-cli` 较老，`--no-auth-warning` 直接报 `Unrecognized option`，脚本整行失效。
改用 `redis-cli -a 123321 <cmd> 2>$null`（PowerShell 里把 stderr 的告警丢掉）即可，
不要因为一条告警就把整条管道写成 `| Out-Null`，那样连输出也一起丢了。

### 7.6 别在 PowerShell 里连写多条含中文输出的 mysql 命令

`mysql` 的 `Duplicate entry` 走 stderr，PowerShell 5.1 会把 `NativeCommandError` 当成终止性错误，
**后续命令不再执行**（我第一次验证 1062 时，后面的 `delete` 清理就没跑）。
要么分多次调用，要么在命令末尾加 `2>&1 | Select-Object -First 3` 把它收成普通输出。

## 八、局限与后续

| 局限 | 说明 | 建议 |
|---|---|---|
| **无法反序列化的报文拿不到** | DLQ 监听器用的是和主队列同一个 `Jackson2JsonMessageConverter`；如果报文本身不是合法 `SeckillOrderMessage`（只有外部生产者才会造成），转换会在**进入方法之前**失败，消息被 `reject(requeue=false)` 丢弃，且 `seckill.dlq` 没有二级 DLX | 本项目生产端只会发 `SeckillOrderMessage`，不受影响；将来若对接外部生产者，把 DLQ 监听器改成**只收 `Message` 并手动解析**，解析失败也要落一行 `status=2` |
| **对账是最终一致** | 最坏情况下（一轮门禁 + 两轮确认）偏差会存活约 **2 分钟**；这期间 `Redis > DB` 会继续放行预扣，`Redis < DB` 会继续少卖 | 偏差只影响"数字"，不影响"账本"：超卖方向有 DB `stock>0` + `uk_uid_vid` 兜底；想更快就缩短 cron 间隔，但必须同步缩短"两轮确认"的等待（现在 3 秒 ≪ 60 秒，是安全余量） |
| **`consumers=0 + ready>0` 只能靠日志发现** | 消费者全挂时门禁会永远拒绝修复（这是对的），但没人会主动发现 | ✅ 05 课已落地：`SeckillQueueAlertTask` 每 30 秒采样，违规持续 120 秒升级为 `【队列告警】`，恢复时主动打 `【队列告警解除】`；阈值在 `seckill.alert.*` |
| **`retry_count` 还没有重放入口** | 字段已经留好（自动对账不改它，只统计人工重放） | ✅ 05 课已落地：`POST /seckill/ops/dead-letters/{id}/replay`（路径不加 `/admin` 前缀，权限由 `AdminInterceptor` 挂在 `/seckill/ops/**` 上），重放前把 `status` 打回 0、`retry_count` 原子 +1 |
| **对账只覆盖"库存 + 已抢集合"** | 订单状态、支付状态不在本课范围 | 后续接对账报表（券维度：DB 订单数 vs Redis 扣减数 vs 死信数） |
