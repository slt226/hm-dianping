# 秒杀 P0 · 03 消费失败无重试、无死信 · 复盘

> 第三课。一句话：**catch 里回补 Redis + 容器无限重投 = 预扣闸门被"重试次数"线性放大成漏斗。**
> 重试必须"有次数、有退避、**有终点（死信）**"，补偿必须"整条消息只做一次"。
>
> 上一课（02 消费端幂等）解决的是「消息到了之后会不会被执行 N 次」；
> 这一课解决的是「执行失败了怎么办——重试几次、退避多久、彻底失败后消息去哪」。
> 所有数字都是本机实测（8081 / MySQL 3306 / Redis 6379 / RabbitMQ 15672）。

---

## 一、一句话概括

修复前，一条**必然失败**的消息（毒消息）会：

1. 被容器 `reject(requeue=true)` 塞回队列 → 立刻重新投递 → **2 秒重投 94 次**；
2. 每次失败都执行 `catch` 里的 `rollbackRedis` → **Redis 库存 97 被回补到 179**；
3. 日志 **2 秒涨 1 MB**，两个消费线程被一条消息轮流占死；
4. **永远消化不掉**：队列 ready 永远是 1，毒消息像堵在喉咙里的鱼刺。

修复后同一条消息：

| | 修前 | 修后 |
|---|---|---|
| 方法执行次数 | 82 次 / 2 秒（无限） | **3 次**（首次 + 重试 2 次） |
| 重试间隔 | 毫秒级狂刷 | **1s、2s** 指数退避 |
| Redis 库存 | 97 → **179**（+82） | 97 → **98**（只 +1） |
| 日志增量 | 1036.5 KB | **44.2 KB** |
| 主队列 ready | **1（永久堵塞）** | **0**（尸体已移走） |
| 消息最终去向 | 死循环 | **`seckill.dlq` + 告警日志** |

## 二、交付清单

| 层 | 文件 | 内容 |
|---|---|---|
| 配置 | `application.yaml` | `listener.simple.retry`（3 次 / 1s×2 退避）+ `default-requeue-rejected: false` |
| 配置 | `RabbitMqConfig` | 主队列加 `x-dead-letter-exchange` / `x-dead-letter-routing-key`；新增 `seckill.dlx` / `seckill.dlq` / `seckillDlqBinding` |
| 消费端 | `VoucherOrderConsumer` 最后一个 `catch` | **删除 `rollbackRedis`**，只 `log.error` + `throw e` |
| 消费端 | `SeckillDeadLetterConsumer`（新增） | 监听 `seckill.dlq`，做**一次性**回补：先查 DB 是否已落库 → 再 `SETNX` 幂等护栏 → 回补 Redis |

## 三、问题现场（实验 3-A：探针 + 强杀）

### 3.1 怎么造一条必死的消息

在 `handleSeckillOrder` 的 `try` 内、`insert` 之前埋探针：

```java
try{
    if(orderId!=null && orderId<0){
        throw new IllegalStateException("模拟下游异常(故障注入)");
    }
    voucherOrderMapper.insert(order);
}
```

投一条 `orderId=-1` 的消息即可。**探针位置极其关键**，见第六节 6.1。

### 3.2 实测数据（探针在 `try` 内）

```
BEFORE: REDIS=97  MEMBERS=3          （预扣 1 张 + 假用户 99999）
2 秒后强停应用：
OUR_CATCH_LOG=82      ← 方法被调用失败 82 次
REDIS_INCR=+82        ← 97 → 179，1:1 线性放大
DB_STOCK=98           ← 事务回滚兜住了，账本没错
MEMBERS=12|1016       ← 99999 第一次回补就被解锁了
GROWTH_KB=1036.5      ← 2 秒 1 MB 日志 ≈ 30 MB/分钟
QUEUE ready=1         ← 毒消息还在队里，永远消费不掉
```

日志里两个线程轮流出场，说明**毒消息会轮流毒害每一个消费者**：

```
WARN [RabbitListenerEndpointContainer#0-1] ConditionalRejectingErrorHandler : Execution of Rabbit message listener failed.
Caused by: java.lang.IllegalStateException: 模拟下游异常(故障注入)
WARN [RabbitListenerEndpointContainer#0-2] ...（200ms 后轮到另一个线程）
```

### 3.3 为什么会放大：一条乘法公式

```
Redis 库存增量 = 失败次数 × 每次失败的回补量(+1)
失败次数      = 无限（无 max-attempts、reject 后 requeue=true）
```

修复前是「**无限 × 1**」，所以库存会被吹到无穷大。加了 `retry: max-attempts: 3` 而不改 `catch`，就变成「**固定 3 × 1**」——
从"炸成 179"变成"稳定多 3 张"，**依然是超卖，只是没那么刺眼**。
这就是为什么这一课**两个改动必须成对出现**：

> **限制重试次数（retry）** 只解决"无休止"；
> **把回补搬出重试循环** 才解决"回补被放大"。

## 四、修复：四件套，缺一不可

### 4.1 本地重试：有次数、有退避

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 2
        prefetch: 1
        default-requeue-rejected: false
        retry:
          enabled: true
          max-attempts: 3         # 总共 3 次 = 首次 + 重试 2 次
          initial-interval: 1s
          multiplier: 2           # 1s -> 2s
          max-interval: 10s
```

**为什么用本地重试而不是让 MQ 重投？**

| | 本地重试（本次采用） | MQ 重投（reject + requeue） |
|---|---|---|
| 消息标记 | 不置 `redelivered` | 每次重投都置 `redelivered=true` |
| 退避 | 支持 1s / 2s 指数退避 | 立刻重投，无退避（就是 94 次/2 秒的来源） |
| 队列压力 | 消息不出容器 | 消息在队列里反复进出，监控曲线全乱 |
| 代价 | **占住消费者线程**（所以 `max-attempts` 不能配大） | 线程被让出，但消息会被别的线程抢到继续炸 |

> 生产含义：`max-attempts` 是「拿线程时间换成功率」的旋钮。配 10 次 + 1s×2 退避 = 一条毒消息占线程 511 秒。
> 本项目 3 次足够：下游抖动通常 1~3 秒内自愈，超过就该进死信让人看。

### 4.2 `default-requeue-rejected: false` —— 没有它，retry 等于白配

Spring 的默认行为是：重试耗尽后抛 `AmqpRejectAndDontRequeueException` 才算"别再投了"，
但普通 `RuntimeException` 走到容器时，`default-requeue-rejected` 默认 **true** → **requeue 回去**。
于是 `max-attempts: 3` 只是把"无限重投"变成"每轮 3 次、无限轮"，队列照样堵死。

这一行是**开关**，不是优化项：`false` 才能让重试耗尽的瞬间 `reject(requeue=false)`，进而触发 4.3 的死信路由。

### 4.3 主队列挂死信：`x-dead-letter-*`

```java
@Bean
public Queue seckillQueue() {
    return QueueBuilder.durable(SECKILL_QUEUE)
            .withArgument("x-dead-letter-exchange", SECKILL_DLX)      // seckill.dlx
            .withArgument("x-dead-letter-routing-key", SECKILL_DLQ_KEY) // seckill.dlq.key
            .build();
}
```

死信三件套：`seckill.dlx`（DirectExchange）+ `seckill.dlq`（durable Queue）+ `seckill.dlq.key`（routing key）。

> ⚠️ **队列参数不可修改**：`x-dead-letter-*` 属于队列声明参数，若已存在同名同参队列，启动会报
> `PRECONDITION_FAILED - inequivalent arg 'x-dead-letter-exchange'`。
> 所以改参数前**必须先删队列**（本次执行了 `DELETE /api/queues/%2F/seckill.queue`）。

### 4.4 回补搬到死信消费者，并且只做一次

`VoucherOrderConsumer` 的 catch 改成：

```java
catch(Exception e){
    // 只抛出：让 @Transactional 回滚 DB，交给容器 retry 重试。
    // 绝不能回补 Redis —— 本地重试会重复调用本方法，回补会被放大 N 倍。
    log.error("创建订单异常，交由容器重试 | orderId={}, userId={}, voucherId={}", orderId, userId, voucherId, e);
    throw e;
}
```

补偿移到 `SeckillDeadLetterConsumer`，它有三道保险：

```java
// ① 先看 DB：订单已落库说明是"成功单"，回补就是超卖
if (orderId != null && voucherOrderMapper.selectById(orderId) != null) { return; }

// ② SETNX 幂等护栏：concurrency=2 让死信消费者也有 2 个线程，
//    同一订单若有多条死信，两个线程会同时通过 ①，各自回补一次 → 库存反向膨胀
Boolean first = stringRedisTemplate.opsForValue()
        .setIfAbsent("seckill:dlq:done:" + orderId, "1", 24, TimeUnit.HOURS);
if (!Boolean.TRUE.equals(first)) { return; }

// ③ 回补：库存 +1、用户出集合（失败只记日志，死信本身可作补偿依据）
```

**为什么 `@Transactional` 和重试能共存？**
容器每次重试都是**重新调用代理对象**，`@Transactional` 每次开一个新事务；
第 1 次失败 → 事务回滚（DB 库存还原）→ 等 1s → 第 2 次又是全新事务。不会出现"脏事务复用"。

## 六、踩过的坑（每个都会让你误判实验结果）

### 6.1 探针放错位置：只复现了"无限重投"，没复现"回补放大"

第一次把探针放在**方法最前面**（幂等门禁之前）：

```
REDELIVERED=94   ← 重投确实发生了
REDIS_AFTER=97   ← 但库存纹丝不动？！
```

原因：`rollbackRedis` 只写在**最后一个 `catch`** 里，而那个 `catch` 包的是 `insert`。
探针在 `try` 之前抛异常 → 根本没进 `try` → `catch` 不执行 → 一次回补都没有。

**教训**：埋探针前先想清楚"我要证明哪条路径"。要复现放大，探针必须落在 `try` 内、`rollbackRedis` 的调用链上。

### 6.2 `FAULT_LINES=0`：中文关键词 + 编码双重假阴性

日志明明写着 `模拟下游异常(故障注入)`，`Select-String -SimpleMatch '故障注入'` 却返回 0：

1. 实际文案是 `模拟下游异常(...)`，脚本里搜的是 `模拟下游故障` —— **关键词不一致**；
2. 日志是 GBK 写的，`Select-String -Path` 按 UTF-8 读，中文匹配不上；`Get-Content | Select-String` 走管道才读对。

**教训**：量日志优先用 **ASCII 关键词**（异常类名、SQL 片段），例如 `IllegalStateException`。

### 6.3 一条失败写两份堆栈，次数会翻倍

```
ATTEMPTS=146（grep IllegalStateException）
OUR_CATCH_LOG=82（grep 我们自己的 log.error）
REDIS_INCR=+82  ← 只有它和 82 严丝合缝
```

每次失败有两份堆栈：我们的 `log.error("创建订单异常...", e)` + 容器的 `ConditionalRejectingErrorHandler`。
**权威口径要选"恰好每失败一次执行一次"的那句话**——这一次是 `rollbackRedis` 的副作用计数。

### 6.4 杀进程后 `ready=0` 是假象

`Stop-Process -Force` 后 1 秒内查队列，得到 `ready=0`（消息还在 unacked 里，broker 尚未处理连接断开）。
几秒后再查才是 `ready=1`。

**教训**：验证"消息是否回到队列"要等 3~5 秒，或连查两次取第二次。

### 6.5 `Start-Process -PassThru` 拿到的 `Id` 可能不是真 JVM

```
$app.Id = 29580   ← Oracle javapath\java.exe（转发器）
真 JVM  = 29664   ← 只有它监听 8081
```

杀掉转发器会留下孤儿 JVM：端口继续被占、队列继续刷，看起来"停不住"。

**正确写法**：

```powershell
$p = (Get-NetTCPConnection -LocalPort 8081 -State Listen).OwningProcess
Stop-Process -Id $p -Force
```

### 6.6 `mvn package` 前必须先停应用

Windows 下运行中的 `java -jar` 会锁住 `target\*.jar`，打包直接 `BUILD FAILURE`（文件被占用）。
顺序永远是：**按端口找 PID → 停 → 打包 → 起 → 等就绪**。

## 七、设计取舍与遗留

| # | 遗留问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 死信消费者 ack 掉了消息，**尸体只留在日志里** | 无法批量重放，运维只能翻日志 | 落 `tb_seckill_dead_letter`（payload、异常、时间、重试次数）由 04 课完成；人工重放接口见 05 课 `POST /seckill/ops/dead-letters/{id}/replay` |
| 2 | `concurrency: 2` 是**全局**配置，死信消费者也起了 2 个线程 | 同一订单多条死信时可能重复回补 | 已用 `SETNX seckill:dlq:done:{orderId}` 兜住；更彻底可给 DLQ 单独建 `RabbitListenerContainerFactory`（concurrency=1） |
| 3 | 毒消息仍会占住一个消费者线程 ~3 秒 | 高峰期吞吐略降 | 可接受；`max-attempts` 与 `concurrency` 一起调 |
| 4 | 死信没有外部告警通道（只有 `log.error`） | 无人值守时可能没人看 | 05 课已补「`ready>0` 且 `consumers=0` 持续 120 秒」的自动告警（`SeckillQueueAlertTask`）；钉钉/企微机器人仍待接 |
| 5 | 回补只补 Redis，不回补 DB | 正确行为：DB 库存由事务回滚负责，不需要额外补偿 | 无需改 |

## 九、这一课没解决的事（交给 04）

本课把"失败的消息"处理干净了：重试 3 次、耗尽进 DLQ、死信消费者回补 Redis。
但有三个口子还开着，正好是下一课《秒杀 P0 · 04 死信落库与对账》的主题：

| 本课遗留 | 后果 | 04 怎么解 |
|---|---|---|
| 死信只留一行 ERROR 日志，**没有 payload、没有状态** | 日志一滚（或按天归档）就再没人知道这张券少卖了一张 | 落 `tb_seckill_dead_letter`（`uk_order_id` 去重 + `status` 三态） |
| 死信消费者回补失败后 `catch` 一下就结束 | 这一张库存**永久蒸发**，没有任何人会重试 | `status=0` 留给 `settlePending` 每分钟重试；表本身就是"待补清单" |
| 没人报错的坏账（超卖底账、闸门偏低、集合缺人/幽灵）无人发现 | 安静地错下去，直到用户投诉 | `SeckillReconcileTask` 每分钟对账，按 `Redis = DB − P` 收敛四类偏差 |

一句话衔接：**03 保证"失败的消息不会丢"，04 保证"丢了的东西能被找回来"。**

## 十、结论

| 问题 | 答案 |
|---|---|
| 重试配几次 | **3 次**（首次 + 2 次重试），1s×2 退避；毒消息最多占线程 3 秒 |
| 重试放哪 | 消费者**本地**（`listener.simple.retry`），不靠 MQ 重投 |
| 重试耗尽后消息去哪 | `reject(requeue=false)` → `seckill.dlx` → `seckill.dlq` |
| 为什么必须 `default-requeue-rejected: false` | 否则重试耗尽后仍 requeue，变成"每轮 3 次、无限轮" |
| 回补 Redis 放哪 | **死信消费者**（每条死信只执行一次）；绝不能留在重试循环里的 catch |
| 补偿怎么保证不重复 | 先查 DB（防超卖）+ `SETNX seckill:dlq:done:{orderId}`（防并发重复补偿） |
| 怎么证明修好了 | 六项判据：执行 3 次 / 间隔 1s+2s / 死信 ack=1 / Redis 只 +1 / DB 不变 / 主队列 ready=0 —— 且**再做一次门禁与成功路径回归** |
| 最重要的一句话 | **宁可少卖（死信可人工补），不可超卖（DB 无货却卖出去）。** |
