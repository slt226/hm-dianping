## 关键发现与修复

### 1. 编译期 Bug：Lombok 与 JDK 17 不兼容（用户贴出的报错）
- 报错：`java.lang.ExceptionInInitializerError` / `com.sun.tools.javac.code.TypeTag :: UNKNOWN`
- 根因：项目 pom 目标 `java.version=1.8`，继承 Spring Boot 2.3.12 父工程带来 Lombok 1.18.20。
  Lombok 注解处理器依赖 JDK 内部 API `com.sun.tools.javac.code.TypeTag`，该常量在 **JDK 16+ 已被移除/修改**，
  在 JDK 17 上编译时注解处理阶段直接抛 ExceptionInInitializerError。
- 修复：`pom.xml` 的 `<properties>` 中覆盖 `lombok.version=1.18.34`（支持 JDK 17）。
- 为什么够用：`java.version=1.8` 让 Maven 把字节码目标编成 Java 8（class file 52），
  Spring Boot 2.3.12 自带的 ASM 7.x 能正常读取，运行期不会再出现 CGLIB/ASM 的
  "Unsupported class file major version 61" 问题。所以只需修编译期 Lombok 即可。
- 验证：`mvn compile` / `mvn package` 均 BUILD SUCCESS。

### 2. 环境坑：Maven 在 Git Bash 下启动失败
- 报错：`ClassNotFoundException: org.codehaus.plexus.classworlds.launcher.Launcher`
- 根因：`bin/mvn`(shell 脚本) 在 `MAVEN_HOME` 为 Windows 路径(D:\...) 时拼出的
  `boot/plexus-classworlds-*.jar` 通配符无法在 Git Bash 展开；且 `/d/...`(MSYS) 路径作为
  `-classpath` 传给原生 java.exe 时没被自动转换，java 找不到启动器类。
- 修复：改用 Maven 自带的 **`mvn.cmd`**（Windows 批处理启动器，天然走 Windows 路径），
  调用时 `JAVA_HOME='D:\develop\jdk'`。验证 `mvn.cmd -version` / `compile` 正常。
  （另：机器上只有 JDK 17，无 JDK 8/11，故未采用"换 JDK"方案。）

## 第二次排查（21:xx）：Error starting ApplicationContext
- 用户贴出 `Error starting ApplicationContext` + `LoggingFailureAnalysisReporter`。
- **根因 = 端口冲突**：上一轮用 nohup 起的旧 app 实例（pid 19252）一直 LISTENING 在 8081，
  新实例抢同一端口 → `PortInUseException: Port 8081 is already in use` → 容器启动失败。
  与用户同时贴的 `UserServiceImpl.sendcode` 无关（该方法是请求期执行，启动期不触发）。
- 坑点：`Stop-Process -Id <pid> -Force`（PowerShell 工具）输出会被吞/不生效，
  需用 `netstat -ano | grep 8081` 拿 PID 后强制结束，再 `netstat` 复核端口已释放。
- 完整报错证据：`APPLICATION FAILED TO START / Web server failed to start. Port 8081 was already in use`。
- 清掉旧实例后 `--server.port=8081` 干净启动成功（`Started in 5.6s`，`/shop/1` HTTP 200）。

## 第三次排查（21:3x）：POST /user/code 仍显示"功能未完成"
- 用户已实现 `UserServiceImpl.sendcode`，但调用 `POST /user/code` 仍返回 `{"success":false,"errorMsg":"功能未完成"}`。
- **根因 = 跑的是旧 JAR**：`UserServiceImpl.java` 修改时间 21:22，而 `target/hm-dianping-0.0.1-SNAPSHOT.jar` 打包时间 20:34（早约 50 分钟）。
  之前只执行了 `mvn compile`（仅更新 target/classes），没有重新打进 JAR；`java -jar` 加载的仍是旧字节码（旧 sendcode 占位返回"功能未完成"）。
- 注：`UserController.sendCode` 本身正确调用 `userService.sendcode(...)`，无问题；`login/logout/me` 的"功能未完成"是 UserController 里写死的 //TODO 占位（真未实现），与 JAR 新旧无关。
- 修复：`mvn package -DskipTests` 重新打包（21:36）→ 杀旧实例（Windows PID 需用 PowerShell Stop-Process，Git Bash 的 kill 用 MSYS PID 杀不掉 Windows 进程）→ 新 JAR 重启。
- 复测：`POST /user/code?phone=13800138000` → `{"success":true}`；非法手机号 → `手机号格式错误!`。验证通过。
- **经验（重要）**：改 Java 源码后，`java -jar` 方式必须 `mvn package` 重新打包再重启；用 IDE 运行则 IDE 自动重编译。否则看到的是旧代码。

## UserServiceImpl.sendcode 代码审查（用户贴出，非 bug 来源）
- 代码本身正确可编译：有 `@Slf4j`；`RegexUtils.isPhoneInvalid` 经 `StrUtil.isBlank` 做了空值保护（传 null 判为无效，不抛 NPE）。
- 真正值得注意的设计隐患：验证码用 `session.setAttribute("code", code)` 存 **HttpSession**。
  单实例+同浏览器可用；但**跨实例/前后端分离跨域(CORS)场景下 session 不共享**，
  后续 `login` 取不到验证码会报"验证码错误"。黑马点评教程标准演进是改用 **Redis** 存验证码（带 phone 维度 + 过期时间 + 发送频率限制）。
- 另：当前 sendcode 无发送频率限制（防刷），属功能完善点，非崩溃 bug。
